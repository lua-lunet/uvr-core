abstract: >-
  On OpenZFS, fsync() cannot fail - it will wait until the application's changes are on disk before it returns. If there is a problem, such as a hardware failure, that causes the pool to suspend, then it may wait forever. This feels strange, but is acceptable according to the API contract: fsync() never returned success, so the application has no reason to believe its data is on disk. However, OpenZFS pools can recover if the fault is repaired, and so fsync() can still return. As it turns out though, it's possible in rare situations for the pool to return to service but not have actually put the data on disk. fsync() returns success, because it cannot fail, and the application has been lied to. This paper describes the path taken from the fsync() call, through the ZFS Intent Log, the transaction machinery, the pool failure system and the IO pipeline to understand what happens to IO when disks fail, and why OpenZFS believed that writes had succeeded when they had not. It goes on to describe changes to make OpenZFS understand that something had gone wrong and respond appropriately, such that fsync() once again cannot fail.

    5  Abstract

    6  On OpenZFS,fsync()cannot fail - it will wait until the application's changes are on disk before it returns. If there

    7  is a problem, such as a hardware failure, that causes the pool to suspend, then it may wait forever. This feels
    8  strange, but is acceptable according to the API contract:fsync()never returned success, so the application has no

    9  reason to believe its data is on disk.
   10  However, OpenZFS pools can recover if the fault is repaired, and sofsync()can still return. As it turns out
   11  though, it's possible in rare situations for the pool to return to service but not have actually put the data on disk.
   12  fsync()returns success, because it cannot fail, and the application has been lied to.
   13  This paper describes the path taken from thefsync()call, through the ZFS Intent Log, the transaction machinery,

   14  the pool failure system and the IO pipeline to understand what happens to IO when disks fail, and why OpenZFS

   15  believed that writes had succeeded when they had not. It goes on to describe changes to make OpenZFS
   16  understand that something had gone wrong and respond appropriately, such thatfsync()once again cannot fail.

   17  1. Background

   18  In early 2023 an organisation with a huge deployment of OpenZFS pools came to us with a problem. This

   19  organisation runs a cloud storage service, where they receive files from customers and store them to an OpenZFS
   20  dataset. To ensure that the files were stored safely, they would callfsync()at the end of each file write, and not
   21  return a"success"message to their customer untilfsync()completed successfully, guaranteeing that the file was

   22  safely and reliably stored.

   23  They were having problems with their SAS backplanes. At times, for no apparent reason, they would lose power,

   24  appearing to the OS that multiple disks had failed at the same moment. When this occurred OpenZFS would

   25  simply wait. After a short time, the backplane would return, and OpenZFS would continue. This was not ideal,

   26  but was determined to be a fault in the backplane itself.

   27  Sometimes, after this happened, an attempt to read a file would result in an IO error. Investigation found that the
   28  fsync()call was in progress at the time the backplane failed, and after it returned and OpenZFS recovered, the
   29  fsync()call had returned success, even though the file was clearly not correctly written to disk.

   30  We were asked to investigate what was happening and make appropriate modifications to OpenZFS to ensure
   31  thatfsync()never returns success unless the file is really properly stored.

   32  2. The OpenZFS write path

   33  This section provides a brief overview of how filesystem modifications submitted by a user application make their

   34  way through OpenZFS and out to disk. Readers familiar with OpenZFS internals will note that this is a rather

   35  simplified view, but is all the context needed to understand the rest of this paper.

   36  2.1. The DMU and the SPA

   37  The Data Management Unit (DMU) is a component inside OpenZFS that provides the notion of "objects":

   38  arbitrarily-sized runs of data, named by a single 64-bit identifier. The facilities used by user programs to interact

   39  with OpenZFS, like filesystems (files, directories), volumes and even whole datasets are all implemented as

   40  different kinds of objects.

   41  Under the DMU is the Storage Pool Allocator (SPA). This is the component of OpenZFS that manages the physical
   42  devices and allocates"blocks"from them to be used for storage. Each DMU object is constructed from a tree of

   43  blocks.

   44  2.2. Transactions

   45  The SPA and the DMU share the notion of a"transaction". Modifications made to a DMU object (eg a file) are

   46  accumulated in memory, and assigned to a transaction. After some time, the transaction is closed and starts being

   47  written out to disk, and a new one is opened for the next round of changes to be assigned to. As such, a

   48  transaction is the fundamental unit of storage atomicity in OpenZFS.

   49  2.3. Transaction sync

   50  After a transaction is closed, the DMU iterates over all the changes it has accumulated and submits them to the

   51  SPA as writing IO requests. Because they all belong to the same transaction, they are submitted in a way that if it

   52  one causes an IO error, they all fail with that error. This is important, as there are different subsystems all over

   53  OpenZFS waiting for their return before moving on to something else, so it does no good to return success for a

   54  specific change if the entire transaction failed.

   55  2.4. Labels and uberblocks

   56  Once the data writes are completed, the pool-wide"uberblocks"and the per-device"labels"are updated with
   57  information about the new transaction. These are what OpenZFS looks for when importing a pool, so until they're
   58  fully written out, the transaction does not"exist", as such.
=== PAGE 3 ===

   59  These are written in a special sequence. First the "even"label is written to each device and flushed, then the
   60  uberblocks are written and flushed, then the"odd"label is written and flushed. This is done so that if power is
   61  lost, at import OpenZFS can tell where in the sequence it failed, and understand which transaction is the"correct"

   62  one.

   63  2.5. Signal waiters

   64  Once the transaction is fully written out, waiters all over OpenZFS are woken to inform them of this fact. There's
   65  many that might be waiting depending what's going on at the time, not least the thread waiting to begin syncing

   66  the next transaction out.

   67  3. How OpenZFS implementsfsync()

   68  3.1. What isfsync()?

   69  Thefsync()system call has the prototype:

   70  int fsync(int fildes);

   71  The common understanding is that when called on an open file, its successful return indicates that the file is

   72  durably stored on disk. The expectation is that an unexpected system failure (eg power loss) at that moment
   73  would not affect the file, and after the system is recovered the file contains all the data written up to thefsync()

   74  call. It is often used as a building block for transactional IO.

   75  3.2. The ZFS Intent Log

   76  OpenZFS'transactional model presents a challenge for implementing a system call likefsync(), which requested

   77  that all changes for a single file be stored immediately. Changes accumulated in a transaction may touch multiple
   78  files, and they may be dependent on each other. It's not really possible to commit the changes for a single file
   79  separately from the rest of the transaction. One could makefsync()forcibly commit the entire transaction, but

   80  that can be very slow if the requested file was just one of thousands modified in the transaction.
   81  OpenZFS handles this situation as many other storage systems do, by keeping a"journal"or"intent log"of the

   82  logical changes that have been made on each file. This component inside OpenZFS is known as the ZFS Intent

   83  Log, or ZIL.

   84  Every modification made to a file is now stored in memory twice: once in the Data Management Unit (DMU) as a

   85  normal part of the file state, and again in the ZIL as a record of the operations taken to get the file to that state.

   86  For example, a typical file write sequence might look like:
=== PAGE 4 ===

   87  int fd = open("somefile",O_CREAT | O_WRONLY);
   88  write(fd,"somedata",8);
   89  write(fd,"moredata",8);
   90  close(fd);

   91  In the ZIL, this would generate a sequence of intent log entries. Simplified, they might look like:

   92  TX_CREATE <dirobj> <fileobj> "somefile"
   93  TX_WRITE <fileobj> 0 8 "somedata"
   94  TX_WRITE <fileobj> 8 16 "moredata"

   95  Then, whenfsync()is called on a file, the relevant portions of this list are immediately written to a special
   96  "replay list"associated with each dataset. Only the entries for files specifically requested byfsync(), and any
   97  that were modified as a result, are actually added to the replay list. In this case,fsync()on the file we created

   98  would also add any modifications for the directory object to the replay list.

   99  When the transaction completes and is written down to its final resting place, all in-memory intent log entries are
  100  destroyed, and the on-disk replay list is deleted. This means there's only minimal overhead if nothing uses
  101  fsync()- the intent log entries are only ever in memory.

  102  The last piece of the ZIL is the replay facility. When a dataset is mounted, the replay list is checked. Any

  103  operations there are applied, so the filesystem state moves forward from whatever it was at the last completed
  104  transaction to also have any changes that were explicitlyfsync()'d during the last incomplete transaction.

  105  3.3. Transaction sync fallback

  106  If writing the ZIL replay list fails, the fsync()call simply falls back to waiting for the transaction to be

  107  committed. This is the situation the ZIL exists to avoid, but it is the only remaining option that preserves
  108  fsync()'s API guarantee. When the transaction is successfully committed, the changes are on disk, andfsync()

  109  can return success.

  110  4. How OpenZFS handles device failure

  111  4.1. Device probes

  112  OpenZFS takes a passive approach to detecting device failure. In the general case, it will assume that a device

  113  exists and is in good health until and unless an IO request sent to it returns a error.
  114  Most errors will result in a"probe"sequence being sent to the device. First, an attempt is made to read from the

  115  labels stored on that device, which are always in a known location. If the read succeeds, an attempt to write a new

  116  label is made. The outcome of these tests are saved, and will decide how the device is used in the future; for
  117  example, if a device can't be written to, then no further attempts will be made to store new data to it.

  118  Once the probe sequence has completed, the original IO request is reprocessed. If the probe failed, the IO request
  119  will be forced to have a"no such device"error (ENXIO) and returned to the caller. Often, an interior vdev (eg a

  120  raidz control vdev) can compensate for this, reassigning the IO to a different physical device and retrying it. This

  121  is how pool redundancy options typically work.
=== PAGE 5 ===

  122  If the probe succeeded, then the IO request will be retried. If it still fails, then there is clearly something very

  123  strange going on, and the pool is suspended. The original IO and any others in flight are held in a suspend list.
  124  This has the effect that all user operations block. Once an operator has corrected the fault and runzpool clear,

  125  failed devices are re-probed and if everything looks good, the suspended IO is reissued.

  126  This describes the most common failure process. OpenZFS has many different kinds of IO and many possible
  127  ways to set up a pool, so there's many other things that it tries to correct for, and many special cases. There are

  128  two place in particular where something different happens that are relevant to our secnario.

  129  4.2. ZIL write failure

  130  ZIL writes are issued with a special IO request flag,ZIO_FLAG_CANFAIL. If this type of request fails, the device is

  131  still probed and removed from service if the probe fails, but the original request will not be retried, instead just

  132  returning the original error. The ZIL does this because a failed retry can suspend the pool, which is a rather

  133  heavy-handed response when the ZIL has a fallback available - simply waiting for the transaction to complete. If

  134  the failure is transient, then the transaction will complete normally and the data will be safely on disk, allowing
  135  fsync()to return success.

  136  4.3. Flush failure

  137  Much like filesystems, hard drives typically have their own internal caches that they use to improve performance.

  138  As such, a successful response to a disk write IO may not mean that the data has been physically written to the

  139  disk yet, and if power to the device is lost, so too may the data be.
  140  To help with this, hard drives offer a"flush"operation that forces cached data to be written out, not unlike what
  141  fsync()is to filesystems. As with filesystems, there are several flushing operations available. OpenZFS makes
  142  use of a "write barrier"flushing operation, which is sent independent of other IO types. Its purpose is to

  143  completely write everything in the drive cache to the physical disk. OpenZFS issues device flushes to all devices

  144  in the pool after uberblock, label and ZIL writes complete successfully.

  145  However, and somewhat surprisingly, OpenZFS ignores the response to flush requests, and has done so since ZFS
  146  was first integrated into Solaris. 1 The reasons for this are unclear, but this author s guess is that initially hard
  147  '

  148  drives generally did not have cache memories or flushing operations, and even once they became widespread an

  149  uncaught flush error was extremely unlikely to not be accompanied by related write error or some other

  150  significant hardware fault, so any problem that has been seen was likely discounted as a freak occurrence.

  151  5. Howfsync()fails

  152  5.1. Guaranteed success

  153  In OpenZFS,fsync()only ever returns0, indicating success.
  154  Internally,fsync()is implemented byzil_commit(), which presents an API contract that guarantees success:

  155  void zil_commit(zilog_t *zilog,uint64_t oid);
=== PAGE 6 ===

  156  To make this guarantee, it relies on the fact that if something goes wrong in its own IO, it can fall back to waiting

  157  for the whole transaction to be committed:

  158  void txg_wait_synced(struct dsl_pool *dp,uint64_t txg);

  159  Given these API contracts,fsync()could not be any other way.
  160  This guarantee is a reflection of OpenZFS'fundamental goal of never losing data. The systems described in the

  161  previous sections all work together to ensure that OpenZFS is always aware of where in the pipeline data is, and

  162  it is fundamentally designed to stop the world by suspending the pool if it cannot find a way to make progress.

  163  By design, there is no path through the system whereby a write operation could fail without the entire system

  164  failing, so it is sufficient to assume that forward progress means everything is in good shape.

  165  Unfortunately, because flush errors are not checked, this only holds if writes are guaranteed to succeed. Ironically,

  166  the very presence of a flush operation makes it clear that this guarantee cannot possibly be true in all cases.

  167  5.2. Flushed away

  168  This problem was first presented to us with a failed backplane, but it can also apply to failures in disks, cables,

  169  disk units or power supplies. If the connection is lost to the disk, the OS notices and takes the disk offline, and any

  170  further IO receives an immediate error. If the error is in response to a write request, OpenZFS notices and
  171  responds as described above. If the failure occurs between write and flush however, OpenZFS won't notice and

  172  will proceed, believing all is well.
  173  When the ZIL write succeeds,fsync()returns success. If the connection to the disk fails just after the write and
  174  the flush fails, OpenZFS doesn't know, but even if it did, it would be too late - the user program has already

  175  moved on. This is often survivable - if the pool is still able to operate without the failed disk, the transaction can
  176  still be written out correctly, and the"lost"ZIL write is not needed.

  177  If, on the other hand, the pool does not have sufficient redundancy (eg the whole backplane failing), the tree of

  178  writes for the entire transaction will fail shortly after. This happens during the label/uberblock flush sequence, so

  179  the pool will suspend and the failed IOs will be held. Usually, if the failure can be corrected, the pool will resume,

  180  replay the lost IO, and the data will end up being written out correctly.

  181  What often happens in this situation is that an operator will take some service continuity action, like begin a

  182  service failover to another machine, and then power-cycle the system. After correcting the fault, the pool is

  183  imported, and recovery actions run. The ZIL replay log will be scanned, but since the flush failed, some or all of
  184  the log can be missing. The write that OpenZFS promised made it to disk (via its successfulfsync()return) is

  185  permanently lost.

  261  7. Handling ZIL flush failures

  262  7.1. Propagate flush

  263  The flushing functionzio_flush()is very simple:

  264  void
  265  zio_flush(zio_t *zio,vdev_t *vd)
  266  {
  267  zio_nowait(zio_ioctl(zio,zio->io_spa,vd,DKIOCFLUSHWRITECACHE,
  268  NULL,NULL,
  269  ZIO_FLAG_CANFAIL | ZIO_FLAG_DONT_PROPAGATE | ZIO_FLAG_DONT_RETRY));
  270  }

  271  The flag combination is about the most aggressive way to issue IO and not care what happens:

  272  DONT_RETRY: if this operation fails, don't bother trying again
  273  CANFAIL: if this operation fails, don't suspend the pool
  274  DONT_PROPAGATE: if this operation fails, don't tell me about it

  275  DONT_RETRYandCANFAILare probably reasonable; the success or failure of a flush is a crucial piece of information
  276  we need to manage the pool state. The IO layer shouldn't blindly retry on error and assume all is well if the retry

  277  succeeds, but neither should it just blindly suspend the entire pool since the meaning of the error will depend on

  278  the context the request was issued in.

  279  DONT_PROPAGATEhowever is obvious not reasonable. A flush failure means something, and we have to tell

  280  someone!

  281  Our first attempt to fix this was to simply propagate flush errors into the ZIL. The ZIL code is already structured

  282  to support this; writes and flush IOs are already properly chained together such that a flush failure would cause

  283  the write to fail, and there are comments explaining how it would work, if only flush errors were propagated:

  284  /*
  285  * We expect any ZIO errors from child ZIOs to have been

  289  * flush, as well as any errors from other dependent LWBs
  290  * (e.g. a root LWB ZIO that might be a child of this LWB).

  292  * With that said, it's important to note that LWB flush
  293  * errors are not propagated up to the LWB root ZIO.
  294  * This is incorrect behavior, and results in VDEV flush
  295  * errors not being handled correctly here. See the
  296  * comment above the call to "zio_flush" for details.
  297  */

  298  and:

  299  vdev_t *vd = vdev_lookup_top(spa,zv->zv_vdev);

  322  7.2. Too much flushing

  323  Most IO requests in OpenZFS are issued to a top-level vdev (eg a raidz or mirror) and lets that vdev decide how
  324  to distribute that to its children. zio_flush()looks like that from the outside, but the function under it,
  325  zio_ioctl(), doesn't actually work that way.

  326  zio_t *
  327  zio_ioctl(zio_t *pio,spa_t *spa,vdev_t *vd,int cmd,
  328  zio_done_func_t *done,void *private,enum zio_flag flags)
  329  {
  330  zio_t *zio;
  331  int c;

  345  Instead, it walks the vdev tree building a matching tree of IO requests, and true physical IO requests are only
  346  issued to leaf, that is,"real"devices. So in our case, all 12 drives in the pool receive a flush.
  347  At minimum, this is wasteful, as we're sending flushes to disks that we never wrote anything to, and waiting for

  348  them to respond. The real problem however is that the entire top-level operation succeeds ifall leaf operations

  349  succeed, but fails ifany leaf operations fail.
  350  If we've lost enough disks to suspend the entire pool, this doesn't matter - several disks really will fail their flush

  351  operation, and the pool will rightly suspend. However in the case of a regular degraded pool, where only a single

  352  disk is lost, that disk will also return failure to its flush operation, and again, the entire top-level flush operation

  353  fails.

  354  For our ZIL flushes, that will also fail the ZIL write, which will cause the ZIL to fallback to waiting for the
  355  transaction to be written out, and fsync()to return success. This destroys performance - now every call to
  356  fsync()has to wait, as though the ZIL didn't exist at all.

  373  7.3. An unknown amount of flushing

  374  We spent a long time experimenting with different ways of trying to work around this, with limited success,

  375  before finally understanding the problem and fixing it properly.
  376  The original problem was that we just received a successful response to a ZIL write, but we don't know if it's truly

  377  on disk:

  378  The pool might be in perfect shape, and the write happened normally.

  379  The write may have failed initially, and OpenZFS probed a disk, found it failed, changed its state to
  380  "degraded"and then retried the write to different disks, which succeeded.
=== PAGE 12 ===

  381  The pool may be critically damaged, as in our original backplane failure, but the write has still succeeded.

  382  An operator may have removed a disk in a raidz vdev, and the write successfully happened to other disks in

  383  good health.

  384  What we really need to do is issue a flush for this IO, that is, we need to tell all the disks that were written to that
  385  they need to do a flush. At the same time, we must avoid any disks that wedidn't write to, as we don't know
  386  what they'll do. This means we need to somehow bind flushes to writes, so we only flush what was written, and

  387  no more.
  388  The problem is that at this layer within OpenZFS, all we have is the completed IO object. We don't know how it

  389  was serviced, by design - the entire point of the SPA is that that it presents a uniform interface to all kinds of pool

  390  topologies. We have no idea what happens under the hood.
  391  An early attempt to resolve this problem was to add an IO flag to indicate that this IO should be flushed as it's

  392  written. This is analogous to the SCSI Force Unit Access (FUA) flag, which enables a write-through (no cache)

  393  mode. This worked, in that the performance profile was not affected by a degraded device, but it still reduced
  394  fsync()performance, for two reasons:

  395  it forced a flush after every write, even when multiple writes for the same disk were on the IO tree
  396  it subverted a feature of the ZIL, which is to delay flushing when there's nothing actively waiting for a flushing
  397  operation (for the case where afsync()also required other objects to be flushed, even though there's nothing

  398  explicitly waiting for them)

  399  In the end, we decided that there was no other way, and we would have to know exactly which disks we had

  400  written to in order to be sure that our writes had completed.

  401  7.4. Tracing IO

  402  Since we had to hook something deeper into the IO layer to make this work, we tried to make something

  403  reasonably generic, rather than tied specifically to flushing.
  404  We introduced the notion of "vdev tracing". When creating an IO request, a caller can add the
  405  ZIO_FLAG_VDEV_TRACEflag to indicate that this IO should be traced.

  406  A traced request is executed as normal: each stage of the IO pipeline may create child IO objects, and those create

  407  child IO objects, all the way down the the real disks. As child IO objects complete, as well as propagating their

  408  error code we now also propagate a list of any vdevs that returned a successful response while executing the IO.

  409  There are no other behaviour changes. Thus, when the original request is completed, it will still have the same

  410  overall success/fail response, and if it succeeds it will also have an attached list of all vdevs that were involved in

  411  its success. This list can then be used to instruct those vdevs perform any follow-up operations, such as a flush.

  412  By making our ZIL write request a traced request, so its completion handler can know where to issue a flush to.

  462  8. Status and further work

  463  The two major changes described here –flush error propagation and vdev tracing –are in production at the

  464  sponsoring organisation, and are working as planned.

  465  The intent is to offer these changes to upstream OpenZFS during 2024. These changes were developed against

  466  OpenZFS 2.1.5, so need to be forward-ported to the current development branch, and properly repeatable tests

  467  developed.

  469  sequence of writing labels and uberblocks and if so, how to do so safely.
