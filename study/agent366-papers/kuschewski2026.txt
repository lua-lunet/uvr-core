abstract: >-
  Cloud database systems cannot rely on instance-local disks for write-ahead logging (WAL) durability, forcing WAL onto remote storage. Existing options are unsatisfying: remote block storage like EBS is easy to adopt but adds substantial write latency and cost, while object storage offers excellent durability and low storage cost but is impractical for OLTP due to high latency and per-append cost. Many cloud-native databases, therefore, depend on purpose-built logging backends, which are typically proprietary and tightly coupled to engine-specific replication and recovery protocols, limiting reuse. We present BtrLog, a reusable cloud logging service that combines low-latency durable appends with low-cost archival for the common single-writer architecture. BtrLog replicates log records across a quorum of SSD-backed log nodes in a single network round trip, reducing sensitivity to stragglers in commit latency. To minimize storage cost, log nodes archive records to object storage as large segments, which are written asynchronously and off the latency-critical write path. In our evaluation, BtrLog achieves lower latency than EBS and enables higher end-to-end transaction throughput when integrated into a DBMS.

   14  ABSTRACT
   15  Cloud database systems cannot rely on instance-local disks for
   16  write-ahead logging (WAL) durability, forcing WAL onto remote
   17  storage. Existing options are unsatisfying: remote block storage
   18  like EBS is easy to adopt but adds substantial write latency and cost,
   19  while object storage offers excellent durability and low storage cost
   20  but is impractical for OLTP due to high latency and per-append
   21  cost. Many cloud-native databases, therefore, depend on purposebuilt logging backends, which are typically proprietary and tightly
   22  coupled to engine-specific replication and recovery protocols, limiting reuse. We present BtrLog, a reusable cloud logging service
   23  that combines low-latency durable appends with low-cost archival
   24  for the common single-writer architecture. BtrLog replicates log
   25  records across a quorum of SSD-backed log nodes in a single network round trip, reducing sensitivity to stragglers in commit latency.

  100  BtrLog: fast quorum, cheap archive. We argue that logging

  132  2 BACKGROUND: WAL IN THE CLOUD
  133  In this section, we briefly summarize WAL semantics and the resulting requirements on a logging backend, then review existing
  134  log systems and cloud storage services. The goal is to clarify the
  135  tradeoffs that motivate our design choices.

  136  2.1 WAL Semantics and Requirements
  137  Log interface. Write-ahead logging (WAL) in database systems
  138  requires only a small interface. During transaction execution, the
  139  DBMS appends log records via append [61]. Each record is assigned
  140  a monotonically increasing log sequence number (LSN). At commit,
  141  the engine calls sync to ensure all records up to the commit LSN
  142  are persisted – the ARIES paper [61] refers to this as forcing the log.
  143  For restart recovery, the engine issues a scan operation to retrieve
  144  log records starting from a given LSN. During recovery or rollback,
  145  it calls read to fetch individual records by LSN for undo processing.
  146  Key requirements. Because the log is the source of truth for
  147  recovery, ARIES-style logging requires durable storage that survives

  148  process, system, and device failures [61]. Accordingly, the logging
  149  backend must provide durability and high availability. It must also
  150  support low-latency appends, since WAL lies on the critical path of
  151  transaction processing. Cloud database systems may also operate
  152  at extreme transaction rates (e.g., 70 M/s [53]), producing massive
  153  log volumes. This makes cost-efficiency, both per append and per
  154  GB, another important requirement.
  155  Single-writer semantics. A key observation underlying our work
  156  is that many cloud and distributed databases achieve durability via
  157  per-partition (or per-replica) log streams. Each log stream has an exclusive writer at any given time. In primary/secondary architectures
  158  such as Amazon Aurora [76], Microsoft Azure SQL HyperScale [6],
  159  Alibaba PolarDB [53], and Google AlloyDB [36], only the writer instance issues updates and generates the corresponding log records.
  160  Similarly, in strongly consistent distributed database systems such
  161  as Google Spanner [23], each replicated partition (Paxos group)
  162  elects a leader. All writes are ordered through that leader, yielding a
  163  single total order of writes per group [23]. Even systems that expose
  164  multi-region write APIs (e.g., Cosmos DB [60]) implement durability via locally replicated physical partitions. Ordering guarantees
  165  are defined by a leader within the associated replication scopes [60].
  166  As we discuss next, exploiting the monotonic, single-writer append
  167  order (via sequence numbers) is key to reducing WAL latency.

  168  2.2 Log Service Architectures
  169  Durability and ordering guarantees. General-purpose distributed log systems, and some distributed streaming systems (e.g.,
  170  Apache Kafka), provide an append-only abstraction and use replication to achieve durability and availability. In contrast to the singlewriter WAL streams common in cloud database systems, they are
  171  designed for multiple concurrent writers. They therefore include
  172  a sequencer that orders writes across clients, linearizing appends.
  173  The need to coordinate ordering and replication adds substantial
  174  latency on the append path, and architectures differ in how these
  175  responsibilities are implemented, as Figure 1 visualizes.
  176  Consensus-based systems (Paxos, Raft, VSR). As the left-hand
  177  side of Figure 1 shows, leader-based consensus protocols [50, 66,
  178  67] replicate a log across a set of nodes coordinated by a leader.
  179  The leader serializes appends and replicates them to a quorum of
  180  followers, combining ordering and replication on the write path.
  181  Each append requires four network hops (or two network round
  182  trips): client → leader and leader → follower. The leader is both a
  183  throughput bottleneck and a source of latency variance.
  184  Throughput-optimized systems (Corfu, Scalog). Corfu [12],
  185  Scalog [27], and similar systems [11, 45] decouple sequencing from
  186  storage. This avoids the leader bottleneck by scaling the sequencer
  187  layer across nodes. However, these systems still use eager ordering [56]: clients receive an LSN for an append once both ordering
  188  and replication are complete (append(rec) → LSN). As Figure 1
  189  shows, this results in additional network communication across layers. The replication strategy further impacts latency: Corfu's chain
  190  replication requires six network hops; Scalog's primary-backup
  191  strategy reduces it to four, which is still well above the singleround-trip latency achievable with single-writer WAL semantics.
  192  Lazy ordering (LazyLog). LazyLog [56] reduces append latency
  193  by separating ordering from durability. Clients send metadata to

  222  system. Similarly, cost efficiency is also impacted by architectural
  223  decisions such as the integration of cloud object storage. The rest
  224  of the paper describes how BtrLog achieves low latency and cost
  225  while meeting WAL durability and availability requirements.

  226  3 BTRLOG DESIGN AND DEPLOYMENT
  227  Design space. One possible solution for WAL in the cloud is writing
  228  log records directly to cheap and durable object storage. However,
  229  object storage writes take tens of milliseconds [18] and are expensive for workloads with many small writes – such as WAL. At
  230  the other extreme, one can envision a DRAM-based design similar
  231  to RAMCloud [68], where the client sends data to a quorum of
  232  nodes ("log nodes") that keep data in DRAM and provide durability
  233  through replication. This approach provides low latency but is expensive due to high DRAM cost [72]. Furthermore, it is prone to

  260  3.1 System Overview
  261  BtrLog's high-level design. BtrLog overcomes durability and
  262  cost tradeoffs by combining a staging layer for low-latency appends
  263  with object storage for durable, cost-efficient persistence. BtrLog
  264  stages appends on a cluster of log nodes and flushes them asynchronously to object storage in large segments. Log nodes retain
  265  only a bounded unflushed tail locally: the tail resides in RAM for
  266  fast reads and is backed by local NVMe SSDs for recovery after
  267  crashes or power loss. By flushing large segments asynchronously,
  268  BtrLog amortizes object store PUT cost and eliminates both object
  269  store latency and long-term storage capacity management. BtrLog
  270  thus consists of four components, visualized in Figure 2:
  271  (1) a client library used by the DBMS to append log records,
  272  (2) a cluster of log nodes that form the staging layer,
  273  (3) a cloud object store for durable, low-cost storage, and
  274  (4) metadata storage for log metadata and cluster configuration.
  275  BtrLog requires few metadata operations, which can be implemented using conditional writes (If-Match in S3). Using S3 or a
  276  compatible service for metadata simplifies deployment and avoids
  277  a separate coordination system such as ZooKeeper or etcd.
  278  Log abstraction and API. BtrLog exposes a single-writer, appendonly log abstraction. The client library hides the internal storage

  298  Write path. The append (write) path is BtrLog's hot path, optimized for single network round-trip commits. As Figure 2 illustrates,
  299  each client maintains a local LSN counter and replicates appends in
  300  parallel to all log nodes 1 . Upon receiving an append, a node adds
  301  the record to an in-memory segment and writes it out-of-place [51]
  302  to a local NVMe SSD 2 . Only after the SSD write and fsync complete, the node acknowledges the append to the client. The client
  303  library returns success to the DBMS after receiving acknowledgments from a quorum of nodes. If multiple appends are in flight, the
  304  client library ensures that appends are acknowledged in LSN order
  305  to preserve ARIES semantics. This client-driven sequencing eliminates a separate sequencer, enables single round-trip latency, and
  306  masks network and SSD latency jitter [38] via quorum replication.
  307  Read path. BtrLog distinguishes between hot and cold reads. The
  308  hot, unflushed tail (e.g., for transaction rollback) is read from inmemory segments on log nodes 3 . Cold entries are read from
  309  flushed segments on object storage 4 (e.g., for point-in-time recovery), leveraging its aggregate read bandwidth while reducing load
  310  on log nodes. The client routes requests transparently via read and
  311  scan based on the requested LSN range and the replicated commit
  312  watermark, and may cache recently read tail records.

  314  Durability and correlated failures. BtrLog replicates each append to a quorum of 𝑄 log nodes before acknowledging it and
  315  𝑤
  316  thus tolerates up to 𝑄 − 1 node failures without data loss. For
  317  𝑤
  318  example, with 3 log nodes, 𝑄 = 2, and the system tolerates 1

  320  node failure. Log segments are flushed asynchronously to object
  321  storage for long-term durability 5 . To tolerate correlated failures
  322  (e.g., software bugs or power outages), each node persists the hot
  323  tail on its local NVMe SSD, similar to prior work on highly durable
  324  storage backends [19]. This increases append latency, but strengthens durability: if all log nodes crash because of a software fault,
  325  in-memory data is lost, whereas data persisted on local SSDs can
  326  be recovered after fixing the fault and restarting the processes.
  327  Single writer, multiple readers. BtrLog enforces a single-writer,
  328  multi-reader abstraction, supporting use cases like log shipping.
  329  The writer maintains a commit watermark that is replicated across

  330  log nodes, allowing readers to distinguish committed from uncommitted data. Enforcing a single writer prevents inconsistent appends
  331  during DBMS failover (e.g., when replacing a failed primary).
  332  Failure handling in the cloud. Quorum replication masks transient node failures and network jitter, providing predictable tail
  333  latency for appends. The client-side failover protocol 6 prevents
  334  split-brain during DBMS failover. BtrLog also handles compound
  335  and AZ+1 failure scenarios, as discussed in Section 4.
  336  Database integration. As Figure 2 illustrates, the DBMS integrates
  337  the BtrLog client into its WAL subsystem rather than writing log
  338  records to a storage device. When the primary starts, or when explicitly requested, the client creates a new log on the log nodes and
  339  registers the log in the metadata management layer (c.f., Section 4),
  340  which establishes the primary as the log's single writer. It is then
  341  free to append log records as described in Section 3.1.
  342  Transaction rollback. The client may cache recently appended
  343  records in memory to enable low-latency reads for abort and rollback. In addition, log nodes keep the hot log tail in memory, which
  344  accelerates hot reads. The hot log tail is asynchronously flushed to
  345  object storage when it fills up or becomes cold.
  346  Database recovery. The BtrLog client supports high-throughput
  347  reads of cold log data for database recovery. For example, when a
  348  database node must replay a large log prefix to reconstruct database
  349  state, the client transparently fetches the hot tail from log nodes and
  350  streams older segments from high-bandwidth object storage [30].
  351  Database failover. For planned maintenance or primary failure,
  352  a backup node can take over as the writer. When a BtrLog client
  353  opens an existing log for writing, it acquires ownership and fences
  354  off the previous writer to prevent conflicting appends. Section 4
  355  details the protocol that implements these mechanisms.
  356  Ease of use. Integrating BtrLog into an existing DBMS that relies
  357  on file system storage requires minor source code changes due to
  358  interface differences (append vs. write). Note, however, that filesystem-based logging necessitates protecting against torn writes
  359  and identifying the last successful log record write during recovery.
  360  BtrLog prevents both issues due to its record-level atomicity and
  361  failover support: its interface is purpose-built for database WAL.
  362  Parallel logging. To avoid contention on a single log, some highperformance DBMSs support parallel logging through multiple
  363  (e.g., per-thread) log streams [26, 41, 64, 78]. Such designs already
  364  manage transaction order across multiple log streams to ensure
  365  correct recovery and can thus simply use multiple BtrLog logs.

  366  3.3 Deployment Options
  367  Configurable availability. BtrLog supports two deployment options to adapt to different latency and durability/availability requirements: single-AZ and multi-AZ. Although we use AWS terminology,
  368  the same concepts apply to other cloud providers as well.
  369  Single-AZ deployment. To minimize append latency, BtrLog can
  370  be deployed in the same availability zone as the client application.
  371  An AZ consists of one or more data centers within an AWS region,
  372  which are isolated from failures such as power, network outages,
  373  or flooding [2]. Services such as EBS and S3 Express operate within
  374  a single AZ. Intra-AZ network communication has latency of about
  375  100 µs and is free of charge. BtrLog log nodes reside in partitioned
  376  placement groups [3] to reduce correlated failures like rack-level
=== PAGE 5 ===

  377  power or network faults. If the entire AZ becomes unavailable
  378  (e.g., due to a major power outage), all log nodes in that AZ and
  379  BtrLog become unavailable as well. Because BtrLog writes log
  380  records to instance-local SSDs, which persist data across power-loss
  381  reboots [4], data is still durable and can be recovered upon restart.
  382  Records that were already flushed to object store remain accessible
  383  during the outage, since S3 replicates data across multiple AZs.
  384  Multi-AZ deployment. To improve availability, BtrLog also supports deployments that span multiple AZs. A straightforward approach would place three log nodes across three AZs, ensuring
  385  that AZ failures affect only one replica. However, an additional
  386  independent failure (e.g., an SSD failure in a second AZ) can reduce
  387  a three-node deployment below the required 2/3 quorum, making
  388  the log unavailable for reads. To tolerate such AZ+1 failures [76],
  389  BtrLog uses six nodes (two per AZ). This configuration remains
  390  write-available after losing any two nodes or an entire AZ (4/6 append quorum), and remains read-available after losing up to three
  391  nodes (3/6 read quorum). Even with six nodes, BtrLog persists
  392  records to local SSDs to guard against correlated software failures.
  393  Improving cost-efficiency in multi-AZ deployments. Besides
  394  increasing latency, multi-AZ deployments also increase cost due to
  395  cross-AZ data transfer. For example, replicating 100 million 1 KB
  396  log records from one AZ to another AZ of the same AWS region
  397  transfers 100 GB and costs $2. The overhead is amplified by quorum
  398  replication: if a client sends each append to all four remote nodes,
  399  it pays the transfer charge per remote replica (e.g., 4 · $2 = $8).
  400  BtrLog reduces this overhead by 2× via hierarchical replication:
  401  the client sends each record to one node per AZ, which forwards it
  402  to its peer in the same AZ. This significantly reduces cost but only
  403  slightly increases latency because intra-AZ latency (about 100 µs)
  404  is significantly lower than cross-AZ latency (about 500 µs).

  405  4 PROTOCOLS AND FAULT TOLERANCE
  406  Our design is simple: quorum-replicated appends to a staging layer,
  407  with asynchronous, segment-based persistence to object storage.
  408  The challenge is to preserve BtrLog's guarantees under realistic
  409  cloud failure modes – transient faults, correlated node/AZ outages,
  410  and DBMS failovers – without sacrificing one-round-trip commits.
  411  To this end, we employ a leader-based quorum protocol with view
  412  changes, similar to Apache BookKeeper, customized for BtrLog's
  413  object storage-oriented persistence path. The protocol is grounded
  414  in two invariants: (i) log records commit in order, and (ii) no committed entries are lost, even in the presence of failures within our
  415  failure model. We formalize these safety properties and an abstract
  416  model of the protocol in TLA+ and model-check them (see artifact
  417  URL). The remainder of this section gives a high-level overview of
  418  the protocol design.
  419  Failure model. BtrLog adopts the standard non-Byzantine crashstop failure model in asynchronous networks [22]. Accordingly,
  420  our protocol tolerates message loss, reordering, duplication, delay,
  421  network partitions, log node failures, and client failures. In the
  422  following, we discuss client and log node failures separately. Client
  423  failures coincide with database failover. Log node failures must not
  424  compromise the availability or durability of committed data in the
  425  log tail. Because cloud object storage provides high durability and
  426  availability (e.g., S3 advertises 99.99% availability and 11 nines of

  447  Protocol overview. BtrLog targets the same failure modes as
  448  Paxos-like protocols, but shifts responsibilities to reduce latency
  449  while preserving fault tolerance. It assigns the leader/proposer role
  450  to the single writer (the client) to minimize commit latency, and
  451  leverages WAL monotonicity to avoid per-record ordering at log
  452  nodes. BtrLog integrates object storage to simplify node recovery
  453  and avoid re-replication across log nodes. Cloud object storage also
  454  serves as a highly available metadata store with atomic compareand-swap (CAS) semantics for leader election (client failover). In the
  455  following, we discuss how BtrLog uses these concepts to achieve
  456  fault tolerance. We assume a single-AZ deployment for simplicity,
  457  but our explanations generalize to BtrLog's multi-AZ deployment.
  458  We first describe the failure-free operations that enable low-latency
  459  appends and consistent reads, then we discuss failure scenarios.

  460  4.1 Failure-Free Operation
  461  Log creation. Before appending, clients have to create a new log
  462  by initializing its metadata (such as the segment size (bSize)) in the
  463  metadata store, as shown in Figure 3 1 . To open a log for writing,
  464  the client acquires a write token (wtoken) from the metadata store
  465  (c.f. Section 4.2) and sends an open request to all log nodes to install
  466  that token 2 . Before issuing append requests, the client waits for
  467  acknowledgments from a quorum of log nodes.
  468  Append operations. The BtrLog client sends append requests to
  469  all log nodes and commits after replies from a write quorum 3 . In
  470  addition to the payload, each append request includes three fields:
  471  (1) the record's log sequence number (nLSN), (2) the last committed
  472  LSN (cLSN, a commit watermark for readers), and (3) the record's
  473  byte offset within the current segment, computed as the prefix sum
  474  of payload sizes of preceding records in the segment. The prefix
  475  sum allows log nodes to place each record at a deterministic offset
  476  within a segment, enabling optimized flushing to object storage.
  477  Idempotent segment flushes. On the failure-free fast path, log
  478  nodes flush full segments to object storage asynchronously 4 . If
=== PAGE 6 ===

  479  all nodes wrote the same segment, this would incur 3× the PUT
  480  cost in a 3-node deployment. To avoid redundant PUTs, BtrLog
  481  uses the prefix sum of record sizes to construct byte-by-byte identical segments across all nodes. As a result, each node derives the
  482  same deterministic object name for the segment, making the flush
  483  idempotent. Nodes create the object using a conditional PUT (with
  484  If-None-Match in S3), so at most one concurrent uploader succeeds.
  485  To optimize costs, a node checks whether the object already exists
  486  before issuing a PUT and skips the write if it does. Since flushes
  487  are performed asynchronously, BtrLog can use expensive cryptographic hashing to avoid accidental hash collisions. In the rare
  488  case of packet loss or writer fencing, hashes may differ; BtrLog
  489  then tolerates duplicate flushes to reduce coordination overhead
  490  and performs data de-duplication during read operations.
  491  Read guarantees. The read protocol guarantees that all committed
  492  data is readable. Internally, BtrLog distinguishes hot reads, served
  493  by log nodes, from cold reads, served by object storage. The client
  494  handles both types of reads transparently to the DBMS.
  495  Hot data reads. Hot data residing on log nodes is typically read
  496  either for transaction rollback (where records are read to undo
  497  a transaction), for log shipping, or for read-replication, as in Microsoft Socrates [6], for example. Because the write path tolerates
  498  message loss, committed entries may be absent on some log nodes.
  499  Similarly, the committed LSN watermark (cLSN) may be stale on
  500  nodes that have not yet received the latest appends. Hot data reads
  501  are therefore performed as quorum reads, which enable clients to
  502  tolerate gaps on individual nodes and observe up-to-date committed
  503  LSN watermarks. To optimize bandwidth utilization, readers may
  504  optimistically decide to read only from a single node and switch to
  505  quorum reads when encountering gaps or detecting a stale cLSN
  506  on that node. If the requested LSN range has already been flushed,
  507  log nodes redirect the request to object storage.
  508  Cold data reads. BtrLog clients leverage object storage for highthroughput reads of cold data, as required for database recovery.
  509  After a crash, the DBMS replays log segments directly from object
  510  storage, reducing load on log nodes and allowing them to prioritize
  511  low-latency tail operations. To enable clients to build an index via
  512  LIST operations and use it to retrieve ranges, log nodes encode the
  513  log ID, epoch, and LSN range in addition to the hash of the data
  514  in the object key. The index can be incrementally maintained on
  515  clients using metadata from log nodes (e.g., the last flushed LSN).
  516  Deferred eviction for low-latency reads. The core protocol guarantees that no committed data is lost, but does not by itself guarantee low read latency for all access patterns. For example, data
  517  requested for log shipping or transaction rollback may have already
  518  been evicted to object storage. In practice, object store eviction can
  519  be controlled without modifying the core protocol using the LSN
  520  window mechanism, which is described in Section 5.

  525  concurrent append operations can create divergent tails across log
  526  nodes and conflicting persisted segments in object storage.

  562  committed data. Figure 4 highlights a subtlety introduced by object

  566  avoids putting object storage reads on the critical path.
  567  Finding the log tail. Fortunately, failover does not require using
  568  object storage. To locate the tail of the log without losing committed
  569  data, the new writer determines the largest contiguous recoverable
  570  LSN prefix supported by a read quorum of log nodes. To accelerate
  571  this step, log nodes piggyback their last committed LSN watermark
  572  when acknowledging the installation of the client's write token.
  573  The client then starts reading log records sequentially 3 , starting
  574  from the highest watermark it observed (cLSN = 2 in the example).
  575  Determining committed data. The retrieved log record's LSN
  576  might be below the last committed watermark observed by a node,
  577  and only one copy of the record might exist. A stricter setting that
  578  requires the writer to observe a quorum of copies might cause data

  579  loss, as illustrated in Figure 4. In the example, C2 observes only
  580  one copy of LSN 3 even though the previous writer replicated it to
  581  2/3 nodes and reported success to the application (cLSN = 3 on C1).
  582  Such cases occur because quorum replication can introduce gaps,
  583  e.g., due to message loss, and the last committed watermark can
  584  lag, especially when multiple appends are in flight. To avoid data
  585  loss, new writers are conservative when inferring the log tail: they
  586  include every consecutive LSN present on at least one node in the
  587  quorum. Only LSNs that a quorum of log nodes confirms as absent
  588  could not have been committed. In the example, although LSN 4 is

  590  because a read quorum confirms it absent.
  591  Log repair and appending. Under-replicated records (e.g., LSNs
  592  2 and 3 in Figure 4) are more susceptible to data loss during network partitions. For example, the only accessible copy of LSN 2 is
  593  lost when node L3 fails. To improve durability of under-replicated
  594  records, the new client re-replicates such records to all nodes using
  595  the new write token 4 . These repair writes may fail if the new
  596  client is also fenced, in which case it stops the failover process and
  597  informs the application to handle retries. Writer fencing can happen
  598  at any stage, but the protocol guarantees that concurrent repairs
  599  will recover the same or a higher log tail. Once fencing and repair
  600  are complete, the new client continues appending to the same log.
  601  Reconstructing the client's log state. As described earlier, the
  602  failover protocol determines all required metadata for the new
  603  writer's state, including the last committed LSN and the next LSN
  604  (nLSN). During tail recovery, the writer also retrieves each record's
  605  byte offset from log nodes. This information is used to reconstruct
  606  the segment prefix sum for idempotent object storage flushes.

  607  4.3 Node Failures
  608  Detecting node failures. Although BtrLog uses a client-driven
  609  replication protocol, it does not depend on clients to detect or handle
  610  node failures. If failure detection were delegated to clients, node
  611  outages could go unnoticed when a client idles or crashes, leaving
  612  the tail unreplicated and increasing the risk of data loss. Instead,
  613  BtrLog detects node failures via peer-to-peer heartbeats between
  614  log nodes. If a node misses heartbeats from a peer for a configurable
  615  interval, it marks that peer as failed.
  616  Handling node failures. Traditional protocols, like VSR [66],
  617  Raft [67], Corfu [24], or Scalog [27], use re-replication from surviving nodes to recover and rebuild failed nodes. Healthy nodes
  618  serve read requests to recovering nodes, increasing load. To avoid
  619  this overhead, BtrLog flushes a snapshot of the log segments to
  620  object storage rather than re-replicating the data to other nodes.
  621  The snapshot flush persists all LSNs up to the point at which the
  622  failure was detected. Entries committed after detection are still
  623  replicated to a quorum by design. Besides reducing load on healthy
  624  nodes, this strategy also enables new or recovering nodes to accept
  625  new writes immediately after receiving the current write token.
  626  Cost-efficient failure handling. Flushing log segment snapshots
  627  to object storage on every node failure might, however, increase
  628  costs due to the number of PUT requests. To reduce the flush costs,
  629  BtrLog introduces two optimizations: First, log nodes trigger a
  630  flush only when they detect 𝑁 − 𝑄 node failures. For example, in
  631  𝑤
  632  a cluster with 3 nodes and 𝑄 = 2, a single failure would already
  633  𝑤

  634  trigger a flush. In a cluster of 6 nodes and 𝑄 = 4, snapshot flushes
  635  𝑤
  636  are only triggered after two failures. Second, we deterministically
  637  assign a per-log flush leader: the leader flushes immediately, while
  638  other nodes first check whether the object already exists before
  639  writing. This optimization avoids unnecessary flushes.
  640  Node replacement and reconfiguration. BtrLog does not automatically redeploy failed nodes and assumes that a higher-level
  641  monitoring component handles such logic. Currently, faulty nodes
  642  can be replaced by removing a node and replacing it with a new
  643  node, reusing the same DNS name or IP address. More automated
  644  node replacement strategies and cluster resizing through reconfiguration are interesting avenues of future work.

  645  4.4 Unreliable Networks
  646  Impact of network issues. BtrLog assumes unreliable networks
  647  where append requests may get reordered or dropped entirely. Network issues can introduce gaps in node-local segments and delay
  648  the propagation of the committed watermark from the client to
  649  the log nodes. Nodes may also flush incomplete or overlapping
  650  segments to object storage, potentially leading to uncommitted
  651  or duplicated records stored there. For instance, a node may flush
  652  while client failover is in progress. Figure 4 illustrates how this failure case can cause data to appear on object storage even without
  653  being replicated and committed by quorum.
  654  Handling uncommitted data. To keep the write path fast, BtrLog
  655  postpones handling such cases to the read path. A key invariant
  656  for the read path is that data in object storage is only durable, not
  657  necessarily committed. Readers identify committed data through
  658  the last committed watermark (cLSN) that the client propagates
  659  to log nodes, which in turn include it as object metadata on each
  660  flush. For example, when clients retrieve data with the read API,
  661  nodes return both the requested data and the committed LSN they
  662  observed. This mechanism enables readers to distinguish committed
  663  data from merely durable data. Similarly, when retrieving data from
  664  object storage, clients evaluate the committed watermark in the
  665  object's metadata to filter out uncommitted data if required.
  666  Handling overlapping data. Due to quorum replication, log segments may have gaps and overlapping ranges. For instance, some
  667  nodes might observe LSN1 and LSN3, while others receive LSN2 and
  668  LSN4. When such overlapping log segments are flushed to object
  669  storage, e.g., due to a node failure, clients may observe overlapping
  670  copies of those segments. The BtrLog client transparently merges
  671  log segments while reading from object storage.
  672  Handling duplicate data. A more subtle issue can occur during
  673  client failover. As Figure 4 illustrates, pending requests from an
  674  old writer (client C1) can fill up log segments and trigger a flush to
  675  object storage. When a new writer (client C2) takes over the log,
  676  it might append new data with the same LSN, for instance, LSN4
  677  in Figure 4. Once the new log segment is flushed to object storage,
  678  readers would observe multiple different copies of LSN4. To resolve
  679  such conflicts in object storage, BtrLog utilizes the write token
  680  as an epoch. Each flushed object encodes the epoch in its key and
  681  includes it in its metadata. Similar to the last committed watermark,
  682  BtrLog clients use this information to ignore outdated data from
  683  prior epochs while streaming from object storage.

  703  5 ENGINEERING BTRLOG FOR LOW LATENCY
  704  Implementation overview. Achieving high throughput and low
  705  latency requires efficient protocols and an optimized implementation that can effectively utilize modern networks, NVMe SSDs,
  706  and multi-core CPUs [43]. Our prototype implements the latencycritical, failure-free append path; failure cases are modeled in TLA+.
  707  Lower latency bound. Microbenchmarks using sockperf [59] and
  708  fio [9] in AWS show that a cluster of c6id.metal instances can achieve
  709  approximately 40 µs network round-trip and 30 µs SSD write latency
  710  without load in a partitioned placement group. Our implementation
  711  thus targets 70 µs latency without load. Achieving this requires
  712  careful optimization of cache misses, allocations, and system calls:
  713  For example, system calls and large allocations can take hundreds
  714  of nanoseconds or even microseconds, potentially deteriorating
  715  response latency by several percent. Thus, our technology stack
  716  needs to allow for fine-grained control over such operations.
  717  Technology stack: Rust, io_uring, UDP. BtrLog is implemented
  718  in Rust. Since no tested off-the-shelf asynchronous Rust runtime
  719  offered consistently low latency and observability, we implemented
  720  our own. Our custom asynchronous runtime is built on io_uring [10],
  721  which allows batching system calls for common operations such as
  722  send, recv, and write [44]. Finally, since the quorum-based BtrLog
  723  protocol obviates the need for many of TCP's guarantees, we use
  724  UDP by default, avoiding stream and connection overhead.
  725  Multi-Core architecture. BtrLog is designed as a multi-tenant
  726  cloud service, so it expects to manage many independent open
  727  log streams simultaneously. Conversely, each log requires sequential semantics internally, and the most common append operation
  728  needs few CPU cycles: As Figure 5 illustrates, each thread 1 checks
  729  the message and copies it to the in-memory log segment if valid,
  730  2 asynchronously writes it to the local SSD, ensuring fsync semantics, 3 replies to the client once data is durable, and then
  731  asynchronously flushes full segments to S3 if necessary. This model
  732  naturally yields an architecture where each log is owned by a single
  733  thread that sequentially processes requests for that log.
  734  Per-Thread runtime. I/O dominates the end-to-end latency of
  735  requests, so I/O wait times should be utilized to process other requests. One could achieve this by using synchronous I/O requests

  736  and letting the OS schedule other threads. However, the resulting
  737  thread-to-core oversubscription and excessive OS scheduling can
  738  lead to latency spikes. BtrLog thus spawns one thread per CPU
  739  core and uses cooperative scheduling within a custom asynchronous Rust runtime to interleave I/O and CPU work on each thread.
  740  Symmetric networking. Many systems use dedicated networking
  741  threads to simplify the architecture and guarantee fast packet acceptance. However, this asymmetric approach requires cross-thread
  742  synchronization for every packet and is detrimental on small nodes
  743  with few CPUs, since one CPU thread is designated to networking
  744  only. In BtrLog, every thread accepts network requests on its own
  745  port using the io_uring-based runtime and processes them directly.
  746  Internal load balancing. The symmetric networking approach
  747  has a significant drawback: If clients send requests directly to individual threads on BtrLog nodes, the node cannot balance log
  748  segments across threads. Load balancing is important since we expect multi-tenant workloads to serve tenants with both very high
  749  and very low append frequency. Having multiple high-frequency
  750  logs handled by the same thread would negatively impact peak
  751  throughput. To enable load balancing while still allowing threads
  752  to respond to clients directly and reduce cross-thread synchronization, our network protocol includes a reply_to field that specifies
  753  a port number. Clients can use any previously used port, including
  754  a well-known port for initial requests, and the BtrLog node may
  755  internally forward the message to a different thread, handing over
  756  the connection. The receiving thread responds to the client directly,
  757  setting its own port in the reply_to field, which the client uses for
  758  future requests – until the log moves to a different thread again.
  759  Figure 5 illustrates the resulting architecture.
  760  S3 integration. BtrLog uses AWS's Rust S3 SDK to flush full log
  761  segments to S3. As Section 4 describes, BtrLog reduces network
  762  utilization and costs when flushing to S3: Log segments flushed to
  763  S3 by some node will not be flushed again by another. The Rust S3
  764  SDK integrates with Rust's asynchronous ecosystem but exhibits
  765  long-running blocking operations (single-digit milliseconds) that deteriorate latency when run on regular log node worker threads. The
  766  implementation thus executes S3 operations on dedicated threads.
  767  Concurrent appends. The BtrLog protocol permits clients to
  768  issue a bounded number of appends concurrently. We implement
  769  this via an LSN window 𝑊 respected by both the client library and
  770  the log nodes: a client does not submit LSN 𝑋 until a write quorum
  771  has acknowledged LSN 𝑋 −𝑊 . Conversely, log nodes delay flushing
  772  segments overlapping with the LSN window to S3, ensuring that
  773  the corresponding records remain accessible in memory. Beyond
  774  allowing pipelining, the LSN window also serves as a retention
  775  mechanism for tail-following readers such as database secondaries,
  776  as discussed in Section 4.1. A larger window accommodates slower
  777  readers but entails higher memory usage per active log stream.

  821  client node to achieve IOPS comparable with the BtrLog cluster.
  822  This volume is used as a block device, without a file system, similar
  823  to how BtrLog log nodes write to their local SSD.

  824  6.1 Append Latency and Throughput
  825  Open-loop latency under load. Response latency depends on
  826  both system configuration and load. For example, systems may
  827  batch disk writes from multiple requests to improve peak throughput at the cost of higher latency. Therefore, we vary the system load
  828  (appends per second), and record the end-to-end latency of each
  829  append. For comparability, we configure all systems to achieve the
  830  best possible latency by deactivating write batching. Our open-loop
  831  benchmark schedules requests with exponentially distributed interarrival times per log stream, i.e., as a Poisson point process. The
  832  client node adds more independent log streams over time, increasing system load and stress-testing many concurrent log streams.

  833  Latency with increasing load. Figure 6 shows the median and
  834  99th-percentile response latency for BookKeeper, EBS io2, and Btr-
  835  Log with 128-byte appends, which we choose based on observed
  836  YCSB, TPC-C, and pgbench LSN write sizes. Each point corresponds
  837  to a 500 ms interval over which throughput and latency percentiles
  838  are measured. BookKeeper does not scale beyond 240,000 appends
  839  per second in either configuration ( , ), and its throughput and
  840  latency fluctuate strongly under load, producing the chaotic pattern
  841  in Figure 6. The default BookKeeper configuration is not visible
  842  in the figure because its latency never falls below 2 ms. EBS io2
  843  ( ) shows steadily increasing write latency as load rises and consistently exhibits 4–5× higher median latency than the BtrLog
  844  prototype. At approximately 1 M appends/s, which is the IOPS limit
  845  of the instance-local SSD, both EBS and BtrLog latency deteriorate.
  846  Additional functionality such as authentication and encryption
  847  can be comfortably supported by BtrLog's remaining CPU cycles;
  848  stronger hardware-based protection using enclaves [32, 57, 58] is
  849  also an interesting avenue for future work.
  850  Best-case latency. Let us now discuss interesting latency and
  851  system load results for each system using the data points shown in
  852  Figure 6. Across a large set of BookKeeper configurations, the best
  853  median latency we observed was 262 µs at 6,800 appends per second;
  854  latency deteriorates quickly as load increases. The best median
  855  latency on EBS was 318 µs, which increased steadily with higher
  856  load. BtrLog's best median latency is 70 µs (79 µs p99 latency) at a
  857  load of 35,500 appends per second. At half of the maximum system
  858  load, approximately 500 k appends per second, BtrLog achieves a
  859  median latency of 111 µs. This headroom would also allow adding
  860  a BtrLog gateway that exposes a simple authenticated HTTP or
  861  gRPC API. Even with an additional 40 µs of latency, such a design
  862  would remain substantially faster than EBS and BookKeeper.
  863  Full system load. At the maximum load of 1 M appends/s (128byte), EBS reaches 503 µs median latency and 651 µs p99 latency.
  864  Once the provisioned-IOPS volume is saturated, EBS latency increases beyond the range shown in Figure 6. BtrLog reaches 188 µs
  865  median latency at full load, limited by the 1.1 M IOPS of the underlying SSDs. To enable overload detection and to bound the latency
  866  of admitted requests, BtrLog limits its internal queue lengths and
  867  drops excess requests once the system is saturated [42]. As a result,
  868  it does not exhibit the typical "hockey stick" latency curve near full
  869  load. At peak throughput, BtrLog serves 2,186 concurrently active
  870  logs in this experiment, and log nodes use 71 GiB of main memory.
  871  While the maximum append rate is bounded by SSD IOPS, the number of logs stored is bounded by main memory because each log
  872  consumes 32 MiB on average. A production implementation should
  873  therefore flush segments of logs with very low append frequency
  874  to SSD or S3.
  875  Impact of SSD latency. Applications with weaker durability requirements may run BtrLog with SSD writes disabled on log nodes:
  876  Each log node appends to log segments in memory and flushes them
  877  to S3 when full, but does not write its own WAL to SSD. This setting
  878  improves latency, since SSD write latency is similar to the network
  879  round-trip time in a single availability zone (35 µs vs 40 µs). We find
  880  that disabling SSDs reduces median latency by approximately 50%
  881  and improves tail latency across most throughput settings.

 1006  6.4 End-to-End Database Performance
 1007  Integration in LeanStore. Experiments so far have used a custom
 1008  open-loop benchmarking client designed to measure response latency as accurately as possible under different load settings. We now
 1009  turn towards evaluating the performance of these systems in a transactional database, LeanStore [52]. LeanStore's autonomous commit
 1010  protocol [64] uses multiple log streams (one per worker thread)
 1011  that are flushed independently. This design was conceived for local
 1012  SSDs, which require many parallel writes to saturate bandwidth,
 1013  but it also fits the BookKeeper and BtrLog APIs, since their multitenant architecture supports multiple independent log streams. We
 1014  modify LeanStore by swapping its WAL implementation with different backends: Custom-built backends for BookKeeper and BtrLog,
 1015  and the default block-device backend for EBS.
 1016  Transaction Throughput. Figure 9 shows the measured YCSB-A
 1017  (50% reads, 50% writes) throughput using different WAL backends in
 1018  LeanStore. LeanStore using the BtrLog WAL backend achieves 2×
 1019  higher throughput than LeanStore using the BookKeeper backend,
 1020  3× higher throughput than EBS gp3, and 1.25× higher throughput
 1021  than EBS io2. These results show that systems previously using
 1022  EBS io2 for their WAL can replace EBS with a non-provisioned,
 1023  multi-tenant service while simultaneously increasing transaction
 1024  throughput using a simple append interface.

 1084  7 RELATED WORK
 1085  In addition to prior discussions, we review related work on cloudnative databases, shared-log designs, and cloud storage backends.
 1086  Disaggregated and cloud databases. Decoupling and optimizing
 1087  logging functionality is a common pattern in modern cloud database
 1088  systems. Amazon Aurora [76] uses a log-centric design with a
 1089  highly coupled log and storage component to reduce network traffic
 1090  and improve fault tolerance. Microsoft Socrates [6] implements a
 1091  dedicated XLOG service with quorum-based commit, and Huawei
 1092  TaurusDB [25] uses distinct log nodes (PLog) to reduce commit
 1093  latency. OceanBase PALF [39] and FoundationDB [83] similarly
 1094  utilize a dedicated log component in their design. Neon separates
 1095  PostgreSQL compute from a replicated WAL service ("safekeepers")
 1096  that provides durable WAL ingestion and supports failover [63].
 1097  Many of these systems, e.g., Aurora, Socrates, OceanBase, and Neon,
 1098  also integrate object storage for low-cost storage. Although these
 1099  systems highlight the need for a specialized logging component,
 1100  their components are tightly coupled with the database engine and
 1101  are not described sufficiently in the literature. In contrast, BtrLog
 1102  aims to provide a reusable write-ahead logging system that can be
 1103  integrated with database engines, supporting the development of
 1104  modular and composable cloud database architectures [54, 79].
 1105  Shared logs and distributed log systems. Besides industrial systems, log abstractions have also been studied in academic research.
 1106  Hyder proposed using a single totally ordered log on shared flash as
 1107  the backend for OLTP [16], motivating systems such as Corfu [13].
 1108  However, shared-log systems including Corfu, Delos, and Scalog
 1109  emphasize multi-writer semantics and throughput rather than low
 1110  latency [11, 13, 27]. Milliscale [82] recently proposed using S3 Express for OLTP to achieve scalable multi-millisecond latency, while
 1111  BtrLog targets scalable multi-microsecond latency. LazyLog [56]
 1112  and SpecLog [17] explore lazy or speculative binding of records to
 1113  log positions to reduce append latency, and FuzzyLog [55] relaxes
 1114  ordering to partial orders to increase concurrency. These works,
 1115  however, introduce new append semantics in which LSNs are unknown at commit time, making them incompatible with common
 1116  recovery protocols such as ARIES.
 1117  Log-centric streaming systems. There has also been work on
 1118  distributed log systems for streaming. LogDevice is a deprecated
 1119  distributed log system developed by Facebook that was designed to
 1120  support generic record-oriented and append-only use cases such
 1121  as write-ahead logging for durability and stream processing [33].
 1122  Kafka [48] popularized the replicated commit-log model for highthroughput streaming and introduced tiered storage [29] to archive
 1123  old log segments to object storage. Streaming-oriented systems
 1124  such as Apache Pulsar [7] and Pravega [75], built on top of Apache
 1125  BookKeeper [46] as a backend for durability, also provide data
 1126  offloading to object storage. BtrLog complements these works by
 1127  optimizing for databases instead of streaming use cases: it targets
 1128  the single-writer, low-latency append pattern of database WAL and
 1129  leverages ARIES-style semantics to minimize commit overhead,
 1130  while still supporting asynchronous archival to object storage. Still,
 1131  the prevalence of the log abstraction in other systems motivates us
 1132  to explore using BtrLog for other latency-sensitive use cases.
 1133  Low-latency durable commits. Related work has studied how fast
 1134  networks and memory can reduce commit latency. FaRM [28] and

 1135  RAMCloud [68] replicate logs to remote DRAM to make commits
 1136  durable with microsecond-scale overhead. QueryFresh [77] uses an
 1137  RDMA-accessible NVRAM log as primary storage to enable fresh
 1138  reads on standbys. In contrast to these works, BtrLog aims to
 1139  achieve low-latency durability on commodity cloud infrastructure.
 1140  Using cloud storage for databases. Cloud storage characteristics
 1141  shape database design beyond WAL. Durner et al. study how to
 1142  use object storage for analytics despite higher latency and different access patterns [30]. Other benchmarking efforts characterize
 1143  cloud storage services and database I/O behavior in cloud-native
 1144  systems [81]. Early work evaluated alternative database architectures on cloud primitives such as EC2/EBS/S3 and quantified their
 1145  performance implications [47]. More recent studies characterize
 1146  cloud database system architecture tradeoffs [40, 84] and the implications of object vs. block storage latency/variance [73]. Instead of
 1147  adapting database systems to different storage backends, BtrLog
 1148  provides a specialized WAL storage backend that requires minimal
 1149  database adaptation and transparently tiers storage for cold data.

 1150  8 SUMMARY & F UTURE WORK
 1151  Summary. We present BtrLog, a reusable single-writer logging
 1152  service purpose-built for cloud-native database systems. It combines low-latency durable appends with low-cost, highly durable
 1153  archival on cloud object storage. Our evaluation shows that Btr-
 1154  Log improves latency by up to 4× relative to the commonly used
 1155  EBS io2, translating to higher end-to-end transaction throughput in
 1156  OLTP systems. Unlike EBS, BtrLog does not require provisioned
 1157  IOPS or capacity when run as a multi-tenant service.
 1158  Beyond database systems. Logging is a primitive with a multitude
 1159  of applications, and although BtrLog is designed as a WAL backend
 1160  for database systems, we believe its low latency and cost can also
 1161  be advantageous in other use cases. Like BookKeeper, BtrLog can
 1162  be used as a storage backend for streaming systems such as Apache
 1163  Pulsar. Using an additional ordering layer, it can also support multiwriter semantics, similar to Corfu and Scalog.
 1164  Towards extensibility. BtrLog provides a reusable interface and
 1165  is not coupled to a specific database engine. One can conceive of
 1166  further BtrLog extension points in an open ecosystem. For example, custom log segment filtering and transformation functions on
 1167  log nodes enable writing to S3 in application-specific formats [35],
 1168  or verification metadata [31] for long-term storage. This can be
 1169  achieved securely using WebAssembly functions, which have recently been used for future-proof storage formats [34, 80]. Custom
 1170  archival backends, such as a page materialization service, enable
 1171  optimizations for cloud-native OLTP systems, such as Socrates [6].
