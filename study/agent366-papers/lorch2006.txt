abstract: >-
  Many stateful services use the replicated state machine approach for high availability. In this approach, a service runs on multiple machines to survive machine failures. This paper describes SMART, a new technique for changing the set of machines where such a service runs, i.e., migrating the service. SMART improves upon existing techniques in three important ways. First, SMART allows migrations that replace non-failed machines. Thus, SMART enables load balancing and lets an automated system replace failed machines. Such autonomic migration is an important step toward full autonomic operation, in which administrators play a minor role and need not be available twenty-four hours a day, seven days a week. Second, SMART can pipeline concurrent requests, a useful performance optimization. Third, prior published migration techniques are described in insufficient detail to admit implementation, whereas our description of SMART is complete. In addition to describing SMART, we also demonstrate its practicality by implementing it, evaluating our implementation's performance, and using it to build a consistent, replicated, migratable file system. Our experiments demonstrate the performance advantage of pipelining concurrent requests, and show that migration has only a minor and temporary effect on performance.

   49  It is easy to achieve consistency in a replicated service

   51  services, such as file systems, databases, or market trading
   52  systems. A stateful service must replicate its state so that
   53  clients never see inconsistencies, even when failures occur.
   54  The state of the art for building consistent, replicated

   59  stay synchronized. System designers are increasingly using

   65  deal with Byzantine server failures, i.e., failures that cause

   76  been published, making it difficult for others to duplicate
   77  their designs. We are only aware of one publication de-

  127  2. BACKGROUND: PAXOS
  128  This section provides enough detail about Paxos and the
  129  replicated state machine approach to understand SMART.
  130  Other sources contain complete details [13, 14, 22].

  131  2.1 Assumptions
  132  First, we describe the assumptions that must hold for the
  133  replicated state machine approach to be applicable. Except
  134  where noted, we make the same assumptions for SMART.
  135  We assume the service runs only on fail-stop machines,
  136  i.e., machines that fail only by stopping. In §8, we discuss
  137  how SMART could be extended to deal with Byzantine failures. Note that if a machine crashes and eventually recovers,
  138  this is temporary unavailability, not a failure.
  139  Paxos assumes that fewer than half the machines will fail.
  140  In other words, there is always some future time when a
  141  quorum of replicas will be alive, where a quorum is a simple
  142  majority. SMART weakens this assumption in that once a
  143  new configuration is established, machines in older configurations can fail. After all, one purpose of service migration is
  144  to eliminate dependence on the current configuration when
  145  one believes it may stop operating properly. Consequently,
  146  SMART only assumes that fewer than half the machines
  147  in a configuration will fail before the next configuration is
  148  established.
  149  The service must be deterministic, i.e., its state changes
  150  and outputs can depend only on its state, its input requests,
  151  and the order of those requests. So, for example, the service cannot use local random number generators or clocks,
  152  and must be single-threaded to avoid non-deterministic effects of thread scheduling. Many techniques and tools simplify building deterministic services [3, 21]. For instance,
  153  there are deterministic techniques to approximate the current time, schedule future events, and choose pseudorandom
  154  numbers. It may also be possible to use a virtual machine
  155  monitor to make arbitrary non-deterministic services run
  156  deterministically [11]. In our discussion of future work in
  157  §8, we sketch how SMART might be modified to allow nondeterministic services.
  158  All we assume about network reliability is that if one alive
  159  process sends a message to another alive process an infinite
  160  number of times, it is eventually received.

  161  2.2 Overview
  162  In the replicated state machine approach [13, 20, 22], a
  163  replica, i.e., a copy of the service, runs on each of several
  164  machines. These replicas run the Paxos protocol to ensure
  165  they all execute the same client requests in the same order.
  166  Then, since the service is deterministic, the replicas change
  167  their states in the same way and produce identical outputs,
  168  e.g., replies to clients. The replicas thereby act like a single
  169  copy of the service that is more resilient to failure than any
  170  individual machine.
  171  Paxos's goal is to ensure all replicas execute the same
  172  requests in the same order. In other words, Paxos must
  173  decide what request to execute first, what request to execute
  174  second, etc. In general, we say that Paxos assigns requests
  175  to slots, where the request it assigns to slot n is the one each
  176  replica will execute as its nth request.
  177  Figure 1 illustrates how Paxos works. One of the replicas is the leader. To submit a request, a client sends it to
  178  this leader. The leader chooses an unused slot and sends
  179  each replica a proposal, which is a tentative suggestion that

  240  3. MIGRATION: CURRENT METHODS
  241  In this section, we discuss current approaches to migrating replicated state machines. §3.1 presents Lamport's idea,
  242  which all current approaches use. §3.2 describes challenges
  243  in implementing this idea, and §3.3 shows how current implementations address them only by significantly restricting
  244  functionality.

  245  3.1 Lamport's idea
  246  Lamport's description of Paxos includes the following idea
  247  about how to perform migration [13]. The service state includes the configuration, and the service migrates when a
  248  request changes this configuration. The migration does not
  249  happen immediately; it takes effect α slots later, where α is
  250  some positive constant. In other words, if n is the slot of
  251  the request that changes the configuration, then this change
  252  takes effect starting with slot n + α.
  253  Using a small α can hurt performance, because the leader
  254  cannot make a proposal for slot n + α until it has executed
  255  slot n. Until it executes slot n, it cannot know whether the
  256  request in that slot excludes the leader's machine from the
  257  configuration as of slot n +α. For instance, if the leader has
  258  only executed slots 1–100 and α is 2, it can only propose slots
  259  101–102 because as far as it knows it is excluded as of slot
  260  103. The bigger α is, the less likely the leader must wait to
  261  propose a request until it has finished executing some other
  262  one, and thus the more undecided proposals the leader can
  263  have outstanding. We call the use of concurrent undecided
  264  proposals pipelining, reflecting how this overlaps the Paxos
  265  network delays for multiple requests.

  266  3.2 Implementation challenges
  267  Storing the configuration in the state is an elegant idea
  268  for migrating replicated state machines. However, it is not
  269  a complete solution to the problem. Implementing the idea
  270  involves addressing several challenges, including the following five.

  271  Unaware-leader challenge: A new leader may not know

  272  the latest configuration.
  273  A new leader must poll the replicas to ensure its assignments do not conflict with previous leaders' assignments.
  274  However, when it is elected, it may have not yet executed a
  275  request that changed the configuration. It may then poll the
  276  wrong set of replicas, not learn about a recent assignment,
  277  and make a proposal that conflicts with that assignment.
  278  For example, suppose that after the service migrates from
  279  {A, B, C} to {A, B, D}, the leader, A, fails. Now, B initiates
  280  a leader change, but B has not yet executed the request that
  281  migrated the service. So, it only polls A, B, and C, and is
  282  content getting responses only from B and C, since they are
  283  a quorum of the configuration it knows. However, A and D
  284  together constitute a quorum of the new configuration, so
  285  they may have assigned some request to a slot. B does not
  286  learn of these assignments, and may propose requests that
  287  conflict with them.

  288  Window-of-vulnerability challenge: Migrations that

  289  remove or replace a machine can create a period of

  290  reduced fault tolerance.
  291  During migration, a service can have reduced fault tolerance. For example, a service replicated on three machines
  292  should be able to survive one machine failure. But, if it migrates from configuration {A, B, C} to {A, B, D}, a failure of
  293  A at the wrong time can halt the service forever. Suppose
  294  the leader, A, crashes while sending DECIDED messages for
  295  the request that changes the configuration. Only C receives
  296  a DECIDED message, and when it executes the request, it
  297  learns that it has been removed from the configuration and
  298  terminates. Now, some replica must become the new leader.
  299  B thinks the only replicas are A, B, and C, so it will never
  300  receive a quorum of poll responses; C has terminated; and D
  301  is not even aware yet that it is part of the configuration. So,
  302  no replica can become leader, and the service halts forever
  303  even though only one machine has failed.
  304  It might seem we could avoid this problem by first migrating to {A, B, C, D} and then migrating to {A, B, D}, but this
  305  also has a window of vulnerability. The leader, A, may crash
  306  while sending DECIDED messages for the request that removes C. Only C receives a DECIDED message, and it executes the request and terminates. Now, some replica must
  307  become the new leader. However, A has failed and C has
  308  self-terminated, so at most two replicas, B and D, can reply
  309  to polls. Since {B, D} is not a quorum of {A, B, C, D}, no
  310  replica can receive a quorum of poll responses and become
  311  leader.

  312  Extended-disconnection challenge: After a long dis-

  313  connection, a client may be unable to find the service.
  314  If a client reconnects after a long disconnection, its idea
  315  of the latest configuration may be out of date due to migrations during the disconnection. Furthermore, all machines in
  316  the configuration it knows of may have permanently failed.
  317  Thus, every machine it contacts will never respond, it will
  318  never learn of a working configuration, and it will not be
  319  able to submit requests.
  320  Consecutive-migration challenge: If request n changes
  321  the configuration, requests n+1 through n+α−1 cannot

  322  change the configuration.
  323  Suppose request n removes machine C from the configuration as of slot n + α, and request n + 1 restores C to the
  324  configuration as of slot n + α + 1. Suppose also that C does
  325  not execute request n because it receives a state transfer of
  326  the checkpoint with index n + 1. In this case, it will never
  327  see the configuration that removes it from the configuration,
  328  and will incorrectly think it is responsible for slot n + α.

  329  Multiple-poll challenge: A new leader may have to poll

  330  several configurations.
  331  It is possible for several undecided proposals to be outstanding at the time of a leader change. Thus, it is possible
  332  that some of these are managed by one configuration and
  333  others are managed by another. The leader change algorithm must be modified so it can poll multiple configurations.

  334  3.3 Current approaches
  335  Current approaches to migration address these challenges
  336  at the cost of restricted functionality. In this section, we discuss a typical example of these approaches, Petal's global
  337  state manager (GSM) [16, 23]. Anecdotal evidence suggests that unpublished commercial systems use similar techniques.
  338  To address the unaware-leader challenge, Petal's GSM
  339  uses the following unpublished technique [23]. After a new
=== PAGE 5 ===

  340  leader collects poll responses from a quorum of replicas, it
  341  fetches the configuration from the responder that executed
  342  the most requests. If this configuration is different than the
  343  leader's, it updates its configuration and restarts the leader
  344  change process. Petal's GSM also enforces two additional
  345  restrictions that, together with the preceding technique, are
  346  sufficient to address the unaware-leader challenge. First,
  347  requests are not pipelined. Second, only two types of migration are allowed: adding one machine, or removing one
  348  machine. This ensures quorums from consecutive configurations always overlap. Since SMART addresses the unawareleader challenge in a different way, it can pipeline requests
  349  for performance and it does not require quorums from consecutive configurations to overlap. In fact, SMART does
  350  not require any overlap at all between consecutive configurations.
  351  To sidestep the window-of-vulnerability challenge, Petal's
  352  GSM removes a machine via migration only if a human
  353  knows it is failed and beyond repair. Thus, although
  354  such a migration reduces the number of tolerable permanent failures by one, this is acceptable because one machine is already known to have permanently failed. For
  355  instance, Petal's GSM will only migrate from {A, B, C, D}
  356  to {A, B, D} when C is permanently failed. It is reasonable to not survive the failure of A during migration,
  357  since the service is not expected to survive two simultaneous machine failures. SMART addresses the window-ofvulnerability challenge differently, by eliminating the window of vulnerability. Thus, unlike Petal's GSM, it can remove a non-failed machine via migration. In particular, it
  358  can migrate replicas from highly loaded machines to lightly
  359  loaded ones, and it can safely rely on an autonomic system
  360  with an imperfect failure detector to decide when to replace
  361  a machine.
  362  Petal's GSM addresses the extended-disconnection challenge similarly to how SMART does. We discuss how
  363  SMART addresses it in §4.5.
  364  Petal's GSM avoids the consecutive-migration and
  365  multiple-poll challenges by requiring α = 1. This precludes
  366  pipelining concurrent requests. SMART uses a different approach, so it can pipeline concurrent requests.

  367  4. SMART
  368  This section describes SMART incrementally, adding details and optimizations as it proceeds. Figure 3, appearing
  369  later, will present an overview of the protocol this section
  370  describes.

  371  4.1 Configuration-specific replicas
  372  A key feature of SMART is configuration-specific replicas:
  373  each replica is associated with one and only one configuration. A migration request creates a new set of replicas, one
  374  for each machine in the new configuration. Figure 2 illustrates an example. When the service migrates from configuration {A, B, C} to {A, B, D}, we do not create a new replica
  375  on D and destroy the one on C, as current approaches do.
  376  Instead, we keep the three configuration-1 replicas running

  410  4.2 Avoiding inter-configuration conflict
  411  Separate configurations use separate instances of Paxos,
  412  so we must ensure they do not assign different requests to
  413  the same slot. We achieve this by making each configuration
  414  responsible for a range of slots, FirstSlot through LastSlot,
  415  with no two ranges overlapping. If the request that creates
  416  a configuration is in slot n, then the new configuration's
  417  FirstSlot is n + α, and the old configuration's LastSlot is
  418  n + α − 1. Each replica only assigns and executes slots in
  419  its range because a leader only proposes slots in its range.
  420  A leader can avoid proposing slots less than FirstSlot because each replica is created knowing its FirstSlot. If it is
  421  in configuration 1, it knows FirstSlot is 1. Otherwise, it
  422  was created due to a JOIN message, and the JOIN message
  423  specified this value.
  424  It is trickier to avoid proposing slots after LastSlot, since
  425  often the leader will not know this value because it has not
  426  yet created a successor configuration. For this case, we use
  427  Lamport's idea: the leader may not make a proposal for slot
  428  n +α until it has executed slot n. Thus, as usual, α controls
  429  the degree to which the leader's proposals can get ahead of
  430  its execution.

  526  4.5 Configuration repository
  527  Next, we discuss how we address the extendeddisconnection challenge. If a machine reconnects after a long
  528  disconnection, it may not know the latest configuration due
  529  to migrations during the disconnection. Furthermore, due to
  530  the weak reliability assumption in §2.1, all servers it knows
  531  of may have permanently failed, so it may never discover
  532  a working configuration. If it is a client, its requests may
  533  never get executed. If it has a defunct replica, that replica
  534  may never learn it is defunct. This is a fundamental problem
  535  for any self-migrating service, and necessitates a configura-
=== PAGE 7 ===

  536  tion repository where the service can store its most recent
  537  configuration information.
  538  We use the repository as follows. Periodically, e.g., every
  539  five minutes, a leader of an established configuration writes
  540  its configuration information to the repository. A process
  541  suspecting a configuration is defunct reads the repository to
  542  try to learn a newer configuration. Also, a leader reads the
  543  repository before writing its own information; if it finds an
  544  earlier configuration, it sends DEFUNCT messages to the
  545  replicas in that configuration.
  546  This protocol ensures correct operation even if the repository is not consistent or durable. Furthermore, the service
  547  can be highly available even if the repository is less available,
  548  because the repository is only necessary on those rare occasions when a machine reconnects after an extremely long
  549  disconnection. It is important that the repository need not
  550  be consistent, durable, and highly available, since otherwise
  551  we could not build a service with those properties unless we
  552  already had a repository service with those properties.
  553  Because there are such weak requirements for the repository, there are several simple ways to build it. For instance,
  554  one can store the configuration information in a DNS entry.

  555  4.6 Ensuring new replicas are created
  556  Next, we discuss how we ensure that every alive machine
  557  in a non-defunct configuration eventually joins that configuration.
  558  We cannot rely on the JOIN messages replicas send when
  559  they create a new configuration. There are a finite number
  560  of these messages, so they may all be lost. We can use
  561  them as an optimization to start the replicas quickly, but
  562  not as a guarantee that every machine that should join the
  563  configuration does so.
  564  If a machine receives a FINISHED message addressed to
  565  a not-yet-created replica on that machine, it creates the addressed replica. Since some replica will send FINISHED
  566  messages repeatedly until it receives a READY message
  567  from a quorum, a quorum of the new configuration will
  568  eventually join. This does not completely solve our problem, since we want every alive machine to eventually join.
  569  So, in addition, if a machine receives a HEARTBEAT or
  570  ELECT message addressed to a not-yet-created replica, it
  571  creates the addressed replica.
  572  A small problem with this is that a machine must join
  573  upon receiving a FINISHED, HEARTBEAT, or ELECT
  574  message, but such a message does not specify the configuration's set of machines or FirstSlot. Thus, a machine does not
  575  join immediately upon receiving such a message. It sends
  576  back a JOIN-REQUEST message, and the recipient replies
  577  with a JOIN message.

  578  4.7 Acquiring starting state
  579  Recall that a new replica generally obtains its starting
  580  state from a finished replica in its predecessor configuration. Instead of repeatedly polling those replicas, waiting
  581  for one to be finished, a new replica just waits to receive a
  582  FINISHED message, then asks the sender for a state copy.
  583  However, there is a wrinkle. Once the predecessor configuration becomes defunct, its replicas may destroy themselves
  584  and become unable to provide a state copy. So, sometimes a
  585  new replica must acquire its starting state from one of its cohorts. A replica can always eventually do this, because if its
  586  predecessor configuration is defunct then its configuration

  587  is established, and eventually an alive cohort can provide a
  588  state copy with index at least FirstSlot − 1.

  589  4.8 Null requests
  590  In Paxos [13], sometimes upon election a new leader must
  591  propose a null request to fill a slot. A null request is simply
  592  an extra request whose execution does nothing, so it is always safe to propose a null request. SMART has the leader
  593  submit null requests in an additional scenario.
  594  When a leader knows its LastSlot, it proposes null requests
  595  for all remaining unproposed slots. This hastens establishment of the successor configuration, reducing the time that
  596  correctness relies on the old configuration's machines and
  597  letting replicas of the old configuration destroy themselves
  598  sooner. It also serves to prevent deadlock, as follows.
  599  Suppose a leader with LastSlot of 100 has made proposals for slots 1–100. Having filled up all its slots, it starts
  600  redirecting clients to the next configuration as discussed in
  601  §4.3. Now, the leader crashes, and the network loses all its
  602  proposal messages for slots 98–100. A new leader is elected,
  603  learns about slots 1–97 in its poll, and waits for a client request to propose for slot 98. However, it waits in vain: all
  604  clients were redirected to the next configuration, so they will
  605  not submit a request to that leader. This next configuration
  606  may assign requests to slots 101 and beyond, but not slots
  607  98–100. No request ever gets assigned to slot 98, so the service stops forever. Our technique avoids this scenario since
  608  the newly elected leader will propose null requests for slots
  609  98–100, allowing the service to make progress.

  610  4.9 Configuration information in state
  611  Often, a replica needs to obtain from its service state information about its successor configuration: whether it has
  612  been created and, if so, its FirstSlot and its set of machines.
  613  A leader needs this to determine for what slots it may propose. A replica needs this to determine whether it is finished
  614  and, if so, where to send FINISHED messages.
  615  The consecutive-migration challenge arises because sometimes this information may not be present, having been
  616  overwritten by a later configuration. However, in SMART,
  617  the service state includes information not just about the
  618  latest configuration, as Lamport recommended, but also
  619  about older, non-defunct configurations. Consequently, the
  620  consecutive-migration challenge does not arise, and SMART
  621  can let any request change the configuration.
  622  The service state may also include information about defunct configurations. However, the service should eventually
  623  discard such information to prevent its state from growing
  624  indefinitely. Since it is deterministic, it can only change its
  625  state while executing requests. So, at the beginning of executing request n, it checks whether n − MaximumLogSize
  626  is the LastSlot of some configuration C. If so, it knows that
  627  C is defunct, and discards information about it. It knows
  628  C is defunct because, as we discussed in §2.3, no leader can
  629  propose request n unless n − MaximumLogSize is a stable
  630  index of its configuration. This means that LastSlot of C is a
  631  stable index of some successor configuration, so C is defunct.

  651  The optimization factors some of the functionality out of

  657  successive configurations will overlap, so several new replicas will be colocated with replicas of the old configuration.
  658  For instance, an autonomic system might replace a failed
  659  machine C in configuration {A, B, C} by reconfiguring to
  660  {A, B, D}, so the new replicas on A and B find themselves
  661  with colocated replicas. Each new replica that is colocated
  662  with a replica from its predecessor configuration defers copying its starting state. It hopes that the colocated replica will
  663  soon finish executing its final slot, thereby putting the EM
  664  in exactly the state the new replica needs and obviating a
  665  copy.
  666  However, its hopes may be dashed, and the colocated
  667  replica may not reach its final state before destroying itself.
  668  Fortunately, even in this case there is opportunity to save
  669  state-copying costs. Although the EM did not execute all
  670  requests from the previous configuration, it likely executed
  671  most of them, so its state is close to the required starting
  672  state. Thus, the replica can substantially reduce copying
  673  time with an incremental state transfer [3].
  674  Some things a replica used to do internally now involve
  675  communication with the EM. For instance, it no longer executes requests. Instead, it tells the EM when requests are
  676  assigned to slots, and the EM executes those requests when
  677  it is ready.
  678  A seemingly problematic aspect of EMs is that a replica
  679  may find its EM state progressing beyond LastSlot. For instance, if replicas in configurations 3 and 4 coexist on a machine, then the replica in configuration 4 may cause the EM
  680  to execute a slot that configuration 4 is responsible for. Or,
  681  the replica in configuration 4 may overwrite the EM state

  682  with a checkpoint copy reflecting slots that configuration 4
  683  is responsible for. However, this does not pose a problem,
  684  since the only reason a replica ever inspects its EM's state
  685  is to obtain information about its successor configuration.
  686  As we discussed in §4.9, executing further requests cannot
  687  change this information due to the way we manage configuration information in the state.

  688  5. CORRECTNESS
  689  In this section, we sketch our arguments about SMART's
  690  correctness. For the full proof, see our technical report [12],
  691  which specifies our system and proves its safety property in
  692  the formal systems-specification language TLA+ [15].
  693  SMART's safety property is that no two replicas ever assign different requests to the same slot.
  694  Basic Paxos uses the following proof. Suppose two leaders assign requests to the same slot. The earlier leader must
  695  have gotten a quorum of replicas to log its corresponding
  696  proposal, and the second leader must have gotten a quorum
  697  of replicas to reply to its poll so it could make any proposal
  698  at all. Quorums overlap, so the second leader must have
  699  heard about the first leader's logged proposal and thus proposed the same request for the slot. So, both leaders assign
  700  the same request to the slot.
  701  However, this proof does not work for SMART, since not
  702  all quorum pairs overlap. For instance, one quorum might
  703  be {A, C} from configuration {A, B, C} and another might
  704  be {B, D} from configuration {A, B, D}.
  705  We start by proving the following lemma: if only one configuration is responsible for a slot, only one request is assigned to that slot. Configuration-specific replicas make this
  706  proof straightforward. A replica only sends Paxos messages
  707  to replicas of the same configuration. Therefore, if only one
  708  configuration is responsible for a slot, the quorum of replicas
  709  that logs a proposal for that slot must come from the same
  710  configuration as any quorum that replies to a poll that enables a future leader to create a new proposal for that slot.
  711  Reasoning as in the basic Paxos proof, the lemma follows.
  712  We now prove that only one request is assigned to each
  713  slot by induction on slot. Only the initial configuration is
  714  responsible for slot 1, so by the lemma, the induction condition holds for slot 1. Now, suppose it holds for slots 1
  715  through n. This implies only one request is assigned to
  716  each of those slots. The state machine is deterministic, so
  717  the outcome of executing requests 1 through n will be the
  718  same everywhere such an outcome is observed. This outcome specifies the configuration responsible for slot n + 1,
  719  and the uniqueness of that configuration means only one request will be assigned to that slot according to the lemma.
  720  This completes the inductive step and thus the proof.
  721  The proof in the companion technical report [12] is formal and far more detailed. One illustration of this is that it
  722  showed us a bug in both the implementation and the protocol specification. Our specification considers volatile state
  723  by admitting a "crash" action that erases certain variables.
  724  We discovered that after a crash, a leader forgot which slots
  725  it had proposed for. If it recovered quickly enough that
  726  none of its cohorts noticed its failure, it could remain leader
  727  throughout its crash and recovery. Then, it could propose
  728  new requests in slots it had already used, possibly leading
  729  to conflicting requests for the same slot. Once we discovered
  730  this bug, it was easy to fix.

  732  To evaluate SMART, we built a prototype implementation
  733  of it and performed experiments to evaluate its performance.

  735  6.1 Implementation
  736  We implemented SMART as a library called LibSMART.
  737  Service implementations can use this library to obtain replication and migratability. LibSMART presents a similar
  738  interface to BFT [3], enabling us to port existing services
  739  written for that interface. LibSMART's implementation of
  740  SMART is complete except for the configuration repository.
  741  To demonstrate SMART's practicality, we used LibS-
  742  MART to build a real service: a consistent, replicated,
  743  migratable file system. We ran thousands of hours of file
  744  system traces on this new file system, and thousands of
  745  runs that verified the correctness of our implementation during disconnections, reboots, and migrations. Furthermore,
  746  building this service was fairly straightforward. We already
  747  had a file system that used BFT for consistency and replication [1], so by porting it to LibSMART we achieved migratability. Note that by doing so we replaced its Byzantine
  748  fault tolerance with mere fail-stop fault tolerance; it is future
  749  work to enable Byzantine fault tolerance in SMART.
  750  The file system uses highly effective techniques to hide
  751  the latency of server operations, so evaluating its performance sheds little light on the performance of LibSMART.
  752  Therefore, in this section, we benchmark LibSMART with
  753  a simple key/value service. This service permits client requests that read, write, and delete string values associated
  754  with integer keys. Each replica of the service caches information in memory for the most recently accessed 1,000 keys.
  755  Thus, it must access the disk when processing a request for
  756  a non-recently accessed key.

  857  6.5 Effect of network latency
  858  Our next experiment measures the effect of network delay
  859  on client latency. A client submits 20,000 consecutive requests and we measure the average latency. We do this four
  860  times, each time simulating a different additional network
  861  delay. The added delays range from 0–30 ms.
  862  Figure 7 shows the results. We see that for every 1 ms
  863  added to network latency, request latency goes up by approximately 4 ms. This is as expected since, as illustrated
  864  in Figure 5, there are four network hops on the critical path
  865  of handling a client request: the client sends the request to
  866  the leader, the leader sends a proposal to the other replicas,
  867  the replicas send the leader a LOGGED message, and the
  868  leader sends the client a reply.

  898  6.7 Disconnection
  899  We next perform a simple experiment to demonstrate resilience to a single failure. A client submits 1,000 requests;
  900  partway through, we disconnect machine C. Figure 8 shows
  901  the results, with the following two things most notable.
  902  First, there is no pause in service operation at the time
  903  of disconnection, since Paxos performs no special processing to exclude a disconnected non-leader machine. Second,
  904  average latency is the same before and after disconnection:
  905  2.6 ms in both cases. The critical path of request handling
  906  involves the time it takes the fastest quorum of replicas to
  907  log the proposal and respond to the leader, so it goes essentially just as quickly with machine C disconnected as with
  908  all machines alive.
  909  In another experiment, we disconnect the leader instead.
  910  The service continues operating correctly, but in this case
  911  the performance effect is far higher: after the disconnection,
  912  the next client request has a latency of 3.1 sec. This large
  913  delay is mostly due to the tunable 3-second timeout before
  914  another replica concludes the leader has failed and initiates
  915  a leader change.

 1010  6.9 Sources of delay following migration
 1011  To understand the source of the latency increases immediately following migration, we conduct an additional experiment. In this experiment, we perform 200 consecutive migrations, alternating between configurations {A, B, C} and
 1012  {A, B, R}. We find that the delays observed by the client
 1013  correspond to certain phases leader machine A goes through
 1014  during migration, shown in Figure 11. Phase 1, taking 3 ms
 1015  on average, is waiting for the migration request to be logged.
 1016  Phase 2, taking 4 ms on average, is executing that request,
 1017  including sending JOIN messages and proposing null requests. Phase 3, taking 12 ms on average, is waiting for
 1018  null requests to be logged and then executing them. Phase
 1019  4, taking 8 ms on average, is waiting for a checkpoint save;
 1020  our implementation always saves a checkpoint upon reaching a configuration's final state, to hasten the establishment
 1021  of the next configuration. Depending on whether any client
 1022  request arrives during phase 1, either one request observes
 1023  the latency of phase 2 and another observes the latency of
 1024  phase 4, or a single request observes the latency of most of
 1025  phases 2–4. The former case happened in our earlier migration experiments, explaining the two slightly elevated latencies immediately following migration. In our 200 migrations,
 1026  the former case happens 83% of the time and when it does,
 1027  the two delayed requests have average latency of 11 ms and

 1048  7. RELATED WORK
 1049  Yin et al. [25] argue for the separation of agreement from
 1050  execution in Byzantine fault-tolerant state machine replication, to reduce the number of execution modules in a static
 1051  configuration and to enable the use of a privacy firewall.
 1052  SMART also separates agreement from execution, but for
 1053  a different purpose, namely to share one execution module
 1054  among replicas of different configurations on the same machine.
 1055  Our use of configuration-specific service replicas is similar
 1056  to the use of configuration-specific object replicas in systems
 1057  such as RAMBO [17]. We are the first to use configurationspecific replicas to migrate replicated state machines, and
 1058  to use shared execution modules to make this approach efficient.
 1059  Researchers have developed several methods for migrating
 1060  replicated services that do not involve migrating replicated
 1061  state machines. In the remainder of this section, we discuss
 1062  these methods and compare them to SMART.
 1063  One method is to use a view-oriented group communication system (GCS) such as ISIS [2], Transis [6], or Horus [8].
 1064  Such a system allows a process to send a message to a group
 1065  of processes, and allows the set of processes in this group,
 1066  called the view, to change. This is a useful building block for
 1067  replicated state machines, since it allows client processes to
 1068  send requests to a changing group of servers. Most GCSes
 1069  also provide virtual synchrony, meaning that processes in
 1070  consecutive views see the same set of messages in the earlier view [4]. This simplifies coordination of replicas when
 1071  views change. The main advantage SMART has over GCSes
 1072  for replicating services is that Paxos deals more efficiently
 1073  with temporarily unavailable machines. A GCS must incur
 1074  the overhead of view change whenever any machine becomes
 1075  temporarily unavailable [10, 17], while Paxos incurs comparable overhead only when the leader becomes temporarily
 1076  unavailable or the configuration changes.
 1077  Another method for building replicated services is to build
 1078  them out of replicated objects, as in RAMBO [17] and Martin et al.'s reconfigurable Byzantine quorum system [19]. In
 1079  such a system, an object is replicated among several servers,
 1080  and the set of servers can change. A client request can either read or write an object. The main disadvantage of
 1081  this approach is that some services cannot be composed out
 1082  of read/write objects. For instance, some services need to
 1083  atomically read and conditionally modify an object, or to
 1084  atomically modify two objects. This is why a file service
 1085  built on a replicated object system, such as Om [26], cannot
 1086  provide namespace operations such as atomically moving a
 1087  file out of one directory and into another.
 1088  Finally, a service can obtain migratability by using a separate configuration service, as done by Boxwood [18], GFS [9],
 1089  and chain replication [24]. In this method, a separate service
 1090  determines the current configuration of the main service.
 1091  This approach is reasonable, but still requires a mechanism
 1092  like SMART to allow the configuration service itself to migrate. For instance, most components in the Boxwood system are migratable, with the notable exception of the master
 1093  configuration service, a limitation acknowledged by its authors [18]. SMART would be an excellent tool for building
 1094  a migratable master configuration service for Boxwood.

 1095  8. FUTURE WORK
 1096  In this section, we discuss two promising avenues of future
 1097  work. One is modifying SMART to allow non-deterministic
 1098  services. The other is modifying it to survive a limited number of Byzantine server failures, i.e., failures that cause behavior other than merely stopping.
 1099  For some services, determinism is impractical, such as a
 1100  multi-threaded service whose behavior is affected by thread
 1101  scheduling. A standard way to deal with non-determinism
 1102  in Paxos is semi-passive replication [5]. In this method, a
 1103  leader does not propose requests. Instead, it tentatively executes requests, recording state changes and buffering outputs. What it proposes are those state changes and outputs.
 1104  When another replica learns a proposal is decided, it merely
 1105  applies the state changes. Thus, only one replica executes
 1106  requests, as is appropriate considering the service is nondeterministic and thus may execute differently on different
 1107  replicas. We believe SMART can be used with semi-passive
 1108  replication, thereby enabling non-deterministic services.
 1109  There are well-known approaches, such as BFT [3], that
 1110  let replicated state machines operate correctly despite limited Byzantine behavior. In principle, SMART could use
 1111  BFT instead of basic Paxos, and thereby also tolerate such
 1112  failures. However, many changes to SMART would be necessary. For instance, we would require a method like Martin
 1113  et al.'s forgetting protocol [19] to ensure that old configurations cannot mislead clients if they become faulty.

 1114  9. CONCLUSIONS
 1115  In this paper, we presented SMART, our technique for
 1116  migrating replicated stateful services. Unlike similar approaches, SMART can overlap processing of multiple requests, allows migrations with no overlap between consecutive configurations, and allows migrations that remove or
 1117  replace a non-failed machine. Thus, it can migrate services
=== PAGE 13 ===

 1118  to balance load, and it can safely rely on autonomic systems
 1119  to decide when to migrate. Also, we are the first to publish
 1120  full details of how our migration technique works.
 1121  A key element of SMART is its use of configurationspecific replicas. We create a new configuration by starting
 1122  a new replica of the service on each machine in the new configuration. These replicas run concurrently with the replicas from the old configuration until the new configuration
 1123  is established. The replicas of each configuration run a perconfiguration instance of Paxos; this simplifies the protocol
 1124  since Paxos never has to run across multiple configurations
 1125  simultaneously.
 1126  When multiple replicas run on the same machine, there is
 1127  unnecessary duplication of service state, which can lead to
 1128  expensive copying of service state across machines and/or
 1129  processes. Thus, we use shared execution modules to let
 1130  replicas on the same machine share service state.
 1131  We evaluated the performance of our technique by running experiments on our implementation of it. We found
 1132  that SMART's ability to overlap processing of multiple requests reduces latency of requests when there are concurrent
 1133  requests. We also found that migration has only a small and
 1134  temporary effect on performance.
 1135  SMART allows a service to migrate and still preserve absolute consistency. Any deterministic algorithm may guide
 1136  this migration, permitting any desired mechanism for balancing load and for recovering from lost fault tolerance due
 1137  to failures. Even if the algorithm sometimes incorrectly decides that a machine has failed and needs replacement, it
 1138  does not risk halting the service forever. Such autonomic
 1139  migration is an important step toward full autonomic operation, in which administrators play a minor role and need
 1140  not be constantly available.
