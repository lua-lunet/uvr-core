abstract: >-
  Consensus is an essential ingredient of a fault-tolerant distributed system systems. When equipped with a consensus algorithm a distributed system can act as a replicated state machine (RSM), duplicating its state across a cluster of redundant components to avoid the failure of any single component leading to a system-wide failure. Paxos and Raft are examples of algorithms for achieving distributed consensus. Practical implementations of this kind of system must support dynamic reconfiguration in order to be able to replace failed components and perform other administrative tasks without downtime. Paxos can achieve high performance by pipelining (starting work on new requests before existing requests have completed) but typically bounds the length of the pipeline to ensure consistency during reconfiguration. Raft also supports pipelining and imposes no such bound on concurrent requests, preserving consistency instead by restricting which reconfigurations may be performed. This article shows how to extend Paxos to support a more general form of reconfiguration which subsumes the original bounded-pipeline approach as well as Raft-like fully-concurrent reconfigurations and more besides.

   25  I. INTRODUCTION
   26  RELIABLE distributed systems must be able to tolerate
   27  a fault in any individual component without suffering
   28  a system-wide failure, and typically achieve this by ensuring
   29  that there is redundancy between the components. A replicated
   30  state machine (RSM) is a style of fault-tolerant distributed
   31  system in which a deterministic state machine is replicated
   32  across a set of distinct nodes [1]. Being deterministic, the
   33  nodes' states remain synchronised if they all start in the same
   34  state and perform the same sequence of transitions.
   35  In order to arrange for each node to perform the same
   36  transitions the system may achieve consensus on (or choose)
   37  a sequence of values which describe the transitions. The
   38  sequence must be consistent across the whole system even in
   39  the presence of failures, and as long as there are not too many
   40  failures it must remain possible to continue to make progress.
   41  This is known as the distributed consensus problem, for which
   42  a number of solutions are known to exist, including Paxos [2]
   43  and Raft [3]. They typically run on a cluster of 2f + 1 nodes,
   44  where f is the number of faulty nodes that should be tolerated,
   45  and consensus is achieved when a nonempty quorum of nodes
   46  (e.g. at least f + 1 of them) agree. The collection of quorums
   47  in use is known as the configuration of the cluster.

   56  It is normally necessary to be able to dynamically reconfigure a cluster by adding or removing nodes while it is
   57  running, in order that parts of the system can be repaired
   58  or replaced without needing to take the whole system offline. It is crucial that all participating nodes agree on the
   59  cluster configuration, and this can be achieved by holding the
   60  configuration within the RSM itself and using the consensus
   61  algorithm to choose special reconfiguration commands when
   62  a configuration change is desired.
   63  In Paxos, each value is chosen using a conceptually-separate
   64  instance of a two-phase consensus protocol known as Synod.
   65  The full Paxos algorithm essentially runs an infinite sequence
   66  of Synod instances in parallel, using uniformity of the instances to do so without requiring infinite time or resources. It
   67  starts by running phase I of all instances at once and then runs
   68  phase II of each instance in turn to yield the desired sequence
   69  of chosen values. It normally continues to run phase II for
   70  extended periods of time, but will return to phase I if certain
   71  nodes become faulty, or if messages between certain pairs of
   72  nodes cease to be delivered reliably for a period, or if the
   73  configuration changes. Raft's pattern of execution is similar.
   74  Both algorithms can achieve high throughput by allowing
   75  for pipelining [4] whereby work may begin on an instance
   76  even before all previous instances have fully completed. It is
   77  a little tricky to ensure that this preserves consistency when
   78  the configuration is held in the RSM itself because a value
   79  may only be proposed once a quorum of nodes are ready for
   80  it, but there may be a configuration change in the pipeline
   81  which would change the quorums so as to make a proposal
   82  invalid. If this case is not handled carefully then it may lead
   83  to inconsistency. Paxos implementations typically solve this
   84  problem by limiting the length of the pipeline to some α > 0
   85  and requiring that a configuration change chosen at instance ⟩
   86  does not take effect until at least instance ⟩ +α, which means
   87  that when a proposal is made there can be no as-yet-undecided
   88  configuration change in the pipeline that could affect it. In
   89  contrast, Raft imposes no limit on the number of concurrentlyrunning instances and instead restricts the reconfigurations
   90  that may occur to only allow ones that cannot result in
   91  inconsistency. An operator may then perform a sequence of
   92  these restricted reconfigurations in order to achieve an arbitrary
   93  reconfiguration.
   94  In Paxos, the choice of the pipeline length parameter α
   95  must be made carefully. If it is too small then the system may
   96  suffer from poor performance due to lack of parallelism, but if
   97  it is too large then configuration changes can be unreasonably
   98  expensive to complete. It is more elegant [5] to limit the
   99  pipeline length only during reconfiguration and to allow the
  100  limit to vary while the system is running, but it would be

  122  II. RELATEDWORK
  123  Lamport's original presentation of Paxos [2] introduced the
  124  bounded-pipeline technique for supporting reconfiguration in
  125  which the pipeline length was defined to be 3. He later clarified
  126  that the value '3' was intended to stand for an arbitrary α > 0
  127  in [7]. Later still Lamport and Massa [8] drew a distinction
  128  between Static Paxos in which the configuration may not
  129  change and Dynamic Paxos which supports reconfiguration
  130  but requires a bounded pipeline. Dynamic Paxos was used as
  131  a basis for Cheap Paxos in which the system automatically
  132  reconfigures itself to achieve higher resilience to failures that
  133  do not occur simultaneously, and which uses a heterogeneous
  134  set of nodes to reduce the costs of operating a cluster.
  135  Malkhi, Lamport and Zhou [9] proposed Stoppable Paxos,
  136  an alternative method for reconfiguring clusters in which an
  137  RSM may be stopped, reconfigured, and then restarted with
  138  the new configuration. Stoppable Paxos improves on Dynamic
  139  Paxos by removing the need for a pipeline limit when the
  140  configuration is static and by allowing a different limit to be
  141  selected for different reconfigurations.
  142  Malkhi, Lamport and Zhou [10] then proposed Vertical
  143  Paxos which keeps the RSM running throughout a reconfiguration, but requires a separate oracle to manage the configuration. The Egalitarian Paxos of Moraru, Andersen and
  144  Kaminsky [11] uses a similar reconfiguration scheme. The
  145  problem with needing an external oracle is that for full
  146  resilience it must be possible to reconfigure the oracle itself,
  147  which requires another oracle and so on ad infinitum.
  148  Chandra, Griesemer and Redstone [12] noted that the details
  149  of reconfiguration are "relatively minor" but "subtle" and do
  150  not give any details on the reconfiguration scheme used in
  151  their Chubby system. It seems likely that they also used the
  152  bounded-pipeline approach. In contrast, Birman, Malkhi and
  153  van Renesse [13] noted that allowing for α > 1 may require
  154  an unacceptably complex implementation, leading many real-

  155  2

  156  world systems to disable pipelining by setting α = 1, or even
  157  to disable reconfiguration entirely.
  158  Bortnikov et al. [14] implemented a reconfigurable RSM
  159  using static RSMs which may pass responsibility to each
  160  other in a manner that is similar to that of Stoppable Paxos.
  161  They improve the performance of their system compared with
  162  Stoppable Paxos by allowing each RSM to speculatively start
  163  executing commands before the transfer of responsibility has
  164  been fully agreed.
  165  Ongaro and Ousterhout [3] developed the Raft protocol
  166  which supports an unbounded pipeline throughout the reconfiguration process without inconsistency by instead limiting
  167  the reconfigurations that can be performed. They performed a
  168  formal proof of the correctness of Raft without reconfiguration,
  169  and an informal argument that consistency is preserved when
  170  a single node is added or removed from the cluster. Raft uses
  171  simple majorities of the set of nodes as its quorums.
  172  Viewstamped Replication and Zab are two other well-known
  173  consensus protocols. Viewstamped Replication supports reconfiguration as described by Liskov and Cowling [15] in a similar
  174  fashion to Vertical Paxos. Reed and Junqueira [16] initially
  175  presented Zab without reconfiguration and this feature was
  176  subsequently added by Shraer, Reed, Malkhi and Junqueira
  177  [17], using a limited-pipeline approach much as in Dynamic
  178  Paxos.
  179  An interesting alternative approach to reconfiguration was
  180  proposed by Jahl and Meling [18] which uses eventual consistency rather than consensus to determine the configuration
  181  of the system, and therefore supports reconfiguration as long
  182  as it is still possible to communicate with a quorum of nodes
  183  even if consensus cannot be achieved due to an inability to
  184  elect a distinguished leader. In such a situation consensusbased approaches such as the one presented here would fail
  185  to make any further progress, whereas one based on eventual
  186  consistency could be reconfigured into one in which a leader
  187  may be elected and thus in which further progress can be
  188  made.

  323  B. Per-phase quorums
  324  The consistency property of the Synod algorithm relies on
  325  the fact that the set of nodes involved in completing phase I
  326  must always intersect the set of nodes involved in completing
  327  phase II so that there is at least one node involved in both
  328  phases. Write Q1 ⌢ Q2 iff every q1 ∈ Q1 and q2 ∈ Q2 have
  329  q1 ∩ q2 6= ∅, and write QI(b) and QII(b) for the sets of phase-I
  330  and phase-II quorums for ballot b respectively.
  331  In the original presentation of the Synod algorithm any
  332  (weighted) majority of the nodes could be used as a quorum,
  333  so that QI(b1) = QII(b2) and hence QI(b1) ⌢ QII(b2) for all
  334  b1 and b2 since all majorities intersect.
  335  Theorem 8 shows that consistency can still be guaranteed
  336  even if sometimes QI(b1) 6= QII(b2), as long as QI(b1) ⌢
  337  QII(b2) when proposed(b1), chosen(b2) and b1 ≻ b2, as
  338  described in invariant S1. This weaker invariant is the key to
  339  allowing more general reconfigurations to take place safely as
  340  described in section IV-A below.

  465  C. Liveness
  466  To be useful, a consensus algorithm must not only guarantee
  467  consistency but also ensure that it cannot "get stuck", i.e. it
  468  is always possible to make progress by eventually choosing
  469  a value for each instance. It is known to be impossible to
  470  guarantee liveness in a deterministic asynchronous system [21]
  471  but as with earlier presentations of Paxos [7] here liveness can
  472  be shown under the assumption that a distinguished node ℓ is
  473  eventually selected as the only one that may emit prepare(b)
  474  messages.
  475  The original liveness proof then proceeded by having ℓ emit
  476  prepare(b) for some b that is chosen to be large enough that a
  477  quorum of nodes may respond with promises. In contrast, here
  478  there is an upper bound on suitable ballots since a proposed
  479  ballot must not belong to an era which is too large, because
  480  if e(b) > e(⟩) then no promise for ballot b at instance ⟩ may
  481  be made. Therefore here ℓ must be able to choose a ballot
  482  that is large enough to be accepted but which still belongs to
  483  the correct era, or, more precisely, for each ballot b, each era
  484  e ≥ e(b) and each node a there must be a ballot b′ ≻ b having
  485  e(b′) = e and owner(b′ ) = a.
  486  This means that ballot numbers cannot be simple integers
  487  because this would imply that there exist eras containing
  488  only finitely many ballots. Instead an implementation could,
  489  for example, let B = N × N × A ordered lexicographically,
  490  where e(⟨e, n, a⟩) , e and owner(⟨e, n, a⟩) , a. This is
  491  the approach used in Egalitarian Paxos [11] in which eras
  492  are known as epochs but this terminology is avoided here
  493  to prevent confusion with the epochs (views, terms, . . . ) of
  494  leader-election protocols (e.g. [22]) which track the current
  495  leader rather than the current configuration.

  901  VI. CONCLUSION
  902  The approach described here improves on Dynamic Paxos
  903  [8] by supporting changing the pipeline length parameter
  904  α and running with an unlimited-length pipeline while a
  905  configuration change is not in progress. In that sense, it can
  906  be compared to that of Stoppable Paxos [9] which allows for
  907  an unlimited number of proposals to run in parallel within
  908  each configuration, but requires a temporary arbitrary limit on
  909  concurrency while a reconfiguration takes place.
  910  In both Dynamic and Stoppable Paxos, if the selected
  911  limit is either too small or too large then it may affect the
  912  system's performance, and the best choice of limit depends
  913  on a prediction of the system's future performance. The
  914  approach described here avoids the need to make any such
  915  prediction or select any such limit and responds to changing
  916  system conditions without needing further tuning. Once a
  917  reconfiguration is chosen, it can complete after a single roundtrip to a quorum of nodes and the system can continue to serve
  918  all clients while this round-trip is in progress, no matter how
  919  long it takes.
  920  This is achieved by using Raft-style reconfigurations [3]
  921  which can be performed with an unlimited pipeline throughout.
  922  Unlike in Raft, here a configuration change only takes effect
  923  once it is chosen, which avoids the need to back-track to
  924  an earlier state if a leader fails during reconfiguration. It
  925  generalises the simple majorities used in Raft to integerweighted majorities which can reduce the costs of dealing with
  926  correlated failures during maintenance.
  927  It achieves equivalent goals to those of Vertical Paxos [10]
  928  except that here there is no requirement for a separate oracle
  929  to manage the configuration of the system.
  930  It is also noted that there is no need for every message to
  931  include the corresponding value, or even a hash of the value,
  932  which may allow for even cheaper implementations of Cheap
  933  Paxos [8] and can simplify the transfer of state [10] required
  934  when new nodes are commissioned.
