   12  that every protocol for this problem has the possibility of nontermination, even with only one faulty

   14  problem.

   41  A well-known form of the problem is the "transaction commit problem," which
   42  arises in distributed database systems [6, 13, 15-17, 21-241 (see also G. LeLann,
   43  private communication, quoted in [ 151). The problem is for all the data manager
   44  processes that have participated in the processing of a particular transaction to
   45  agree on whether to install the transaction's results in the database or to discard
   46  them. The latter action might be necessary, for example, if some data managers

   48  Whatever decision is made, all data managers must make the same decision in
   49  order to preserve the consistency of the database.
   50  Reaching the type of agreement needed for the "commit" problem is straightforward if the participating processes and the network are completely reliable. However, real systems are subject to a number of possible faults, such as process crashes,
   51  network partitioning, and lost, distorted, or duplicated messages. One can even
   52  consider more Byzantine types of failure [5, 7, 8, 11, 14, 18, 191 in which faulty
   53  processes might go completely haywire, perhaps even sending messages according
   54  to some malevolent plan. One therefore wants an agreement protocol that is as
   55  reliable as possible in the presence of such faults. Of course, any protocol can be
   56  overwhelmed by faults that are too frequent or too severe, so the best that one can
   57  hope for is a protocol that is tolerant to a prescribed number of "expected" faults.
   58  In this paper, we show the surprising result that no completely asynchronous
   59  consensus protocol can tolerate even a single unannounced process death. We do
   60  not consider Byzantine failures, and we assume that the message system is reliableit delivers all messages correctly and exactly once. Nevertheless, even with these
   61  assumptions, the stopping of a single process at an inopportune time can cause any
   62  distributed commit protocol to fail to reach agreement. Thus, this important
   63  problem has no robust solution without further assumptions about the computing
   64  environment or still greater restrictions on the kind of failures to be tolerated!
   65  Crucial to our proof is that processing is completely asynchronous; that is, we
   66  make no assumptions about the relative speeds of processes or about the delay
   67  time in delivering a message. We also assume that processes do not have access to
   68  synchronized clocks, so algorithms based on time-outs, for example, cannot be
   69  used. (In particular, the solutions in [6] are not applicable.) Finally, we do not
   70  postulate the ability to detect the death of a process, so it is impossible for one
   71  process to tell whether another has died (stopped entirely) or is just running very
   72  slowly.

  250  4. Initially Dead Processes
  251  In this section, we exhibit a protocol that solves the consensus problem for N
  252  processes as long as a majority of the processes are nonfaulty and no process dies
  253  during the execution of the protocol. No process knows in advance, however,
  254  which of the processes are initially dead and which are not.
  255  The protocol works in two stages. During the first stage, the processes construct
  256  a directed graph G with a node corresponding to each process. Every process
  257  broadcasts a message containing its process number and then listens for messages
  258  from L - 1 other processes, where L = I(N + 1)/21. G has an edge from i to j iffj
  259  receives a message from i. Thus, G has indegree L - 1.
  260  In the second stage, the processes construct G+ (the transitive closure of G) in
  261  the sense that upon completion of this stage, each process k knows about all of the
  262  edges (j, k) incident on k in G+ as well as the initial values of all suchj.
  263  To carry out this stage, each process broadcasts to all other processes its process
  264  number and initial value together with the names of the L - 1 processes it heard
  265  from during the first stage. It then waits until it has received a stage 2 message
  266  from every ancestor in G that it knows about. Initially, it knows only about the
  267  L- 1 processes from which it heard directly during the first stage, but it learns
  268  about additional ancestors from the stage 2 messages that it receives. Waiting
  269  continues until such time as all currently known-about processes have been heard
  270  from.
  271  At this point, each process knows all of its own ancestors and the edges of G
  272  incident on them. Using this information, it computes all of the edges of G+
  273  incident on each of its ancestors. It then determines which of its ancestors belong
  274  to an initial clique of G+, that is, a clique with no incoming edges. To do this, it
  275  uses the fact that a node k is in an initial clique iff k is itself an ancestor of every
  276  node j that is an ancestor of k. Since every node in G+ has at ieast L - '1
  277  predecessors, there can be only one initial clique; it has cardinality at least L, and
  278  every process that completes the second stage knows exactly the set of processes
  279  comprising it.
  280  Finally, each process makes a decision based on the initial values of the processes
  281  in the initial clique using any agreed-upon rule. Since all processes know the initial
  282  values of all members of the initial clique, they all reach the same decision.
  283  The correctness of this protocol proves the following theorem.

  287  5. Conclusion

  288  We have shown that a natural and important problem of fault-tolerant cooperative

  289  computing cannot be solved in a totally asynchronous model of computation.

  290  These results do not show that such problems cannot be "solved" in practice;

  291  rather, they point up the need for more refined models of distributed computing

  292  that better reflect realistic assumptions about processor and communication tim-

  293  ings, and for less stringent requirements on the solution to such problems. (For

  294  example, termination might be required only with probability 1.) Subsequent to

  295  the original announcement of these results [ 121, progress has been made along both

  296  of these lines [ 1-4, 9, 10, 20, 251.
