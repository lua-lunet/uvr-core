  We present the first comprehensive study of application-level crash-consistency protocols built atop modern file systems. We find that applications use complex update protocols to persist state, and that the correctness of these protocols is highly dependent on subtle behaviors of the underlying file system, which we term persistence properties. We develop a tool named BOB that empirically tests persistence properties, and use it to demonstrate that these properties vary widely among six popular Linux file systems.    25  Abstract
   26  We present the first comprehensive study of applicationlevel crash-consistency protocols built atop modern file
   27  systems. We find that applications use complex update
   28  protocols to persist state, and that the correctness of
   29  these protocols is highly dependent on subtle behaviors
   30  of the underlying file system, which we term persistence
   31  properties. We develop a tool named BOB that empirically tests persistence properties, and use it to demonstrate that these properties vary widely among six popular Linux file systems. We build a framework named
   32  ALICE that analyzes application update protocols and
   33  finds crash vulnerabilities, i.e., update protocol code that
   34  requires specific persistence properties to hold for correctness. Using ALICE, we analyze eleven widely-used
   35  systems (including databases, key-value stores, version
   36  control systems, distributed systems, and virtualization
   37  software) and find a total of 60 vulnerabilities, many of
   38  which lead to severe consequences. We also show that
   39  ALICE can be used to evaluate the effect of new filesystem designs on application-level consistency.

   40  1 Introduction
   41  Crash recovery is a fundamental problem in systems
   42  research [8, 21, 34, 38], particularly in database management systems, key-value stores, and file systems.
   43  Crash recovery is hard to get right; as evidence, consider the ten-year gap between the release of commercial
   44  database products (e.g., System R [7, 8] and DB2 [34])
   45  and the development of a working crash recovery algorithm (ARIES [33]). Even after ARIES was invented, another five years passed before the algorithm was proven
   46  correct [24, 29].
   47  The file-systems community has developed a standard
   48  set of techniques to provide file-system metadata consistency in the face of crashes [4]: logging [5, 9, 21, 37, 45,
   49  51], copy-on-write [22,30,38,44], soft updates [18], and
   50  other similar approaches [10, 16]. While bugs remain in
   51  the file systems that implement these methods [28], the
   52  core techniques are heavily tested and well understood.
   53  Many important applications, including databases
   54  such as SQLite [43] and key-value stores such as LevelDB [20], are currently implemented on top of these
   55  file systems instead of directly on raw disks. Such datamanagement applications must also be crash consistent,

   56  USENIX Association

   57  Ramnatthan Alagappan

   58  Remzi H. Arpaci-Dusseau

   59  but achieving this goal atop modern file systems is challenging for two fundamental reasons.
   60  The first challenge is that the exact guarantees provided by file systems are unclear and underspecified.
   61  Applications communicate with file systems through the
   62  POSIX system-call interface [48], and ideally, a wellwritten application using this interface would be crashconsistent on any file system that implements POSIX.
   63  Unfortunately, while the POSIX standard specifies the
   64  effect of a system call in memory, specifications of how
   65  disk state is mutated in the event of a crash are widely
   66  misunderstood and debated [1]. As a result, each file system persists application data slightly differently, leaving
   67  developers guessing.
   68  To add to this complexity, most file systems provide
   69  a multitude of configuration options that subtly affect
   70  their behavior; for example, Linux ext3 provides numerous journaling modes, each with different performance
   71  and robustness properties [51]. While these configurations are useful, they complicate reasoning about exact
   72  file system behavior in the presence of crashes.
   73  The second challenge is that building a highperformance application-level crash-consistency protocol is not straightforward. Maintaining application consistency would be relatively simple (though not trivial)
   74  if all state were mutated synchronously. However, such
   75  an approach is prohibitively slow, and thus most applications implement complex update protocols to remain
   76  crash-consistent while still achieving high performance.
   77  Similar to early file system and database schemes, it is
   78  difficult to ensure that applications recover correctly after a crash [41, 47]. The protocols must handle a wide
   79  range of corner cases, which are executed rarely, relatively untested, and (perhaps unsurprisingly) error-prone.
   80  In this paper, we address these two challenges directly,
   81  by answering two important questions. The first question
   82  is: what are the behaviors exhibited by modern file systems that are relevant to building crash-consistent applications? We label these behaviors persistence properties
   83  (§2). They break down into two global categories: the
   84  atomicity of operations (e.g., does the file system ensure
   85  that rename() is atomic [32]?), and the orderingof operations (e.g., does the file system ensure that file creations
   86  are persisted in the same order they were issued?).

  137  Using ALICE, we also show that many of these vulnerabilities (roughly half) manifest on current file systems

  141  trouble properly recovering from a crash. We also find
  142  that 10 of the 11 applications expect atomicity of filesystem updates. In some cases, such a requirement is
  143  reasonable (e.g., a single 512-byte write or file rename

  155  allocation was introduced in Linux ext4, it broke several
  156  applications, resulting in bug reports, extensive mailinglist discussions, widespread data loss, and finally, filesystem changes [14]. With ALICE, testing the impact of
  157  changing persistence properties can become part of the
  158  file-system design process.

  171  2 Persistence Properties
  172  In this section, we study the persistence properties of
  173  modern file systems. These properties determine which
  174  possible post-crash file system states are possible for a
  175  given file system; as we will see, different file systems
  176  provide subtly different guarantees, making the challenge of building correct application protocols atop such
  177  systems more vexing.
  178  We begin with an example, and then describe our
  179  methodology: to explore possible on-disk states by reordering the I/O block stream, and then examine possible resulting states. Our testing is not complete, but
  180  finds persistence properties that do not hold for a filesystem implementation. We then discuss our findings for
  181  six widely-used Linux file systems: ext2 [6], ext3 [51],
  182  ext4 [50], btrfs [30], xfs [45], and reiserfs [37].
  183  Application-level crash consistency depends strongly
  184  upon these persistence properties, yet there are currently
  185  no standards. We believe that defining and studying persistence properties is the first step towards standardizing
  186  them across file systems.

  187  2.1 An Example
  188  All application update protocols boil down to a sequence
  189  of I/O-related system calls which modify on-disk state.
  190  Two broad properties of system calls affect how they are
  191  persisted. The first is atomicity: does the update from the
  192  call happen all at once, or are there possible intermediate
  193  states that might arise due to an untimely crash? The
  194  second is ordering: can this system call be persisted after
  195  a later system call? We now explain these properties with
  196  an example.
  197  We consider the following pseudo-code snippet:
  198  write(f1, "pp");
  199  write(f2, "qq");
  200  In this example, the application first appends the string
  201  pp to file descriptor f1 and then appends the string qq to
  202  file descriptor f2. Note that we will sometimes refer to
  203  such a write() as an append() for simplicity.
  204  Figure 2 shows a few possible crash states that can
  205  result. If the append is not atomic, for example, it would
  206  be possible for the size of the file to be updated without
  207  the new data reflected to disk; in this case, the files could
  208  contain garbage, as shown in State A in the diagram. We

  209  USENIX Association

  210  refer to this as size-atomicity. A lack of atomicity could
  211  also be realized with only part of a write reaching disk, as
  212  shown in State B. We refer to this as content-atomicity.
  213  If the file system persists the calls out of order, another
  214  outcome is possible (State C). In this case, the second
  215  write reaches the disk first, and as a result only the second
  216  file is updated. Various combinations of these states are
  217  also possible.
  218  As we will see when we study application update protocols, modern applications expect different atomicity
  219  and ordering properties from underlying file systems. We
  220  now study such properties in detail.

  221  2.2 Study and Results
  222  We study the persistence properties of six Linux file systems: ext2, ext3, ext4, btrfs, xfs, and reiserfs. A large
  223  number of applications have been written targeting these
  224  file systems. Many of these file systems also provide
  225  multiple configurations that make different trade-offs between performance and consistency: for instance, the
  226  data journaling mode of ext3 provides the highest level of
  227  consistency, but often results in poor performance [35].
  228  Between file systems and their various configurations, it
  229  is challenging to know or reason about which persistence
  230  properties are provided. Therefore, we examine different
  231  configurations of the file systems we study (a total of 16).
  232  To study persistence properties, we built a tool, known
  233  as the Block Order Breaker (BOB), to empirically find
  234  cases where various persistence properties do not hold
  235  for a given file system. BOB first runs a simple usersupplied workload designed to stress the persistence
  236  property tested (e.g., a number of writes of a specific size
  237  to test overwrite atomicity). BOB collects the block I/O
  238  generated by the workload, and then re-orders the collected blocks, selectively writing some of them to disk to
  239  generate a new legal disk state (disk barriers are obeyed).
  240  In this manner, BOB generates a number of unique disk
  241  images corresponding to possible on-disk states after a
  242  system crash. BOB then runs file-system recovery on
  243  each resulting disk image, and checks whether various
  244  persistence properties hold (e.g., if writes were atomic).
  245  If BOB finds even a single disk image where the checker
  246  fails, then we know that the property does not hold on
  247  the file system. Proving the converse (that a property
  248  holds in all situations) is not possible using BOB; currently, only simple block re-orderings and all prefixes of
  249  the block trace are tested.
  250  Note that different system calls (e.g., writev(),
  251  write()) lead to the same file-system output. We group
  252  such calls together into a generic file-system update we
  253  term an operation. We have found that grouping all operations into three major categories is sufficient for our
  254  purposes here: file overwrite, file append, and directory
  255  operations (including rename, link, unlink, mkdir, etc.).

  287  2.2.1 Atomicity
  288  We observe that all tested file systems seemingly provide atomic single-sector overwrites: in some cases (e.g.,
  289  ext3-ordered), this property arises because the underlying disk provides atomic sector writes. Note that if such
  290  file systems are run on top of new technologies (such as
  291  PCM) that provide only byte-level atomicity [12], singlesector overwrites will not be atomic.
  292  Providing atomic appends requires the update of two
  293  locations (file inode, data block) atomically. Doing so requires file-system machinery, and is not provided by ext2
  294  or writeback configurations of ext3, ext4, and reiserfs.
  295  Overwriting an entire block atomically requires data
  296  journaling or copy-on-write techniques; atomically appending an entire block can be done using ordered mode
  297  journaling, since the file system only needs to ensure the

  298  entire block is persisted before adding a pointer to it.
  299  Current file systems do not provide atomic multi-block
  300  appends; appends can be broken down into multiple operations. However, most file systems seemingly guarantee that some prefix of the data written (e.g., the first 10
  301  blocks of a larger append) will be appended atomically.
  302  Directory operations such as rename() and link()
  303  are seemingly atomic on all file systems that use techniques like journaling or copy-on-write for consistency.

  304  2.2.2 Ordering
  305  We observe that ext3, ext4, and reiserfs in data journaling mode, and ext2 in sync mode, persist all tested operations in order. Note that these modes often result in
  306  poor performance on many workloads [35].
  307  The append operation has interesting special cases. On
  308  file systems with the delayed allocation feature, it may
  309  be persisted after other operations. A special exception
  310  to this rule is when a file is appended, and then renamed.
  311  Since this idiom is commonly used to atomically update
  312  files [14], many file systems recognize it and allocate
  313  blocks immediately. A similar special case is appending to files that have been opened with O TRUNC. Even
  314  with delayed allocation, successive appends to the same
  315  file are persisted in order. Linux ext2 and btrfs freely reorder directory operations (especially operations on different directories [11]) to increase performance.

  316  2.3 Summary
  317  From Table 1, we observe that persistence properties
  318  vary widely among file systems, and even among different configurations of the same file system. The order of
  319  persistence of system calls depends upon small details
  320  like whether the calls are to the same file or whether the
  321  file was renamed. From the viewpoint of an application
  322  developer, it is risky to assume that any particular property will be supported by all file systems.

  323  3 The Application-Level Intelligent

  324  Crash Explorer (ALICE)
  325  We have now seen that file systems provide different persistence properties. However, some important questions
  326  remain: How do current applications update their on-disk
  327  structures? What do they assume about the underlying
  328  file systems? Do such update protocols have vulnerabilities? To address these questions, we developed ALICE
  329  (Application-Level Intelligent Crash Explorer). ALICE
  330  constructs different on-disk file states that may result due
  331  to a crash, and then verifies application correctness on
  332  each created state.
  333  Unlike other approaches [53, 54] that simply test an
  334  application atop a given storage stack, ALICE finds the
  335  generic persistence properties required for application
  336  correctness, without being restricted to only a specified

  356  3.1 Usage
  357  ALICE is simple to use. The user first supplies ALICE
  358  with an initial snapshot of the files used by the application (typically an entire directory), and a workload script
  359  that exercises the application (such as performing a transaction). The user also supplies a checker script corresponding to the workload that verifies whether invariants
  360  of the workload are maintained (such as atomicity of the
  361  transaction). ALICE runs the checker atop different crash
  362  states, i.e., the state of files after rebooting from a system
  363  crash that can occur during the workload. ALICE then
  364  produces a logical representation of the update protocol
  365  executed during the workload, vulnerabilities in the protocol and their associated source lines, and persistence

  389  3.2 Crash States and APMs
  390  Figure 3 shows an overview of the steps ALICE follows
  391  to find crash vulnerabilities. The user-supplied workload
  392  is first run, and a system-call trace obtained; the trace
  393  represents an execution of the application's update protocol. The trace is converted into a sequence of logical
  394  operations by ALICE. The sequence of logical operations, along with an APM, is used to calculate the different crash states that are possible from the initial state.
  395  These steps are now explained in detail.

  396  3.2.1 Logical Operations
  397  ALICE first converts the trace of system calls in the application workload to logical operations. Logical operations abstract away details such as current read and write
  398  offsets, file descriptors, and transform a large set of system calls and other I/O producing behavior into a small
  399  set of file-system operations. For example, write(),
  400  pwrite(), writev(), pwritev(), and mmap()-writes
  401  are all translated into overwrite or append logical operations. Logical operations also associate a conceptual
  402  inode to each file or directory involved.

  493  As explained, using the APM, ALICE can translate the
  494  system-call trace into micro-ops and calculate ordering
  495  dependencies amongst them. Listing 2 shows an example

  501  micro-ops in a selected set to the initial state (represented
  502  as logical entities). For each crash state, ALICE then converts the logical entities back into actual files, and supplies them to the checker. The user-supplied checker thus
  503  verifies the crash state.

  505  By default, ALICE targets specific crash states that concern the ordering and atomicity of each individual system
  506  call. The explored states thus relate to basic persistence
  507  properties like those discussed in Section 2, making it

  512  We now briefly describe the crash states explored.
  513  Atomicity across System Calls. The application update protocol may require multiple system calls to be
  514  persisted together atomically. This property is easy to
  515  check: if the protocol has N system calls, ALICE constructs one crash state for each prefix (i.e., the first X
  516  system calls, ∀ 1 < X < N) applied. In the sequence
  517  of crash states generated in this manner, the first crash
  518  state to have an application invariant violated indicates
  519  the start of an atomic group. The invariant will hold
  520  once again in crash states where all the system calls in
  521  the atomic group are applied. If ALICE determines that a
  522  system call X is part of an atomic group, it does not test
  523  whether the protocol is vulnerable to X being persisted
  524  out of order, or being partially persisted.
  525  System-Call Atomicity. The protocol may require a
  526  single system call to be persisted atomically. ALICE tests
  527  this for each system call by applying all previous system calls to the crash state, and then generating crash
  528  states corresponding to different intermediate states of
  529  the system call and checking if application invariants are
  530  violated. The intermediate states for file-system operations depend upon the APM, as shown (for example)
  531  in Table 2. Some interesting cases include how ALICE
  532  handles appends and how it explores the atomicity of
  533  writes. For appends, we introduce intermediate states
  534  where blocks are filled with random data; this models
  535  the update of the size of a file reaching disk before the
  536  data has been written. We split overwrites and appends
  537  in two ways: into block-sized micro-operations, and into
  538  three parts regardless of size. Though not exhaustive, we
  539  have found our exploration of append and write atomicity useful in finding application vulnerabilities.
  540  Ordering Dependency among System Calls. The
  541  protocol requires system call A to be persisted before B
  542  if a crash state with B applied (and not A) violates application invariants. ALICE tests this for each pair of system
  543  calls in the update protocol by applying every system call
  544  from the beginning of the protocol until B except for A.

  545  3.4 Static Vulnerabilities
  546  ALICE must be careful in how it associates problems
  547  found in a system-call trace with source code. For example, consider an application issuing ten writes in a loop.
  548  The update protocol would then contain ten write()
  549  system calls. If each write is required to be atomic for
  550  application correctness, ALICE detects that each system
  551  call is involved in a vulnerability; we term these as dynamic vulnerabilities. However, the cause of all these
  552  vulnerabilities is a single source line. ALICE uses stack
  553  trace information to correlate all 10 system calls to the
  554  line, and reports it as a single static vulnerability. In the
  555  rest of this paper, we only discuss static vulnerabilities.

  557  3.5 Implementation
  558  ALICE consists of around 4000 lines of Python code, and
  559  also traces memory-mapped writes in addition to system
  560  calls. It employs a number of optimizations.
  561  First, ALICE caches crash states, and constructs a new
  562  crash state by incrementally applying micro-operations
  563  onto a cached crash state. We also found that the time
  564  required to check a crash state was much higher than
  565  the time required to incrementally construct a crash state.
  566  Hence, ALICE constructs crash states sequentially, but invokes checkers concurrently in multiple threads.
  567  Different micro-op sequences can lead to the same
  568  crash state. For example, different micro-op sequences
  569  may write to different parts of a file, but if the file is unlinked at the end of sequence, the resulting disk state is
  570  the same. Therefore, ALICE hashes crash states and only
  571  checks the crash state if it is new.
  572  We found that many applications write to debug logs
  573  and other files that do not affect application invariants.
  574  ALICE filters out system calls involved with these files.

  575  3.6 Limitations
  576  ALICE is not complete, in that there may be vulnerabilities that are not detected by ALICE. It also requires the
  577  user to write application workloads and checkers; we believe workload automation is orthogonal to the goal of
  578  ALICE, and various model-checking techniques can be
  579  used to augment ALICE. For workloads that use multiple
  580  threads to interact with the file system, ALICE serializes
  581  system calls in the order they were issued; in most cases,
  582  this does not affect vulnerabilities as the application uses
  583  some form of locking to synchronize between threads.
  584  ALICE currently does not handle file attributes; it would
  585  be straight-forward to extend ALICE to do so.

  586  4 Application Vulnerabilities
  587  We study 11 widely used applications to find whether
  588  file-system behavior significantly affects application
  589  users, which file-system behaviors are thus important,
  590  and whether testing using ALICE is worthwhile in general. One of ALICE's unique advantages, of being able
  591  to find targeted vulnerabilities under an abstract file system and reporting them in terms of a persistence property violated, is thus integral to the study. The applications each represent different domains, and range
  592  in maturity from a few years-old to decades-old. We
  593  study three key-value stores (LevelDB [20], GDBM [19],
  594  LMDB [46]), three relational databases (SQLite [43],
  595  PostgreSQL [49], HSQLDB [23]), two version control
  596  systems (Git [26], Mercurial [31]), two distributed systems (HDFS [40], ZooKeeper [3]), and a virtualization
  597  software (VMWare Player [52]). We study two versions
  598  of LevelDB (1.10, 1.15), since they vary considerably in
  599  their update-protocol implementation.

  619  4.1 Workloads and Checkers
  620  Most applications have configuration options that change
  621  the update protocol or application crash guarantees. Our
  622  workloads test a total of 34 such configuration options
  623  across the 11 applications. Our checkers are conceptually simple: they do read operations to verify workload
  624  invariants for that particular configuration, and then try
  625  writes to the datastore. However, some applications have
  626  complex invariants, and recovery procedures that they
  627  expect users to carry out (such as removing a leftover
  628  lock file). Our checkers are hence complex (e.g., about
  629  500 LOC for Git), invoking all recovery procedures we
  630  are aware of that are expected of normal users.
  631  We now discuss the workloads and checkers for
  632  each application class. Where applicable, we also
  633  present the guarantees we believe each application makes
  634  to users, information garnered from documentation,
  635  mailing-list discussions, interaction with developers, and
  636  other relevant sources.
  637  Key-value Stores and Relational Databases. Each
  638  workload tests different parts of the protocol, typically
  639  opening a database, and inserting enough data to trigger
  640  checkpoints. The checkers check for atomicity, ordering,
  641  and durability of transactions. We note here that GDBM
  642  does not provide any crash guarantees, though we believe lay users will be affected by any loss of integrity.
  643  Similarly, SQLite does not provide durability under the
  644  default journal-mode (we became aware of this only after interacting with developers), but its documentation
  645  seems misleading. We enable checksums on LevelDB.

  646  Version Control Systems. Git's crash guarantees are
  647  fuzzy; mailing-list discussions suggest that Git expects a
  648  fully-ordered file system [27]. Mercurial does not provide any guarantees, but does provide a plethora of manual recovery techniques. Our workloads add two files to
  649  the repository and then commit them. The checker uses
  650  commands like git-log, git-fsck, and git-commit
  651  to verify repository state, checking the integrity of the
  652  repository and the durability of the workload commands.
  653  The checkers remove any leftover lock files, and perform
  654  recovery techniques that do not discard committed data
  655  or require previous backups.
  656  Virtualization and Distributed Systems. The
  657  VMWare Player workload issues writes and flushes from
  658  within the guest; the checker repairs the virtual disk
  659  and verifies that flushed writes are durable. HDFS is
  660  configured with replicated metadata and restore enabled.
  661  HDFS and ZooKeeper workloads create a new directory
  662  hierarchy; the checker tests that files created before the
  663  crash exist. In ZooKeeper, the checker also verifies that
  664  quota and ACL modifications are consistent.
  665  If ALICE finds a vulnerability related to a system call,
  666  it does not search for other vulnerabilities related to the
  667  same call. If the system call is involved in multiple, logically separate vulnerabilities, this has the effect of hiding some of the vulnerabilities. Most tested applications,
  668  however, have distinct, independent sets of failures (e.g.,
  669  dirstate and repository corruption in Mercurial, consistency and durability violation in other applications). We
  670  use different checkers for each type of failure, and report
  671  vulnerabilities for each checker separately.
  672  Summary. If application invariants for the tested configuration are explicitly and conspicuously documented,
  673  we consider violating those invariants as failure; otherwise, our checkers consider violating a lay user's expectations as failure. We are careful about any recovery
  674  procedures that need to be followed on a system crash.
  675  Space constraints here limit exact descriptions of the
  676  checkers; we provide more details in our webpage [2].

  774  4.2.2 Version Control Systems
  775  Git and Mercurial maintain meta-information about their
  776  repository in the form of logs. The Git protocol is illustrated in Figure 4(G). Git stores information in the
  777  form of object files, which are never modified; they are
  778  created as temporary files, and then linked to their permanent file names. Git also maintains pointers in separate files, which point to both the meta-information log
  779  and the object files, and are updated using update-viarename. Mercurial, on the other hand, uses a journal to
  780  maintain consistency, using update-via-rename only for
  781  a few unimportant pieces of information.
  782  We find many ordering dependencies in the Git protocol, as shown in Figure 4(G). This result is not surprising, since mailing-list discussions suggest Git developers
  783  expect total ordering from the file system. We also find
  784  a Git vulnerability involving atomicity across multiple
  785  system calls; a pointer file being updated (via an append)
  786  has to be persisted atomically with another file getting
  787  updated (via an update-via-rename). In Mercurial, we
  788  find many ordering vulnerabilities for the same reason,
  789  not being designed to tolerate out-of-order persistence.

  790  4.2.3 Virtualization and Distributed Systems
  791  VMWare Player's protocol is simple. VMWare maintains a static, constant mapping between blocks in the
  792  virtual disk, and in the VMDK file (even for dynamically allocated VMDK files); directly overwriting the VMDK

  793  file maintains consistency (though VMWare does use
  794  update-via-rename for some small files). Both HDFS and
  795  ZooKeeper use write-ahead logging. Figure 4(K) shows
  796  the ZooKeeper logging module. We find that ZooKeeper
  797  does not explicitly persist directory entries of log files,
  798  which can lead to lost data. ZooKeeper also requires
  799  some log writes to be atomic.

  897  4.4.2 Atomicity within System Calls
  898  Append atomicity. Surprisingly, three applications require appends to be content-atomic: the appended portion should contain actual data. The failure consequences
  899  are severe, such as corrupted reads (HSQLDB), failed
  900  reads (LevelDB-1.15) and repository corruption (Mercurial). Filling the appended portion with zeros instead of
  901  garbage still causes failure; only the current implementation of delayed allocation (where file size does not increase until actual content is persisted) works. Most appends seemingly do not need to be block-atomic; only
  902  Mercurial is affected, and the affected append also requires content-atomicity.
  903  Overwrite atomicity. LMDB, PostgreSQL, and
  904  ZooKeeper require small writes (< 200 bytes) to be
  905  atomic. Both the LMDB and PostgreSQL vulnerabilities
  906  are previously known.
  907  We do not find any multi-block overwrite vulnerabilities, and even single-block overwrite requirements are
  908  typically documented. This finding is in stark contrast
  909  with append atomicity; some of the difference can be
  910  attributed to the default APM (overwrites are contentatomic), and to some workloads simply not using overwrites. However, the major cause seems to be the basic
  911  mechanism behind application update protocols: modifications are first logged, in some form, via appends;
  912  logged data is then used to overwrite the actual data. Applications have careful mechanisms to detect and repair
  913  failures in the actual data, but overlook the presence of
  914  garbage content in the log.
  915  Directory operation atomicity. Given that most file
  916  systems provide atomic directory operations (§2.2), one
  917  would expect that most applications would be vulnerable to such operations not being atomic. However, we
  918  do not find this to be the case for certain classes of applications. Databases and key-value stores do not employ atomic renames extensively; consequently, we observe non-atomic renames affecting only three of these
  919  applications (GDBM, HSQLDB, LevelDB). Non-atomic
  920  unlinks seemingly affect only HSQLDB (which uses unlinks for logically performing renames), and we did not
  921  find any application affected by non-atomic truncates.

  922  4.4.3 Ordering between System Calls
  923  Applications are extremely vulnerable to system calls being persisted out of order; we find 27 vulnerabilities.

  924  Safe renames. On file systems with delayed allocation, a common heuristic to prevent data loss is to persist
  925  all data (including appends and truncates) of a file before
  926  subsequent renames of the file [14]. We find that this
  927  heuristic only matches (and thus fixes) three discovered
  928  vulnerabilities, one each in Git, Mercurial, and LevelDB-
  929  1.10. A related heuristic, where updating existing files
  930  by opening them with O TRUNC flushes the updated data
  931  while issuing a close(), does not affect any of the vulnerabilities we discovered. Also, the effect of the heuristics varies with minor details: if the safe-rename heuristic does not persist file truncates, only two vulnerabilities
  932  will be fixed; if the O TRUNC heuristic also acts on new
  933  files, an additional vulnerability will be fixed.
  934  Safe file flush. An fsync() on a file does not guarantee that the file's directory entry is also persisted. Most
  935  file systems, however, persist directory entries that the
  936  file is dependent on (e,g., directory entries of the file and
  937  its parent). We found that this behavior is required by
  938  three applications for maintaining basic consistency.

  939  4.4.4 Durability
  940  We find vulnerabilities in seven applications resulting in
  941  durability loss. Of these, only two applications (GDBM
  942  and Mercurial) are affected because an fsync() is not
  943  called on a file. Six applications require fsync() calls
  944  on directories: three are affected by safe file flush discussed previously, while four (HSQLDB, SQLite, Git,
  945  and Mercurial) require other fsync() calls on directories. As a special case, with HSQLDB, previously committed data is lost, rather than data that was being committed during the time of the workload. In all, only
  946  four out of the twelve vulnerabilities are exposed when
  947  full ordering is promised: many applications do issue an
  948  fsync() call before durability is essential, but do not
  949  fsync() all the required information.

  950  4.4.5 Summary
  951  We believe our study offers several insights for filesystem designers. Future file systems should consider
  952  providing ordering between system calls, and atomicity within a system call in specific cases. Vulnerabilities involving atomicity of multiple system calls seem to
  953  have minor consequences. Requiring applications to separately flush the directory entry of a created and flushed
  954  file can often result in application failures. For durability,
  955  most applications seem to explicitly flush some, but not
  956  all, of the required information; thus, providing ordering
  957  among system calls can also help durability.

  960  system model (i.e., APM) in order to discover the broadest number of vulnerabilities. We now utilize specific
  961  file-system APMs to understand how modern protocols

  982  4.6 Evaluating New File-System Designs
  983  File-system modifications for improving performance
  984  have introduced wide-spread data loss in the past [14],
  985  because of changes to the file-system persistence properties. ALICE can be used to test whether such modifications break correctness of existing applications. We now
  986  describe how we use ALICE to evaluate a hypothetical
  987  variant of ext3 (data-journaling mode), ext3-fast.
  988  Our study shows that ext3 (data-journaling mode) is
  989  the safest file system; however, it offers poor performance for many workloads [35]. Specifically, fsync()
  990  latency is extremely high as ext3 persists all previous operations on fsync(). One way to reduce fsync() latency would be to modify ext3 to persist only the synced
  991  file. However, other file systems (e.g,. btrfs) that have
  992  attempted to reduce fsync() latency [13] have resulted
  993  in increased vulnerabilities. Our study suggests a way to
  994  reduce latency without exposing more vulnerabilities.
  995  Based on our study, we hypothesize that data that is
  996  not synced need not be persisted before explicitly synced
  997  data for correctness; such data must only be persisted
  998  in-order amongst itself. We design ext3-fast to reflect
  999  this: fsync() on a file A persists only A, while other
 1000  dirty data and files are still persisted in-order.
 1001  We modeled ext3-fast in ALICE by slightly changing
 1002  the APM of ext3 data journaling mode, so that synced
 1003  directories, files, and their data, depend only on previous
 1004  syncs and operations necessary for the file to exist (i.e.,
 1005  safe file flush is obeyed). The operations on a synced file
 1006  are also ordered among themselves.
 1007  We test our hypothesis with ALICE; the observed or-

 1008  USENIX Association

 1009  dering vulnerabilities (of the studied applications) are not
 1010  exposed under ext3-fast. The design was not meant to fix
 1011  durability or atomicity across system calls vulnerabilities, so those vulnerabilities are still reported by ALICE.
 1012  We estimate the performance gain of ext3-fast using
 1013  the following experiment: we first write 250 MB to
 1014  file A, then append a byte to file B and fsync() B.
 1015  When both files are on the same ext3-ordered file system,
 1016  fsync() takes about four seconds. If the files belong to
 1017  different partitions on the same disk, mimicking the behavior of ext3-fast, the fsync() takes only 40 ms. The
 1018  first case is 100 times slower because 250 MB of data is
 1019  ordered before the single byte that needs to be persistent.
 1020  Summary. The ext3-fast file system (derived from inferences provided by ALICE) seems interesting for application safety, though further investigation is required into
 1021  the validity of its design. We believe that the ease of use
 1022  offered by ALICE will allow it to be incorporated into the
 1023  design process of new file systems.

 1024  4.7 Discussion
 1025  We now consider why crash vulnerabilities occur commonly even among widely used applications. We find
 1026  that application update protocols are complex and hard to
 1027  isolate and understand. Many protocols are layered and
 1028  spread over multiple files. Modules are also associated
 1029  with other complex functionality (e.g., ensuring thread
 1030  isolation). This complexity leads to issues that are obvious with a bird's eye view of the protocol: for example,
 1031  HSQLDB's protocol has 3 consecutive fsync() calls to
 1032  the same file (increasing latency). ALICE helps solve this
 1033  problem by making it easy to obtain logical representations of update protocols as shown in Figure 4.
 1034  Another factor contributing to crash vulnerabilities is
 1035  poorly written, untested recovery code. In LevelDB, we
 1036  find vulnerabilities that should be prevented by correct
 1037  implementations of the documented update protocols.
 1038  Some recovery code is non-optimal: potentially recoverable data is lost in several applications (e.g., HSQLDB,
 1039  Git). Mercurial and LevelDB provide utilities to verify
 1040  or recover application data; we find these utilities hard to
 1041  configure and error-prone. For example, an user invoking LevelDB's recovery command can unintentionally
 1042  end up further corrupting the datastore, and be affected
 1043  by (seemingly) unrelated configuration options (paranoid checksums). We believe these problems are a direct
 1044  consequence of the recovery code being infrequently executed and insufficiently tested. With ALICE, recovery
 1045  code can be tested on many corner cases.
 1046  Convincing developers about crash vulnerabilities is
 1047  sometimes hard: there is a general mistrust surrounding
 1048  such bug reports. Usually, developers are suspicious that
 1049  the underlying storage stack might not respect fsync()
 1050  calls [36], or that the drive might be corrupt. We hence

 1053  believe that most vulnerabilities that occur in the wild are
 1054  associated with an incorrect root cause, or go unreported.
 1055  ALICE can be used to easily reproduce vulnerabilities.
 1056  Unclear documentation of application guarantees contributes to the confusion about crash vulnerabilities. During discussions with developers about durability vulnerabilities, we found that SQLite, which proclaims itself
 1057  as fully ACID-complaint, does not provide durability
 1058  (even optionally) with the default storage engine, though
 1059  the documentation suggests it does. Similarly, GDBM's
 1060  GDBM SYNC flag does not ensure durability. Users can
 1061  employ ALICE to determine guarantees directly from the
 1062  code, bypassing the problem of bad documentation.

 1063  5 Related Work
 1064  Our previous workshop paper [47] identifies the problem of application-level consistency depending upon filesystem behavior, but is limited to two applications and
 1065  does not use automated testing frameworks. Since we
 1066  use ALICE to obtain results, our current study includes a
 1067  greater number and variety of applications.
 1068  This paper adapts ideas from past work on dynamic
 1069  program analysis and model checking. EXPLODE [53]
 1070  has a similar flavor to our work: the authors use insitu model checking to find crash vulnerabilities on different storage stacks. ALICE differs from EXPLODE in
 1071  four significant ways. First, EXPLODE requires the target
 1072  storage stack to be fully implemented; ALICE only requires a model of the target storage stack, and can therefore be used to evaluate application-level consistency on
 1073  top of proposed storage stacks, while they are still at
 1074  the design stage. Second, EXPLODE requires the user to
 1075  carefully annotate complex file systems using choose()
 1076  calls; ALICE requires the user to only specify a highlevel APM. Third, EXPLODE reconstructs crash states by
 1077  tracking I/O as it moves from the application to the storage. Although it is possible to use EXPLODE to determine the root cause of a vulnerability, we believe it is
 1078  easier to do so using ALICE since ALICE checks for violation of specific persistence properties. Fourth, EXPLODE stops at finding crash vulnerabilities; by helping
 1079  produce protocol diagrams, ALICE contributes to understanding the protocol itself. Like BOB, EXPLODE can be
 1080  used to test persistence properties; however, while BOB
 1081  only re-orders block I/O, EXPLODE can test re-orderings
 1082  caused at different layers in the storage stack.
 1083  Zheng et al. [54] find crash vulnerabilities in
 1084  databases. They contribute a standard set of workloads
 1085  that stress databases (particularly, with multiple threads),
 1086  and check ACID properties; the workloads and checkers
 1087  can be used with ALICE. Unlike our work, Zheng et al.
 1088  do not systematically explore vulnerabilities of each system call; they are limited by the re-orderings and nonatomicity exhibited by a particular (implemented) file

 1089  system during a single workload execution. Thus, their
 1090  work is more suited for finding those vulnerabilities that
 1091  are commonly exposed under a given file system.
 1092  Woodpecker [15] can be used to find crash vulnerabilities when supplied with suspicious source code patterns
 1093  to guide symbolic execution. Our work is fundamentally
 1094  different to this approach, as ALICE does not require prior
 1095  knowledge of patterns in checked applications.
 1096  Our work is influenced by SQLite's internal testing
 1097  tool [43]. The tool works at an internal wrapper layer
 1098  within SQLite, and is not helpful for generic testing.
 1099  RACEPRO [25], a testing tool for concurrency bugs,
 1100  records system calls and replays them by splitting them
 1101  into small operations, but does not test crash consistency.
 1102  OptFS [9], Featherstitch [16], and transactional file
 1103  systems [17, 39, 42], discuss new file-system interfaces
 1104  that will affect vulnerabilities. Our study can help inform
 1105  the design of new interfaces by providing clear insights
 1106  into what is missing in today's interfaces.

 1107  6 Conclusion
 1108  In this paper, we show how application-level consistency
 1109  is dangerously dependent upon file system persistence
 1110  properties, i.e., how file systems persist system calls.
 1111  We develop BOB, a tool to test persistence properties
 1112  and show that such properties vary widely among file
 1113  systems. We build ALICE, a framework that analyzes
 1114  application-level protocols and detects crash vulnerabilities. We analyze 11 applications, and find 60 vulnerabilities, some of which result in severe consequences
 1115  like corruption or data loss. We present several insights
 1116  derived from our study. The ALICE tool, and detailed descriptions of the vulnerabilities found in our study, can
 1117  be obtained from our webpage [2].
