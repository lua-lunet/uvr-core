   10  Abstract. Lean 4 is a reimplementation of the Lean interactive theorem prover (ITP) in Lean itself. It addresses many shortcomings of the
   11  previous versions and contains many new features. Lean 4 is fully extensible: users can modify and extend the parser, elaborator, tactics, decision
   12  procedures, pretty printer, and code generator. The new system has a hygienic macro system custom-built for ITPs. It contains a new typeclass
   13  resolution procedure based on tabled resolution, addressing significant
   14  performance problems reported by the growing user base. Lean 4 is also
   15  an efficient functional programming language based on a novel programming paradigm called functional but in-place. Efficient code generation
   16  is crucial for Lean users because many write custom proof automation
   17  procedures in Lean itself.

   18  1 Introduction

   19  The Lean project3 started in 2013 [9] as an interactive theorem prover based on

   20  the Calculus of Inductive Constructions [4] (CIC). In 2017, using Lean 3, a com-

   21  munity of users with very different backgrounds started the Lean mathematical

   22  library project mathlib [13]. At the time of this writing, mathlib has roughly half

   23  a million lines of code, and contains many nontrivial mathematical objects such

   24  as Schemes [2]. Mathlib is also the foundation for the Perfectoid Spaces in Lean

   25  project [1], and the Liquid Tensor challenge [11] posed by the renowned mathe-

   26  matician Peter Scholze. Mathlib contains not only mathematical objects but also

   27  Lean metaprograms that extend the system [5]. Some of these metaprograms

   28  implement nontrivial proof automation, such as a ring theory solver and a de-

   29  cision procedure for Presburger arithmetic. Lean metaprograms in mathlib also

   30  extend the system by adding new top-level command and features not related

   31  to proof automation. For example, it contains a package of semantic linters that

   32  alert users to many commonly made mistakes [5]. Lean 3 metaprograms have

   37  We believe the Lean 3 theorem prover's success is primarily due to its exten-

   39  modify many parts of the system without changing Lean 3 source code written

   40  in C++. Another issue is that many proof automation metaprograms are not

   41  competitive with similar proof automation implemented in programming lan-

   42  guages with an efficient compiler such as C++ and OCaml. The primary source

   43  of inefficiency in Lean 3 metaprograms is the virtual machine interpretation

   44  overhead.
   45  Lean 4 is a reimplementation of the Lean theorem prover in Lean itself4.

   46  It is an extensible theorem prover and an efficient programming language. The

   47  new compiler produces C code, and users can now implement efficient proof au-

   48  tomation in Lean, compile it into efficient C code, and load it as a plugin. In

   49  Lean 4, users can access all internal data structures used to implement Lean
   50  by merely importing the Lean package. Lean 4 is also a platform for developing

   51  efficient domain-specific automation. It has a more robust and extensible elab-

   52  orator, and addresses many other shortcomings of Lean 3. We expect the Lean

   53  community to extend and add new features without having to change the Lean

   54  source code. We released Lean 4 at the beginning of 2021, it is open source, the

   55  community is already porting mathlib, and the number of applications is quickly
   56  growing. It includes a translation verifier for Reopt5, a package for supporting
   57  inductive-inductive types6, and a car controller7.

  172  Typeclass Resolution. Typeclasses [16] provide an elegant and effective way of

  173  managing ad-hoc polymorphism in both programming languages and interactive

  174  proof assistants. Then we can declare particular elements of a typeclass to be

  175  instances. These provide hints to the elaborator: any time the elaborator is

  176  looking for an element of a typeclass, it can consult a table of declared instances

  177  to find a suitable element. What makes typeclass inference powerful is that one

  178  can chain instances, that is, an instance declaration can in turn depend on other

  179  instances. This causes class inference to recurse through instances, backtracking

  180  when necessary. The Lean typeclass resolution procedure can be viewed as a

  181  simple λ-Prolog interpreter [8], where the Horn clauses are the user declared

  182  instances.
  183  For example, the standard library defines a typeclass Inhabited to enable

  184  typeclass inference to infer a "default" or "arbitrary" element of types that contain

  185  at least one element.
  186  class Inhabited (α : Sort u) where
  187  default : α

  188  def arbitrary [Inhabited α] : α :=
  189  Inhabited.default
  190  The annotation [Inhabited α] at arbitrary indicates that this implicit parame-

  191  ter should be synthesized from instance declarations using typeclass resolution.
  192  We can define an instance for our BoolExpr type defined earlier as follows
  193  instance : Inhabited BoolExpr where
  194  default := BoolExpr.val false
  195  This instance specifies that the "default" element for BoolExpr is BoolExpr.val
  196  false. The following declaration shows that if two types α and β are inhabited,

  197  then so is their product:
  198  instance [Inhabited α] [Inhabited β] : Inhabited (α × β) where
  199  default := (arbitrary, arbitrary)
  200  The standard library has many builtin classes such as Repr α and DecidableEq
  201  α. The class Repr α is similar to Haskell's Show α typeclass, and DecidableEq α

  202  is a typeclass for types that have decidable equality. Lean 4 also provides code
  203  synthesizers for many builtin classes. The command deriving instructs Lean to

  204  auto-generate an instance.

  213  few limitations in Lean 3: unnecessary overhead due to the lack of term indexing

  214  techniques, and exponential running times in the presence of diamonds. Lean 4

  215  implements a new procedure [12], tabled typeclass resolution, that solves these
  216  problems by using discrimination trees10. for better indexing and tabling, which

  217  is a generalization of memoizing introduced initially to address similar limitations
  218  of early logic programming systems11.

  219  The hygienic macro system. In interactive theorem provers (ITPs), Lean in-

  220  cluded, extensible syntax is not only crucial to lower the cognitive burden of

  221  manipulating complex mathematical objects, but plays a critical role in devel-

  222  oping reusable abstractions in libraries. Lean 3 support such extensions in the

  223  form of restrictive "syntax sugar" substitutions and other ad hoc mechanisms,

  224  which are too rudimentary to support many desirable abstractions. As a result,

  225  libraries are littered with unnecessary redundancy. The Lean 3 tactic languages

  226  is plagued by a seemingly unrelated issue: accidental name capture, which often

  227  produces unexpected and counterintuitive behavior. Lean 4 takes ideas from the

  228  Scheme family of programming languages and solves these two problems simul-

  229  taneously by use of a hygienic, i.e. capture-avoiding, macro system custom-built

  230  for ITPs [15].

  231  Lean 3's "mixfix" notation system is still supported in Lean 4, but based
  232  on the much more general macro system; in fact, the Lean 3 notation keyword

  233  itself has been reimplemented as a macro, more specifically as a macro-generating

  234  macro. By providing such a tower of abstractions for writing syntax sugars, of

  235  which we will see more levels below, we want to enable users to work in the

  236  simplest model appropriate for their respective use case while always keeping

  237  open the option to switch to a lower, more expressive level.

  300  3 The Code Generator

  301  The Lean 4 code generator produces efficient C code. It is useful for building

  302  both efficient Lean extensions and standalone applications. The code genera-

  303  tor performs many transformations, and many of them are based on techniques

  304  used in the Haskell compiler GHC [7]. However, in contrast to Haskell, Lean is a

  305  strict language. We control code inlining and specialization using the attributes
  306  @[inline] and @[specialize]. They are crucial for eliminating the overhead in-

  307  troduced by the towers of abstractions used in our source code. Before emitting

  308  C code, we erase proof terms and convert Lean expressions into an intermediate
  309  representation (IR). The IR is a collection of Lean data structures,12 and users

  310  can implement support for backends other than C by writing Lean programs
  311  that import Lean.Compiler.IR. Lean 4 also comes with an interpreter for the IR,

  312  which allows for rapid incremental development and testing right from inside the

  313  editor. Whenever the interpreter calls a function for which native, ahead-of-time

  314  compiled code is available, it will switch to that instead, which includes all func-

  315  tions from the standard library. Thus the interpretation overhead is negligible

  316  as long as e.g. all expensive tactics are precompiled.

  317  Functional but in-place. Most functional languages rely on garbage collection

  318  for automatic memory management. They usually eschew reference counting in

  319  favor of a tracing garbage collector, which has less bookkeeping overhead at run-

  320  time. On the other hand, having an exact reference count of each value enables

  321  optimizations such as destructive updates [14]. When performing functional up-

  322  dates, objects often die just before creating an object of the same kind. We

  323  observe a similar phenomenon when we insert a new element into a purely func-

  324  tional data structure, such as binary trees, a theorem prover rewrites formulas,

  325  a compiler applies optimizations by transforming abstract syntax trees, or the
  326  function simplify defined earlier. We call it the resurrection hypothesis: many

  327  objects die just before creating an object of the same kind. The Lean mem-

  328  ory manager uses reference counting and takes advantage of this hypothesis,

  329  and enables pure code to perform destructive updates in all scenarios described

  346  static linearity systems, allocations are also avoided even if only a prefix of the list

  347  is not shared. FBIP also allows Lean users to use data structures, such as arrays

  348  and hashtables, in pure code without any performance penalty when they are not

  349  shared. We believe this is an attractive feature because hashtables are frequently

  350  used to implement decision procedures and nontrivial proof automation.

  351  4 The User Interface

  352  Our system implements the Language Server Protocol (LSP) using the task ab-

  353  straction provided by its standard library. The Lean 4 LSP server is incremental

  354  and is continuously analyzing the source text and providing semantic informa-

  355  tion to editors implementing LSP. Our LSP server implements most LSP features

  356  found in advanced IDEs, such as hyperlinks, syntax highlighting, type informa-

  357  tion, error handling, auto-completion, etc. Many editors implement LSP, but VS

  358  Code is the preferred editor by the Lean user community. We provide extensions

  359  for visualizing the intermediate proof states in interactive tactic blocks, and we

  360  want to port the Lean 3 widget library for constructing interactive visualizations

  361  for their proofs and programs.

  362  5 Conclusion

  363  Lean 4 aims to be a fully extensible interactive theorem prover and functional

  364  programming language. It has an expressive logical foundation for writing mathe-

  365  matical specifications and proofs and formally verified programs. Lean 4 provides

  366  many new unique features, including a hygienic macro-system, an efficient type-

  367  class resolution procedure based on tabled resolution, efficient code generator,

  368  and abstractions for sealing low-level optimizations. The new elaboration proce-

  369  dure is more general and efficient than those implemented in previous versions.

  370  Users may also extend and modify the elaborator using Lean itself. Lean has a

  371  relatively small trusted kernel, and the rich API allows users to export their de-

  372  velopments to other systems and implement their own reference checkers. Lean
