   62  2 Models and Definitions
   63  This section formally defines three models: the classic
   64  Crash-Stop model, a Crash-Recovery model that uses
   65  stable storage, and the Diskless Crash-Recovery model
   66  without stable storage.
   67  In each case, we consider a distributed system of a
   68  fixed set of n processes, with IDs 1, . . . , n. Each process
   69  is modeled as an I/O automaton [11] that takes input
   70  or an internal action, produces output, and transitions
   71  between states. A distributed execution happens in discrete timesteps, during each of which, one (or more)
   72  process(es) takes a step. Processes communicate with
   73  each other by sending messages through a complete,
   74  asynchronous network. This means that messages can
   75  be lost, duplicated, or reordered arbitrarily – but not
   76  modified – by the network. However, we assume the
   77  network cannot duplicate or drop messages an infinite
   78  number of times (i.e., the network is fair-lossy).

   79  2.1 Crash-Stop Model
   80  The Crash-Stop (CS) model assumes that processes can
   81  fail by crashing and that crashes are permanent; a failed

   82  node stops executing the algorithm forever and stops
   83  communicating with other nodes. We say a process
   84  is UP if it is executing protocol steps and performing
   85  actions. If it crashes, it transitions to the DOWN state.
   86  Once DOWN, a process no longer accepts messages that
   87  are sent to it and forever remains in the DOWN state.

   88  2.2 Crash-Recovery Model with Local

   89  Stable Storage
   90  In the Crash-Recovery model (CR), a process can recover after crashing and resume executing the algorithm. As in the CS model, a process in this model is
   91  assumed to be either UP or DOWN, but it can also transition between the two states an infinite number of times.
   92  A process that is DOWN can recover and transition back
   93  to the UP state.
   94  We want this model to capture the distinction between the volatile state of the system and stable storage.
   95  As a result, the automaton does not recover in the same
   96  state it was in before the crash. Rather, it can access stable storage that it must manage explicitly. We abstract
   97  access to stable storage using an additional internal automaton action, WRITE(X), that persists X on stable
   98  storage. If the action completes successfully, X will always be seen by the automaton irrespective of the number of crashes. If the process crashes while WRITE(X)
   99  is pending, X may or may not be persisted.
  100  When a process restarts in this model, it can recover
  101  state by using another internal action, READ, that returns the set of all values X that were persisted using
  102  the WRITE(X) action in the past. Our choice of a set of
  103  values as the interface to READ is somewhat arbitrary.
  104  We could instead provide a log interface or a single
  105  atomically-updated value; these options are equivalent
  106  to one another, in that each can trivially be constructed
  107  from the others.

  108  2.3 Diskless Crash-Recovery:

  109  Crash-Recovery without Local Stable

  110  Storage
  111  We focus on the Diskless Crash-Recovery (DCR)
  112  model, where nodes have no access to stable storage.
  113  As in the CR model, a process can recover after crashing and resume execution. However, unlike CR, DCR
  114  has no READ or WRITE actions.
  115  Upon recovery, a process loses all state except its
  116  unique process ID in t1,2, ...,nu. However, processes
  117  can read from a local clock to get a number guaranteed
  118  to be larger than any previous number read by any previous incarnation of that process. Importantly, this makes
=== PAGE 3 ===

  119  it possible to distinguish between different incarnations
  120  of the same processes.1
  121  A recovering process must bring itself to a state that
  122  lets it resume its computation without violating any
  123  guarantee of the algorithm. To do so, a process that recovers runs a distinct recovery protocol. This protocol
  124  can communicate with other processes to recover previous state. Once the recovery protocol terminates, the
  125  automaton changes its internal status to operational and
  126  resumes execution of its normal protocol.
  127  We describe a process that is UP as RECOVERING if
  128  it is running its recovery protocol and OPERATIONAL
  129  otherwise. This distinction makes it possible to state
  130  failure bounds in terms of the number of operational
  131  processes, e.g., that no more than half of the processes
  132  can be either down or recovering at any moment. Our
  133  definition matches the design of existing protocols (e.g.,
  134  Viewstamped Replication [10]).
  135  One important property that protocols in the DCR
  136  model should satisfy is recovery termination, which
  137  requires a recovering process to eventually complete
  138  recovery and become OPERATIONAL, as long as it does
  139  not crash again. We are thus not interested in trivial
  140  solutions, i.e., those where recovering processes declare
  141  themselves to be permanently DOWN and never again
  142  participate in the normal protocol.

  143  3 Model Transformations
  144  Many algorithms solve problems in the CS failure
  145  model. When can these algorithms be applied to solving the same problems in the CR or DCR models?

  146  Crash-Stop to Crash-Recovery with Stable Storage.
  147  Transforming CS protocols to the CR model is trivial when local stable storage is available. This can be
  148  done by recording every state transition to disk before
  149  performing output actions. Equivalently, the automaton can log every message and input action received to
  150  stable storage and replay these in order on recovery.
  151  Any asynchronous CS algorithm transformed in this
  152  way provides the same guarantees in the CR model.
  153  Because the automaton recovers in the same state it
  154  was in before crashing, the only difference is that it
  155  does not process any messages that it received while
  156  it was down. Asynchronous algorithms are inherently
  157  robust to these omission failures [3] because they can
  158  1 The algorithm we present in Section 5 could be easily adapted
  159  to work when processes can only generate a unique number instead
  160  of a monotonically increasing one. We assume a monotonic clock
  161  only for simplicity of exposition.

  162  handle messages that the network drops or delays.
  163  Towards Diskless Crash Recovery. This paper
  164  poses the question, How can a protocol from the
  165  Crash-Stop or Crash-Recovery model be correctly
  166  transformed to one that works in the Diskless Crash-
  167  Recovery model? Specifically, can we implement a virtual stable storage abstraction in the DCR model that
  168  provides the same READ/WRITE() interface defined
  169  in CR? In the DCR model, a process can persist state
  170  only by replicating on other processes in the system.
  171  Hence, any READ/WRITE(X) action must communicate with other processes in the system to provide the
  172  same guarantees even in the presence of concurrent failures. We begin by defining the notion of virtual stable
  173  storage:
  174  Virtual Stable Storage. We say that an algorithm
  175  correctly implements virtual stable storage in the DCR
  176  model if it provides READ and WRITE(X) primitives
  177  with the following properties:

  178  • Persistence: A successful READ outputs the set of
  179  all objects the process successfully persisted through
  180  a prior invocation of WRITE(X).
  181  • Termination: Every READ and WRITE(X) at a process eventually succeeds unless the process crashes.

  182  4 State Machine Replication in

  183  Diskless Crash-Recovery
  184  Providing stable storage in the DCR model seems superficially straightforward – simply replace each write
  185  to disk with a write to a majority of replicas. However, there are surprisingly subtle challenges; if handled
  186  na¨ıvely, delayed messages from prior incarnations of a
  187  process can lead to the illusion that a write has been
  188  persisted when, in fact, it could still be lost.
  189  As evidence of its subtlety, several protocols have
  190  attempted, and failed, to provide diskless crash recovery in the context of a specific problem, state machine
  191  replication. State machine replication (SMR) – a classic
  192  problem that lies at the core of many critical deployed
  193  distributed systems [2, 7, 9, 10, 13, 15] – highlights the
  194  relevance of diskless recovery: SMR deployments are
  195  long-lived and must be able to handle node crashes and
  196  recoveries, including ones where stable storage is lost.
  197  We analyze 3 state machine replication protocols for
  198  the DCR model: Viewstamped Replication [10], Paxos
  199  Made Live [2], and JPaxos [6]. In each case, we show
  200  that these protocols do not completely recover the state
=== PAGE 4 ===

  201  of a failed node under certain scenarios, a situation that
  202  can lead to user-visible violations of protocol correctness. To our knowledge, no prior work has provided a
  203  correct recovery protocol for this problem.
  204  This section provides a detailed case study of correctness problems in Viewstamped Replication and an
  205  overview of the equivalent problem in Paxos Made Live
  206  and JPaxos. A more complete description, including
  207  detailed traces of the failure in all three protocols, is
  208  available in Appendix A.

  209  4.1 Definitions
  210  The SMR approach models a replicated service as a
  211  state machine. Clients submit requests to the service,
  212  which runs a consensus protocol (e.g., Multi-Paxos or
  213  Viewstamped Replication) to establish a global order
  214  of requests; the replicas then execute that request and
  215  respond to the client. A correct SMR protocol provides
  216  linearizability [4]: clients receive responses as though
  217  their requests had been executed by a single system in
  218  a serial order; if operation A receives a response before
  219  B is invoked, A must precede B in that serial order.
  220  SMR is well known to be equivalent to repeated instances of consensus, or atomic broadcast. We choose
  221  to frame the problem as SMR rather than consensus because the former implies a long-lived system consistent
  222  with our DCR model. In particular, single-instance consensus admits some solutions (such as requiring some
  223  fraction of nodes to be up for the duration of the protocol [1]) that are not reasonable in the long-lived SMR
  224  model.

  225  4.2 Viewstamped Replication
  226  Viewstamped Replication (VR) is a classic SMR algorithm. The original presentation by Oki and Liskov in
  227  1988 [13] used stable storage for certain parts of the
  228  replica state. VR always guarantees sequence agreement and integrity, and it guarantees liveness as long as
  229  there is sufficient network synchrony and no more than
  230  f out of 2f `1 replicas are failed. A subsequent version [10] revised the protocol to eliminate the need for
  231  stable storage; we demonstrate that this version does
  232  not correctly handle all loss-of-state failures.
  233  VR is a leader-based algorithm: the system moves
  234  through a series of numbered views, in which one node
  235  is designated as the leader. VR uses 2 protocols. During normal case execution, the leader assigns sequence
  236  numbers to incoming client requests, sends PREPARE
  237  messages to replicas, and executes the operation once
  238  it has received replies from a majority. When the leader

  239  is suspected to have failed, a view change protocol replaces the leader with a new one. Replicas increment
  240  their view numbers, stop processing requests in the old
  241  view, then send the new leader a VIEW-CHANGE message with their log of operations. The new leader begins processing only when it receives VIEW-CHANGE
  242  messages from a majority of replicas, ensuring that it
  243  knows about all operations successfully completed in
  244  prior views. These two protocols are equivalent to the
  245  two phases of Paxos.
  246  View Change Invariant. In VR, an important invariant is that each replica's view number increases monotonically: once a replica sends a VIEW-CHANGE message for view v, it never returns to a lower view. This is
  247  important for correctness because it implies that replicas cannot commit to new operations in prior views
  248  once they have sent a VIEW-CHANGE message to the
  249  new leader. Without this invariant, a new leader cannot
  250  be guaranteed to know about all operations completed
  251  by previous leaders and would thus violate linearizability.
  252  Recovery in VR. Ensuring that nodes in VR can recover from failures requires providing a recovery procedure. This procedure must ensure that the view change
  253  invariant continues to hold, i.e., that each replica recovers in a view number at least as high as the view number
  254  in any VIEW-CHANGE message it has ever sent.
  255  The original version of VR [13] achieved this invariant through stable storage. This protocol logged view
  256  numbers to stable storage during view changes, but it
  257  eschewed the use of stable storage in normal operations
  258  because writing every operation to disk is slow. It used
  259  a recovery protocol to recover all other state, including
  260  the set of committed operations.
  261  A later version, "VR Revisited" [10], claimed to provide a completely diskless mode of operation. It used a
  262  recovery protocol and an extension to the view change
  263  protocol to, in essence, replace each write to disk with
  264  communication with a quorum of nodes. We show below that this protocol is insufficient to ensure continued
  265  correctness of the system.
  266  VR Revisited's recovery protocol is straightforward:
  267  the recovering replica sends a RECOVERY message to
  268  all other replicas.2 If not recovering or in the middle of a view change, every other node replies with
  269  a RECOVERY-RESPONSE containing its view number;

  270  2 This message contains a unique nonce to distinguish responses
  271  from different recoveries if a node recovers more than once.
=== PAGE 5 ===

  272  the leader also includes its log of operations. Once the
  273  recovering replica has received a quorum of responses
  274  with the same view, including one from that view's
  275  leader, it updates its state with the information in the
  276  log.
  277  VR Revisited adds another phase to the view change
  278  protocol. When nodes determine a view change is
  279  necessary, they increment their view number, stop
  280  processing requests in the old view, and send a
  281  START-VIEW-CHANGE message to all other replicas.
  282  Only when replicas receive START-VIEW-CHANGE
  283  messages from a quorum of replicas do they send their
  284  VIEW-CHANGE message to the new leader and proceed
  285  as in the original protocol. The additional phase is intended to serve as the equivalent of a disk write, ensuring that replicas do not commit to a new view until a
  286  majority of them becomes aware of the intended view
  287  change. Together with the recovery protocol, the added
  288  phase aims to prevent violation of the View Change Invariant by ensuring that a crashed replica recovers in a
  289  view at least as high as any VIEW-CHANGE message it
  290  has sent.
  291  By itself, however, this approach is not sufficient. The problem of persistence has only shifted a
  292  layer: rather than a node "forgetting" that it sent a
  293  VIEW-CHANGE message on a crash, it can forget that
  294  it sent a START-VIEW-CHANGE. That is, consider the
  295  following case with three nodes:
  296  Node A initiates a view change by sending
  297  START-VIEW-CHANGE v`1, but this message is delayed.
  298  A crashes and recovers; it receives
  299  RECOVERY-RESPONSEs from B and C. Because they have not seen the START-VIEW-CHANGE
  300  message, A recovers to view v.
  301  B receives A's START-VIEW-CHANGE and sends
  302  START-VIEW-CHANGE v` 1. Because it has a quorum of these messages (from A and itself), it sends
  303  VIEW-CHANGE v `1, but this message is delayed.
  304  B crashes, recovers, and receives
  305  RECOVERY-RESPONSEs from nodes A and C
  306  during recovery. These nodes are in view v and have
  307  no knowledge of the view change, so B recovers to
  308  view v.
  309  B has now sent a VIEW-CHANGE message but has lost
  310  all knowledge of that fact, violating the View Change
  311  Invariant.
  312  This leads to a violation of linearizability. B can
  313  now accept a new operation o in view v by sending

  314  PREPARE-OK messages to the leader (say it is A). This
  315  operation can succeed without C learning of the operations, because A and B together form a quorum. If C
  316  suspects that A has failed and initiates a view change,
  317  it can proceed using only its own log and the delayed
  318  VIEW-CHANGE message from B. Neither log contains
  319  o, so this operation will not be visible to future clients.
  320  Appendix A provides a complete trace of a linearizability violation in the VR Revisited protocol.

  321  4.3 Other Protocols: Paxos Made Live and

  322  JPaxos
  323  Viewstamped Replication is not the only protocol that
  324  attempts to provide diskless recovery for SMR. The
  325  same type of correctness problem exists in two other
  326  protocols, Paxos Made Live [2] and JPaxos [6], and
  327  we briefly review their recovery approaches here; a full
  328  description is in Appendix A.
  329  Paxos Made Live [2] is Google's implementation of
  330  the Multi-Paxos protocol. To handle corrupted disks,
  331  it lets a replica rejoin the system without its previous
  332  state and runs an (unspecified) recovery protocol to restore the application state. The recovering replica must
  333  then wait to observe a full instance of successful consensus before participating. This step successfully prevents the replica from accepting multiple values for the
  334  same instance (e.g., one before and one after the crash).
  335  However, it does not prevent the replica from sending
  336  different promises (i.e., view change commitments) to
  337  potential new leaders, which can lead to a new leader
  338  deciding a new value for a prior successful instance of
  339  consensus.
  340  JPaxos [6], a hybrid of Multi-Paxos and VR, provides a variety of deployment options, including a diskless one. Nodes in JPaxos maintain an epoch vector that
  341  tracks which nodes have crashed and recovered to discard lost promises made by prior incarnations of recovered nodes. However, like VR and PML, this approach
  342  encounters the same problem at a different level: certain failures during node recovery can cause the system
  343  to lose state and violate safety properties.

  447  5.1 Overview
  448  The protocol we propose implements a single reader,
  449  single writer, fault-tolerant non-atomic set that provides
  450  the READ/WRITE interface and virtual stable storage
  451  properties presented in Section 3. Adapted from the definition of regular registers [8], a non-atomic set offers
  452  weaker guarantees than a linearizable one. It guarantees
  453  that a READ returns a set containing all previously successfully written values, but it makes no other guarantees. Importantly, the process is allowed only to write
  454  values to the set, never to remove them. We choose
  455  these weaker guarantees for simplicity, so we can focus
  456  on the main problem – how to correctly obtain diskless
  457  persistence in the presence of crashes and recoveries.
  458  Stronger properties can be implemented on top of
  459  this basic interface. For instance, this protocol could
  460  easily be adapted to provide a multi-reader, multi-writer
  461  non-atomic set. However, to guarantee that a READ
  462  returns all previously written values, a process would
  463  have to read from a (simple, not necessarily consistent)
  464  quorum instead of its local set. A multi-reader, multiwriter set would be a powerful abstraction upon which
  465  to readily build other data structures (e.g., the shared
  466  log of a replicated state machine). Also, it is worth
  467  noting that concurrent instances of this single reader,
  468  single writer set can be run to give all processes access
  469  to virtual stable storage.
  470  While the virtual stable storage protocol is always
  471  safe, the termination of WRITE and recovery are guaranteed only under certain assumptions. Section 5.3
  472  specifies these assumptions and proves protocol correctness.

  473  5.2 Protocol Description
  474  We now describe the protocol, which is presented as
  475  pseudo-code in Algorithm 1. We present the algorithm
  476  using a modified I/O automaton notation. In our protocol, procedures are input actions that can be invoked
  477  at any time (e.g., in a higher level protocol) by the set's
  478  owner, the designated reader/writer process for which
  479  this instance of the protocol is providing virtual stable storage; functions are private methods; and upon
  480  clauses specify how processes handle external events
  481  (i.e., messages, the global startup event, and the transition from DOWN to RECOVERING).
  482  We use guards to prevent actions from being activated under certain conditions. If the guard of a message handler is not satisfied, the message is dropped,
  483  and the action is not executed. If the guard of a procedure is not satisfied, that procedure is inactive and
  484  fails upon invocation.

  485  There is a set of n processes, Π, and every process
  486  has a unique ID in t1,2, ..., nu. Each process maintains
  487  a crash vector of length n, with one entry for each process in system. Entry i in this vector (called i's crash
  488  ID) tracks the latest incarnation of process i. When a
  489  process recovers, it gets a new value from its local,
  490  monotonic clock and updates its crash ID in its own
  491  vector. When the recovery procedure ends, the process
  492  becomes OPERATIONAL and signals this through the
  493  op flag. A process's crash vector is updated whenever
  494  a process learns about a newer incarnation of another
  495  process. Crash vectors are partially ordered, and a join
  496  operation, denoted \, is defined over vectors, where
  497  pv1 \v2qris " maxpv1ris, v2risq.
  498  The crash vector has two purposes: (1) to match requests with their replies (e.g., to ignore old replies), and
  499  (2) to detect whether a process has crashed and recovered. Initially, each process's crash vector is rK, . . . ,Ks,
  500  where K is some value smaller than any value ever returned by any clock, and thus smaller than the crash ID
  501  of any process that has ever crashed and begun recovery.

  502  The single main function of our algorithm,
  503  ACQUIRE-QUORUM, handles both writing values and
  504  recovering. ACQUIRE-QUORUM ensures the persistence of both the process's current crash vector (in particular, the process's own crash ID in the vector) as well
  505  as the value to be written (K, a unique value which every process's local set contains, in the case of recovery).
  506  Additionally, it updates the process's local set to contain all previously written values. This guarantees that
  507  upon recovery, if the set owner calls READ, it will get
  508  those values.

  509  ACQUIRE-QUORUM provides these guarantees by
  510  collecting replies from a quorum of processes and ensuring that those replies are consistent per Section 5.3.
  511  It uses crash vectors to detect when any process that
  512  previously replied could have crashed and thus "forgotten" about the written value and the process's crash ID.
  513  The DISCARD-OLD-REPLIES function detects and removes these replies from the reply set and then resends
  514  the original message. While recovering, processes do
  515  not send replies for WRITEs or other processes' recoveries; all ACQUIRE-REP messages are sent by OPERATIONAL processes.

  702  6 Related work
  703  Early work on the Crash-Recovery failure model proposed protocols to solve the consensus problem [3, 14].
  704  These papers assume stable storage, and do not focus
  705  on state-loss failures, either assuming that processes do
  706  not lose state on crash [14] or that every state transition is persisted to stable storage [3]. (Others persist
  707  only critical state to stable storage [5].) As a result, the
  708  main focus of this work is omission failures, i.e., the
  709  messages that processes do not receive while down.
  710  Aguilera et al. [1] were the first to study consensus
  711  4 In fact, if there is ever a majority of processes that are DOWN
  712  or RECOVERING (where there does not exist a set of messages
  713  currently in the network that will allow any of them to recover),
  714  then no process will ever be able to recover or write again.

  715  in a Crash-Recovery failure model without stable storage. The authors proved that consensus is impossible
  716  to solve in this model unless the number of always-up
  717  processes exceeds the upper bound on processes that
  718  are either eventually-always-down or unstable. Their
  719  failure model, however, differs significantly from ours:
  720  it does not make a distinction between recovering and
  721  operational processes. As a result, it cannot allow processes to recover their state, and hence at least one
  722  process must remain always up. Instead, we show that
  723  it is possible to provide stable storage in the Diskless
  724  Crash-Recovery model as long as there is a quorum of
  725  processes that remain operational for a sufficient time.
  726  This allows any process to crash and fail at some point
  727  during the execution of the protocol, which is expected
  728  to happen in long-lived systems.
  729  An interesting trade-off between stable storage and
  730  a majority of correct process is discussed by Martin et
  731  al. [12]. They consider a particular problem in the DCR
  732  model, eventual leader election, that has weaker requirements than emulating stable storage in this model. In
  733  particular, this problem can be solved even when processes do not always recover the state that they lost.

  734  7 Conclusion
  735  This paper defines the Diskless Crash-Recovery model
  736  (DCR), which supports long-lived distributed services
  737  where nodes may crash and rejoin the system without
  738  their volatile state. Building a correct recovery protocol for this environment is surprisingly subtle; to our
  739  knowledge, it has never been addressed in general. All
  740  previous protocols for the specific case of state machine
  741  replication in this model violate safety under certain
  742  failure scenarios. We present the first general procedure
  743  for transforming Crash-Stop or Crash-Recovery algorithms that rely on stable storage to the DCR model.
  744  Our algorithm, which uses a crash vector to achieve
  745  global knowledge about recovery progress, remains correct in all cases and terminates as long as a majority of
  746  nodes remain operational.

  792  A.1 Viewstamp Replication Revisited
  793  Viewstamped Replication Revisited [10] is a recent version of the classic VR protocol [13] that specifically
  794  targets the DCR model.
  795  Basic VR Protocol. VR is a leader-based algorithm;
  796  the system moves through a series of views in which
  797  one node is designated as the leader. That node is responsible for assigning an order to operations. When
  798  the leader receives a request from a client, it sends
  799  a PREPARE message containing the request and sequence number to the other replicas. Upon receiving
  800  a PREPARE, a replica verifies that it is in the same view
  801  as the leader and then records the request in its log
  802  and responds to the leader with a PREPARE-OK. Once
  803  the leader receives PREPARE-OK messages from a majority of replicas, it executes the request, responds to
  804  the client, and sends a COMMIT message to the other
  805  replicas. The other replicas then execute the request.
  806  VR uses a view change protocol to mask failures
  807  of the leader. If a replica suspects the leader of having failed, it notifies the other replicas. These replicas
  808  stop processing requests, increment their view number,
  809  stop processing requests in the old view, and send a
  810  DO-VIEW-CHANGE message to the leader of the new
  811  view. This request includes the log of operations previously executed or prepared by that replica. Once
  812  the new leader receives DO-VIEW-CHANGE messages
  813  from a majority of replicas, it selects the longest log,
  814  and sends a START-VIEW message to notify the other
  815  replicas that they can resume normal operation. This
  816  protocol ensures that all successfully completed operations persist across view changes: each such operation
  817  must have completed at a majority of replicas, and a
  818  majority of replicas send logs to their leader, so the
  819  new leader will have learned about that operation from
  820  at least one replica.
  821  As described in Section 4, a key invariant in VR is
  822  that once a node has sent a DO-VIEW-CHANGE message to the leader of a view, it must never accept new
  823  operations in prior views – otherwise these operations
  824  could be lost after the view change. A recovery protocol must ensure that this property continues to hold

  826  even if replicas crash and recover.

  885  recovering nodes will receive a reply to their recovery message only after their previous messages (e.g.,
  886  START-VIEW-CHANGE message) have been received.
  887  However, message reordering is not required for this
  888  failure case: we have found a a trace with 7 nodes that
  889  leads to the same behavior, even with FIFO communication channels, as shown in Figure 2.

  961  A.3 JPaxos
  962  JPaxos [6] is a state machine replication protocol based
  963  on Paxos. It is a hybrid between Multi-Paxos and VR,
  964  replacing promises with views. The protocol is presented in several deployment options, including one
  965  that does not use stable storage, i.e., supports the Diskless Crash-Recovery model.5
  966  Recovery Protocol. JPaxos provides a protocol for
  967  the DCR model called epoch-based recovery. This protocol is similar in spirit to our use of crash vectors: it
  968  5The protocol is actually presented as using stable storage on
  969  process initialization, but only to store a monotonic value on write.
  970  The monotonic counter available in our DCR model fills this need.

  972  attempts to maintain a vector clock of how many times
  973  each node has crashed and recovered. Each node updates this vector when it sends a recovery response to
  974  another node, and includes a copy of its vector in the
  975  PROPOSE-OK messages that it uses to commit to a new
  976  view (i.e., the equivalent of the DO-VIEW-CHANGE
  977  message). It then uses these vectors to discard all
  978  PROPOSE-OK messages that do not come from a consistent quorum.
  979  JPaxos's epoch-based recovery protocol has one critical difference from ours. It treats recovery as complete
  980  once it has received RECOVERY-ANSWER messages
  981  from a quorum of replicas. In contrast, our protocol
  982  requires recovery responses from a consistent quorum
  983  of replicas. That is, it discards recovery responses from
  984  the quorum if it learned that the replica that sent the
  985  response itself crashed and recovered.
  986  This subtle change has important implications for
  987  correctness. Without this, JPaxos does not correctly
  988  handle recovery of nodes when the nodes they are recovering from can themselves crash and recover. When
  989  this happens, JPaxos can allow a node to recover in a
  990  way that simultaneously 1) causes the node to lose the
  991  promise that it made in a previous PREPARE-OK, yet 2)
  992  does not allow other nodes to detect that the promise
  993  might have been lost. We give such an example below.
