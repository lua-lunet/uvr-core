   17  Byte-addressable non-volatile memory (NVM) proposes a
   18  new opportunity to enable file systems with better performance and durability by adding a new persistent caching layer.

   20  unknown. This paper conducts a crash consistency case study
   21  of Open CAS, a popular block-level caching system. Through

   29  1 Introduction

   30  Byte-addressable non-volatile memory (NVM) opens a
   31  new opportunity in designing high-performance block-level
   32  caching systems for file systems. NVM provides byte addressability and low-access latency like DRAM and offers
   33  data persistence like HDD. Like page cache in traditional
   34  file systems, similar hybrid storage is adopted in persistent
   35  caching systems, where a fast persistent device is used for a
   36  caching layer and a slow but large storage capacity is used for
   37  a backend file system to achieve high I/O performance while
   38  reducing monetary costs. For example, Open CAS [11], an
   39  advanced caching solution recently developed by Intel, allows
   40  NVM, SSD, and other high-performance storage devices to
   41  be used as a caching layer for improving the I/O performance
   42  of Linux file systems.
   43  While the primary goal for introducing non-volatile memory into block-level caching systems is to improve the performance of file systems that are typically installed at the
   44  HDDs, i.e., backend devices, it also improves the data durability of file systems. Unlike traditional block-level caching

  107  2 Block-Level Caching Systems
  108  Caching systems have long been the most popular design for
  109  improving the performance of storage systems [6,20,40]. In
  110  caching systems, consider a system with two storage layers: a
  111  (fast, expensive, small) performance layer and a (slow, cheap,
  112  large) capacity layer. With caching, all data resides in the capacity layer, and copies of hot data items are placed, via cache
  113  replacement algorithms [7,34], in the performance layer. With
  114  a high-enough fraction of requests going to the fast layer, the
  115  overall performance approaches the peak performance of the
  116  fast layer. In the context of block-level caching systems, e.g.,
  117  Open CAS [11], OrthusCAS [50], First Responder [42], Assise [1], and NVCache [15], they are generally implemented
  118  as a kernel module in operating systems, and provide caching
  119  service for block devices which typically are file systems.
  120  1We have reported the issues exposed in our study to the developers and

  123  The advent of fast storage and interconnect technologies, such as persistent memory (PMem) [37], Non-Volatile
  124  Memory Express (NVMe) [30], and Compute Express Link
  125  (CXL) [13], present new opportunities in boosting the performance of memory hierarchy and caching systems. With
  126  new storage technologies like 3D XPoint [43], NVMe SSDs
  127  (over the PCIe bus) achieve much higher bandwidth (e.g.,
  128  8 GB/s) and lower latency (e.g., 3µs) [58]. Further, byteaddressable persistent memory has also been commercially
  129  available [37] and offers an order of magnitude higher capacity than DRAM and within an order of magnitude performance of DRAM [52].

  130  2.1 Why Crash Consistency Does Matter

  131  Although the main goal for introducing nonvolatile memory
  132  to caching systems is for performance boosting [12,19,24,
  133  25, 49,51,57], this technique also poses opportunities and
  134  challenges to the reliability of end-to-end file systems, including caching layers and backend file systems. During the
  135  past decades, there have been many related works to improve
  136  the reliability of file systems [14,23,29,35,36,55], and they
  137  typically modeled the behavior of in-memory cache, i.e., page
  138  cache, as all information in the caching layer is lost upon a
  139  crash. However, when nonvolatile memory is introduced into
  140  block-level caching systems, this stale crash model doesn't
  141  hold, and it provides a new opportunity for caching systems to
  142  reuse the cached data for fast system recovery. For example,
  143  Open CAS provides a configuration option for the system
  144  managers to perform a fast recovery and reuse the cached
  145  data from an unplanned system shutdown.
  146  Although a persistent caching layer automatically provides
  147  data durability due to the natural behavior of nonvolatile memory, i.e., it retains data even when power is removed, adding
  148  a new tiered persistent caching layer also poses critical challenges to the system reliability. First, a persistent caching system is much more complex than traditional in-memory page
  149  cache. To meet the various use scenarios and user requirements, a persistent caching system normally provides multiple cache modes to cope with. For example, compared with
  150  a single cache mode in page cache, Open CAS provides six
  151  cache modes for the different use scenarios. Similarly, First
  152  Responder offers seven cache modes for users. Furthermore,
  153  to maximally deliver the performance of nonvolatile memory,
  154  caching systems normally design complicated caching algorithms and asynchronous data movement mechanisms to fit
  155  in nonvolatile memory characteristics. For example, in OrthusCAS [50] the cache eviction strategy not only considers
  156  the characteristics of workloads but also is decided by the
  157  performance model of caching devices. In general, the more
  158  complicated software design and implementation means the
  159  systems are less reliable.
  160  Second, testing persistent caching systems poses unique
  161  requirements and challenges. In caching systems, the code

  163  logic usually requires a heavy workload to change the caching
  164  system status and/or trigger the specific cache operation. For
  165  example, cache eviction and cache cleaning operations generally require a heavy workload to be implicitly triggered by
  166  cache replacement policies [7,34]. The requirement for heavy
  167  workloads makes traditional system testing tools, such as
  168  fuzzing [4,17,23,53] and black-box testing [29] less effective
  169  which tend to generate lightweight test cases by applying syntax and semantic mutations [22,54]. Furthermore, implicitly
  170  triggering through heavy workloads also means there are enormous potential crash points in the heavy-workload test case
  171  for a test framework to explore. Therefore, crash-consistency
  172  tests to caching systems specifically require a test framework
  173  that can generate heavy workloads while precisely identifying
  174  crash points for implicit cache operations.
  175  Third, it still remains unknown whether the added persistent
  176  caching layer is compatible with the diverse reliability features of file systems. For file systems, the reliability features
  177  such as logging [18,39], journaling [48], write-back [47,48],
  178  and copy-on-write [21], are designed on a simple crash model
  179  that file systems on the persistent device, e.g., HDD, are the
  180  only survived data source upon system crashes [3]. When
  181  introducing a new persistent caching layer in end-to-end file
  182  systems, this stale crash model doesn't hold anymore, and the
  183  reliability design based on this model may not be compatible
  184  with the newly added persistent caching layer. Actually, in
  185  case of a system crash, data movement between the persistent caching layer and the backend file system immediately
  186  terminates, which is the same as in-memory page cache. However, during the post-recovery process, the survived data in
  187  caching layers and file systems can be inconsistent. If the
  188  reliability design between caching layers and file systems is
  189  not well coordinated, the end-to-end file system may suffer
  190  from durability loss or data inconsistency issues.
  191  In this work, we focus on the crash consistency of blocklevel caching systems. We specifically take Open CAS as an
  192  example and try to answer the system reliability questions in
  193  two aspects: does the persistent caching layer maintain crash
  194  consistency in case of system crashes? Are state-of-the-art
  195  reliability features of file systems compatible with the newly
  196  added persistent caching layer?

  228  3.1 Data Structures
  229  A cache line is the smallest data unit that Open CAS can
  230  manage. Every occupied cache line is associated with a
  231  core line on the backend file system and the cache line
  232  will be eventually written back to its associated core line.
  233  Open CAS supports different cache line sizes ranging
  234  from 4KB to 64KB. For each cache line, Open CAS maintains a small portion of metadata, which contains the information including core id, core line number, and valid
  235  and dirty bits for every sector. The core id determines on
  236  which core is the core line corresponding to the given
  237  cache line located, whereas the core line number determines the precise core line location on the backend file
  238  systems. Valid and dirty bits define the current cache line
  239  state. When a cache line is valid, it means that it's mapped
  240  to a core line determined by a core id and a core line number. Otherwise, all the other cache line metadata information
  241  is invalid and should be ignored. When a cache line is in
  242  an invalid state, it may be used to map core line accessed
  243  by I/O requests, and then it becomes valid. The dirty bit determines if the user data stored in the caching layer is in sync
  244  with the corresponding data on the backend file systems. If
  245  a cache line is dirty, then only data on the caching layer
  246  is up to date, and it needs to be flushed at some point in the
  247  future and be marked as clean by zeroing the dirty bit.

  317  Mapping is a cache operation of linking up a core line

  349  in the caching layer. It's performed when the core line
  350  accessed during a write request is mapped into the caching
  351  layer and the accessed sectors are marked as valid.
  352  Invalidation is a cache operation of marking one or more
  353  cache line sectors as invalid. It can be done during the
  354  handling of discard requests, during purge operations, or as a
  355  result of some internal cache operations.

  357  the backend file system. flushing is a cache management
  358  operation and has to be triggered by users or Open CAS Udev
  359  rule. It is typically done for safely detaching the backend file
  360  system from the caching system or recovering the backend
  361  file system without risking data loss.

  382  3.3.1 Implicit Cache Operation
  383  Block-level caching systems like Open CAS are typically
  384  integrated into Linux operating system as a kernel module.
  385  The advantage of the integration is that the cache solution is
  386  transparent to the user applications and existing storage infrastructures, and no storage migration or application changes are
  387  required. However, due to restrictions by the existing Linux
  388  user interfaces, i.e., the POSIX standard [32], some cache
  389  operations cannot be explicitly invoked by the user interfaces.
  390  It also means that it is hard for a test framework to test these
  391  operations by explicitly invoking while performing system
  392  crashes. Furthermore, as a portion of Linux operation system,
  393  kernel modules are unexpected to change for software testing,
  394  e.g., adding the stub code. Actually, these cache operations
  395  are only invoked by internal cache policies, e.g., Least Recently Used (LRU) [7,34,50], which are typically decided by
  396  a heavy workload. We call these cache operations an implicit
  397  cache operation. For example, in Open CAS, eviction and
  398  cleaning are implicit cache operations. In summary, due to
  399  the implicit invocation and heavy workload requirement, an
  400  implicit cache operation is hard to test, and we will introduce
  401  our solution, workload-oriented test framework (WLOT) in
  402  Section 5.

  403  3.4 Post-Recovery Process

  404  Open CAS post-recovery process provides two options to recover a caching layer from a crash. The first option is to deal
  405  with a caching layer as page cache in volatile memory (e.g.,
  406  DRAM). Specifically, Open CAS reinitializes the caching
  407  layer with new metadata, which clears the cache device, resulting in the loss of all cache data that is currently residing
  408  in the cache device.

  409  2025 USENIX Annual Technical Conference 753
=== PAGE 7 ===

  410  The second option, a more sophisticated one, is to restart a
  411  caching layer and utilize the previous cache data, including
  412  metadata, in the cache device for a fast recovery. Specifically,
  413  Open CAS first performs CRC checksums for all metadata
  414  sections in the cache device and then compares them with
  415  ones stored in the recovery section to guarantee the metadata
  416  data integrity. To guarantee the data integrity of the recovery
  417  section, the recovery size is kept under 4K, which makes Open
  418  CAS update the recovery section atomically with a single 4K
  419  I/O. Then, Open CAS mounts the core devices, i.e., backend
  420  file systems, and the corresponding file system recovery process is activated according to the file system's reliability configuration. If the cache device and core device are successfully
  421  recovered, the recovered data in the caching layer can be accessed and reused by the backend file system and the applications. Open CAS recovery process is performed automatically
  422  in accordance with dynamic device management Udev [26].
  423  Open CAS administrator can set the post-recovery process
  424  option and enable the caching layer to automatically flush the
  425  dirty data to the recovered file systems by configuring the inbuilt Udev rules in 60-persistent-storage-cas.rules.
  426  Note that although Open CAS developers also mention the
  427  potential risk of data durability loss under this recovery option [9], there is no clear description or guidance to help
  428  users to evaluate the tradeoff between performance benefit
  429  and reliability risk for choosing the suitable recovery options.
  430  Therefore, we believe a thorough study is much needed.

  431  4 Crash-Consistency Tests to Caching Systems

  432  In this section, we first investigate the general principles for
  433  crash-consistency tests to a block-level caching system. Then,
  434  we take the in-build test suite in Open CAS as an example
  435  and specifically inspect its crash-consistency tests. Our aim
  436  is to find whether Open CAS in-build crash-consistency tests
  437  can guarantee data consistency in case of system crashes.

  438  4.1 Principle of Reliability Test

  439  Principle 1: Crash-consistency tests should explore the crash
  440  behaviors of a caching system for crashes at any time. Although crash consistency and data durability may not be guaranteed in any crash scenario, a system crash, such as a power
  441  outlet and system corruption, can happen at any time. It's
  442  necessary to understand complete crash behavior rather than
  443  solely crash scenarios where crash consistency is promised
  444  by caching system developers. By contrast, the crash consistency behaviors of file systems under any time system crashes
  445  were well studied [36]. More importantly, it helps system administrators to identify the root cause of crash inconsistency
  446  issues in the end-to-end file system. For end-to-end file systems, it can include multiple persistent caching layers, local
  447  file systems, and remote storage components. Each persistent
  448  layer and component may exhibit various crash consistency

  449  754 2025 USENIX Annual Technical Conference

  450  characteristics. Finding the root cause of crash inconsistency
  451  issues to such systems can be a daunt task. Understanding
  452  the complete crash consistency characteristics of individual
  453  storage layers eases system administrators to identify the root
  454  cause of crash inconsistency issues.
  455  Principle 2: Crash-consistency tests should cover all crashvulnerable cache operations. Like crash-consistency tests to
  456  other storage systems, it's necessary for test cases to cover
  457  all crash-vulnerable operations that potentially cause crash
  458  inconsistency. For example, many file system test tools [23,
  459  29] more focus on testing the write-related operations since
  460  they change the internal state and the persistent user data.
  461  For caching systems, if a cache operation updates user data
  462  and/or caching system metadata in the caching layer, it will
  463  change the caching system state and be potentially vulnerable
  464  to system crashes. This cache operation can be seen as a
  465  crash-vulnerable cache operation. For example, in Open CAS,
  466  all cache operations can be seen as crash-vulnerable cache
  467  operations. By contrast, the cache operation for responding
  468  to a read cache hit request is not a crash-vulnerable cache
  469  operation since it doesn't change user data or caching system
  470  metadata.
  471  Principle 3: Crash-consistency tests should include diverse
  472  reliability features of file systems to guarantee compatibility with them. The state-of-the-art reliability features of file
  473  systems, such as data journaling, copy-on-write, etc., are designed under the assumption that cached data is not available
  474  after crashes. During the post-recovery process, reusing the
  475  cached data in the persistent caching layer for a fast recovery
  476  may cause compatibility issues such as durability loss and
  477  crash inconsistency.

  808  6 Compatibility Tests with File Systems

  809  In Section 5, we showed crash-consistency tests to the caching
  810  layer. In this section, we try to explore how compatible Open
  811  CAS is with diverse reliability features of state-of-the-art file
  812  systems, i.e., whether post-recovery processes of file systems
  813  can coordinately work well with persistent caching layers.
  814  Our compatibility tests with file systems indicates that some
  815  reliability features of file systems are not compatible with
  816  Open CAS: incompatibility issues are various from minor
  817  issues, e.g., performance degradation to serious ones, e.g.,
  818  durability loss.
  819  This section is organized as follows. First, we discuss our
  820  test framework, procedure, and workloads we used to conduct compatibility tests. Then, we present the results and our
  821  observations.

  822  6.1 Test Framework
  823  Our test framework for compatibility tests is similar to crashconsistency tests to caching layers. The difference is the backend file system setting. We choose five state-of-the-art file systems with diverse reliability features as backend file systems.
  824  The target file systems roughly fall into three categories: 1) file
  825  systems with no or simple reliability features, i.e., ext-2 [8];
  826  2) file systems with journaling approaches, i.e., ext-3 [48]
  827  and ext-4 [47] in writeback, ordered, journal, and nodealloc
  828  configurations, and xfs [45]; 3) copy-on-write file systems,
  829  i.e., btrfs [27]. Table 3 lists backend file systems and their
  830  reliability features, i.e., configuration settings, we choose for
  831  our compatibility tests.

  832  6.2 Test Procedure and Workloads
  833  We study the compatibility of Open CAS under the more
  834  realistic crash-recovery procedures. During the crash procedure, we perform a crash as a clean power fault. Specifically, at the time of crashes, all I/O operations between the
  835  caching layer and the backend file system terminate immediately, and the caching layer cannot receive I/O errors from

  836  758 2025 USENIX Annual Technical Conference

  837  the backend device. In addition, all in-DRAM data and metadata that are related to the caching system and backend file
  838  system are not available after a crash. For the recovery procedure, we perform the post-recovery process on both the
  839  caching layer and the backend file system. Also, we reuse
  840  the cached data and metadata in the caching layer for a fast
  841  recovery. The specifics of our crash-recovery procedure in
  842  our test framework are as follows: we use unmount and Open
  843  CAS's command casctl stop to perform synthetic crashes
  844  on the both caching layer and backend file system. We utilize
  845  mount and Open CAS's command casctl start to perform
  846  the caching layer post-recovery process. After that, we utilize
  847  mount to automatically invoke the post-recovery process of
  848  the backend file system.
  849  Since we are only interested in the post-recovery process
  850  of caching layers and backend file systems, we apply with
  851  the simpler workload and cache mode settings than Section 5.
  852  We only choose the repeat write workload and two write
  853  cache modes, i.e., write-back mode and write-only mode for
  854  compatibility tests. The reason for choosing WB and WO
  855  modes is that these cache modes can cache the latest user
  856  data, i.e., dirty data, in the caching layer and leave the stale
  857  user data in the backend file system, which enables us to
  858  expose more interesting results such as crash inconsistency or
  859  durability loss during the post-recovery process. Specifically,
  860  We first restore a file on the backend file system and then
  861  apply repeat write (RW) workload in the write-back mode
  862  and write-around mode separately, in which we repeatably
  863  write a small portion of the cached data to the caching layer.
  864  For the crash point setting, we simultaneously inject synthetic crashes on both the caching layer and the backend file
  865  system. In addition, since we attempt to activate the postrecovery process of backend file systems, we always inject
  866  synthetic crashes during the backend file system performing
  867  I/O operation. We utilize the cache operations cleaning to
  868  raise I/O requests to the backend file system.
  869  For the check criteria, we flush the cached data to the backend file system and compare the recovered file system image
  870  with oracle, which is generated by performing the same workload without a crash. We also check log files and API returns
  871  in both Open CAS and the backend file system for error messages.

  939  For the file systems with journaling-related configurations,
  940  if a crash causes an incomplete journal transaction, the file
  941  systems will automatically switch to read-only mode in postrecovery process. As a result, flushing the dirty data to the
  942  recovered file systems incurs I/O error. Naively forcing the
  943  file systems to the read-write mode incurs a similar dilemma
  944  situation which we discussed in Observation 1.
  945  Observation 3: For ext-3 and ext-4 in journal configuration
  946  and xfs, performing the post-recovery process and flushing
  947  the dirty data to the file systems incur durability loss with
  948  an error. Similar to Observation 2, ext-3 and ext-4 in journal
  949  configuration and xfs automatically switched into read-only
  950  mode when they were remounted to the caching system due
  951  to the incomplete journal transaction. However, forcing these
  952  file systems to read-write mode still cannot solve all compatibility issues. Different from Observation 2, ext-3 and ext-4
  953  in the journal configuration and xfs write both data block
  954  and the related metadata, which are normally larger than 4K
  955  caching line size, to the journal. During the post-recovery
  956  process, if the journal transaction is complete, the data block
  957  and metadata in the journal are checkpointed to its final inplace block location. Otherwise, the incomplete transaction
  958  is discarded. On the other hand, Open CAS only guarantees data transaction at the grain of caching line size. By
  959  setting the dirty bits for each cache line , Open CAS can
  960  identify whether a cache line is successfully synchronized
  961  to the backend file system or not. Furthermore, during the
  962  post-recovery process Open CAS doesn't redo the last failed
  963  cache operation, i.e., cleaning in our case. Since the flushed
  964  dirty cache line didn't include the complete journal transaction, the file systems discarded the flushed data and raised
  965  an I/O error. Although Open CAS persisted the complete journal transaction data in the caching layer, part of them had
  966  been marked as a clean state i.e., setting the dirty bit to zero,
  967  and cannot be flushed to the backend file system again but
  968  be evicted by eviction cache operation which finally cause
  969  durability loss.
  970  Observation 4: For btrfs, performing the post-recovery process and flushing the dirty data to the file system incur durability loss without an error. Btrfs is a copy-on-write file system
  971  that writes to the same block only once except for the superblock which contains root-node information. Specifically,
  972  btrfs first writes to a log tree to record changes and then writes
  973  the data block and any related metadata to new locations and
  974  updates the roots in its superblock. In case of a crash, btrfs
  975  effectively reverts the contents of the data block and metadata
  976  back to its old state. Similar to Observation 3, btrfs simply
  977  discards the incomplete user data and metadata during the
  978  post-recovery process. Flushing the rest data blocks and metadata cannot help btrfs to maintain crash consistency and keep
  979  user data up-to-date. However, unlike Observation 3, flushing
  980  the dirty data to btrfs does not return an error which finally
  981  causes a silent durability loss.
  982  In summary, Open CAS fails to be compatible with the

  984  diverse reliability features of state-of-the-art file systems. The
  985  incompatibility issues are various from minor issues, e.g.,
  986  performance degradation to serious ones, e.g., durability loss.

  988  may suffer from the more serious incompatibility issues.

  989  7 Beyond Open CAS
  990  In addition to Open CAS, we have applied the same test
  991  framework used in Section 5 to a simpler caching system,
  992  NVCache [15]. NVCache is an approach that leverages a
  993  non-volatile main memory (NVMM) as a write cache to improve the write performance of legacy applications. Similar to Open CAS, NVCache intercepts and redirects in userspace I/O function calls to achieve this transparency. Also,
  994  NVCache guarantees data durability once returning an acknowledgment to users. Unlike Open CAS, NVCache uses
  995  log structures for persisting cache line and its metadata.
  996  In each write request, NVCache appends the new user data
  997  at the end of cache line area and directly embeds a commit flag within each cache line. The commit flag indicates
  998  whether cache line data is successfully committed to the
  999  caching layer or not. In order to handle non-committed writes
 1000  left in the caching layer after a crash, NVCache firstly saves
 1001  user data to cache line and then updates the corresponding
 1002  commit flag from non-committed to committed.
 1003  Our initial results indicate that NVCache is also vulnerable
 1004  to system crashes. As shown in table 4, NVCache gracefully
 1005  recovers data from system crashes for the write cache after
 1006  returning an acknowledgment. Moreover, thanks to the log
 1007  structure to cache line, NVCache maintains crash consistency to the caching layer if a crash happens during cache
 1008  miss and hit which is better than Open CAS. However, similar
 1009  to Open CAS, NVCache returns bad data to users if a crash
 1010  happens during the cache operation cleaning, the only implicit cache operation in NVCache. In addition, we see the
 1011  significant throughput collapses when performing the cache
 1012  operation cleaning which indicates the generalization of the
 1013  workload-oriented test for identifying the running state of
 1014  implicit cache operations.
 1015  In summary, so far we have studied two examples: Open
 1016  CAS, a complex block-level caching system with techniques
 1017  to maintain crash consistency, and NVCache, a simpler blocklevel caching system with few mechanisms to provide extra
 1018  reliability. Both are vulnerable to system crashes. In addition,
 1019  since OrthusCAS [50] was integrated with Open CAS with
 1020  minor modifications for performance optimization, we believe
 1021  most of our observations of Open CAS should also apply to
 1022  OrthusCAS. It seems that regardless of the complexity of the
 1023  caching system and the amount of machinery used for crash
 1024  consistency, implicit cache operations are still a bottleneck for
 1025  crash consistency, and systematical crash-consistency tests are
 1026  necessary for various caching systems. In addition, reliability
 1027  feature co-design on caching layers and backend file system
 1028  is necessary for keeping crash consistency.

 1037  8 Related Work
 1038  There is a lack of related work on crash-consistency tests to
 1039  block-level caching systems. In addition, previous work on
 1040  the crash-consistency tests to end-to-end file systems simply
 1041  models the crash behavior of caching layers as an in-DRAM
 1042  page cache in which all cached data is lost in case of a crash.
 1043  We compare our work with ones on file systems and databases.
 1044  Crash-consistency test frameworks and fault injection techniques have been widely used to analyze the robustness and
 1045  find bugs in file systems and databases [23,29,36,44,55,56]
 1046  For example, Crashmonkey [29] exhaustively performs file
 1047  system crash-consistency tests within a bounded space, a
 1048  heuristic pruning rule based on the bug study of real file systems. Hydra [23] mutates both file systems image and operation sequences when performing feedback-oriented fuzzing
 1049  to identify crash consistency bugs. Block Order Breaker
 1050  (BOB) [36] creates crash states from recorded I/O to show
 1051  that different file systems persist file-system operations in significantly different ways. The Application-Level Intelligent
 1052  Crash Explorer (ALICE), explores application-level crash vulnerabilities in databases, key-value stores, etc. The logging
 1053  and replay framework from Zheng et al. [56] is focused on verifying ACID guarantees of databases, works on iSCSI disks,
 1054  and uses four dedicated manual workloads.
 1055  However, our work on Open CAS is the first comprehensive crash consistency analysis of the block-level caching system that covers carefully controlled crash-consistency tests
 1056  to caching layers and compatibility tests with backend file
 1057  systems.

 1058  9 Conclusion and Discussion
 1059  In this paper, we analyzed a representative block-level caching
 1060  system, Open CAS, to study the reliability of the persistent
 1061  caching layer in case of system crashes. We introduce a novel
 1062  approach the workload-oriented test to systematically perform crash consistency experiments to the caching layer and
 1063  selectively perform integration test to the diverse reliability
 1064  features of file systems. We presented our observations about
 1065  Open CAS crash consistency and compatibility with the diverse reliability features of file systems.
 1066  Although these are always the tradeoffs one has to make
 1067  for crash consistency, as one tier of the end-to-end file system,
 1068  the block-level caching layer should provide strong crash
 1069  consistency against crashes. We conclude by discussing some
 1070  techniques that caching systems can use to increase system

 1071  USENIX Association
=== PAGE 14 ===

 1072  reliability and compatibility.
 1073  Checksums in cache lines: Caching systems could protect
 1074  the user data in the cache line by using checksums. For example, Open CAS could use a checksum inside cache line
 1075  in the caching layer, update it on caching operation update,
 1076  and verify the checksum on read-related caching operations
 1077  or during the post-recovery process (Observation 3 in Section 5.3). However, this does incur an overhead in computation as well as some complexity in implementation.
 1078  Data synchronization during post-recovery process: To
 1079  deal with the stale user data in the caching layer due to system
 1080  crashes (Observation 4 in Section 5.3), a caching system could
 1081  synchronize user data with backend file systems during postrecovery process.
 1082  Reliability-feature-aware post-recovery process: A caching
 1083  system could be aware of the reliability features of the backed
 1084  file system, and take a well-co-designed post-recovery process
 1085  with them (Observation 1 - 4 in Section 6.3).
