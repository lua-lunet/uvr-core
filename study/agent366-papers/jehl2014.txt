    6  Abstract. This paper addresses reconfiguration of a Replicated State
    7  Machine (RSM) in an asynchronous system. It is well known that consensus cannot be solved in an asynchronous system. Therefore an RSM providing strong consistency, cannot guarantee progress in an asynchronous
    8  system. However, we show that reconfiguring the RSM is possible in a
    9  purely asynchronous system. This differs from all existing reconfiguration
   10  methods which rely on consensus to choose a new configuration. Since a
   11  reconfiguration to a new set of machines or even a different datacenter
   12  can serve to restore synchrony between replicas, asynchronous reconfiguration can also serve to increase the availability of an RSM.

   13  1 Introduction

   14  State machine replication [1] is a common approach for building fault-tolerant
   15  services. In this approach, all service replicas of the state machine execute the
   16  same requests. To ensure that replicas remain consistent after multiple updates,
   17  the order of requests has to be synchronized across replicas. Typically this is accomplished using a consensus protocol, such as Paxos [2, 3], which is an essential
   18  component in a Replicated State Machine (RSM). Paxos helps to prevent the
   19  replicas from entering an inconsistent state, despite any number of replica failures. Moreover, the RSM can continue to process new requests, as long as more
   20  than half of the replicas remain operational. If this bound is violated, however,
   21  the current RSM is forced to stop making progress indefinitely. Therefore real
   22  systems need to be able to react to failures and include new replicas, before this
   23  bound is exceeded. Additionally, in todays cloud computing infrastructures, a
   24  fault tolerant, replicated service should be able to add, or move replicas based on
   25  the systems load and redistribute the replicas to new physical locations. Therefore real systems should include a reconfiguration method, ensuring a continuous
   26  correct service while enabling the changes above.
   27  The initial descriptions of the state machine approach [1] and Paxos [2, 3]
   28  described a reconfiguration method. This method lets the RSM reconfigure itself
   29  by executing a special command, which specifies the new configuration. It was
   30  refined and implemented, e.g. for the Zookeeper service [4], enabling reconfiguration for a replicated system in production.

   31  To use this method however, the old configuration (being changed) must
   32  be operational to complete the reconfiguration command. Thus the old configuration needs to have a single leader and a majority of correct servers, to use
   33  reconfiguration. Vertical Paxos [5] developed a different reconfiguration method,
   34  showing that reconfiguration is possible with only a minority of correct replicas,
   35  if it is coordinated by an abstract, fault tolerant configuration manager. In Vertical Paxos, synchrony is needed to guarantee a working configuration manager.
   36  In this paper we target the synchrony assumption of traditional reconfiguration. We present ARec, an asynchronous reconfiguration protocol, showing that
   37  reconfiguration is possible in an asynchronous system. This means that, agreeing
   38  on a single leader is not necessary to change to a new set of replicas. Reconfiguring an RSM can therefore take place during a period of asynchrony, e.g. when
   39  clocks are not synchronized and the network introduces unpredictable delays.
   40  This is an important result, because it means that replicas could be moved to a
   41  set of machines or a datacenter where synchrony assumptions hold.

   42  1.1 ARec: Reconfiguration without Consensus

   43  A configuration is a set of replicas running on different machines. To change the
   44  set of replicas, a reconfiguration simply proposes a new configuration. We assume
   45  that any two configurations are disjoint. Thus every replica belongs to exactly
   46  one configuration. However we do not require replicas of different configurations
   47  to run on different machines. Thus reconfiguration also enables operations like
   48  adding or removing one replica. For example, to add a replica to the configuration
   49  {r1, r2, r3}, running on machines m1, m2, and m3, one simply proposes a new
   50  configuration {r0 , r0 , r0 , r } on machines m , m , m , and m . Thus our recon-
   51  1 2 3 4 1 2 3 4
   52  figuration allows all possible changes both in number and placement of replicas.
   53  The main challenges in reconfiguration are to ensure that when stopping
   54  the old configuration, exactly one new configuration starts and that all requests
   55  that have been committed by the old, stay committed in the new configuration.
   56  Assume for example two new configurations C1 and C2 are proposed, while
   57  an initial configuration C0 is running the RSM. Classical reconfiguration uses
   58  consensus in one configuration to choose the next configuration. Thus replicas
   59  in C0 would choose whether to change to C1 or C2. Thus, the new configuration
   60  that is chosen can then simply copy the state from C0.
   61  Since consensus is impossible in an asynchronous system [6], ARec uses eventual consistency to determine the next configuration. For this, we assume that
   62  new configurations are issued together with a unique timestamp. If several configurations are proposed concurrently, we let the one with the highest timestamp
   63  be the next configuration. Thus, if the replicas eventually become aware of all
   64  configurations, they will agree on which configuration should take over.
   65  However this complicates state transfer, since it is difficult to determine which
   66  configuration can transfer a correct state to the new configuration. Assume for
   67  example C1 and C2 have timestamps 1 and 2. In this case, we can ignore C1
   68  and C2 can receive the state from C0. However if C2 is only proposed after C1

   69  received the state from C0 and started the RSM, C2 has to copy its state from
   70  C1. This problem is solved in Section 4.
   71  Another problem in asynchronous reconfiguration is to find a correct state for
   72  the new configuration to start. In classical reconfiguration, the old configuration
   73  again uses consensus to decide on the last request. Any replica can then tell
   74  this decision to the new configuration, which can choose new requests. In an
   75  asynchronous system, the old configuration cannot decide on a final request.
   76  Thus, some requests might be committed in the old configuration but remain
   77  unknown to some replicas. ARec therefore collects the state of a majority of
   78  a configuration's replicas, to determine the new configuration's state. Luckily
   79  leader change in Paxos already includes a mechanism to find any value, that
   80  might be committed.We reuse this mechanism in ARec.

   81  2 Paxos

   82  In this section we briefly present Paxos [2, 3] and how replicas agree on a single
   83  request. We then elaborate on how this is used to implement an RSM.

   84  2.1 Paxos
   85  Paxos is a consensus algorithm used by several participants (our replicas) to
   86  decide on exactly one value (our request). To get chosen, a value has to be proposed by a leader and accepted by a majority of the replicas. Only one value
   87  may be chosen and every correct replica should be able to learn what was decided on. Paxos assumes a partially synchronous network, tolerating asynchrony,
   88  but relying on eventual synchrony to guarantee progress. That means that single
   89  messages can be lost or arbitrarily delayed (asynchrony). However, eventually all
   90  messages between correct processes arrive within some fixed delay (synchrony).
   91  Since an initial leader might fail and a single leader cannot be chosen during
   92  periods of asynchrony, multiple leaders can try concurrently to get their values decided. To coordinate concurrent proposals, leaders use preassigned round
   93  numbers for their proposals. Replicas cooperate only with the leader using the
   94  highest round. However, after leader failure it might be necessary for replicas
   95  to cooperate with several leaders. Paxos solves this problem by enforcing that,
   96  once a value has been decided, leaders of higher rounds will also propose this
   97  locked-in value. Therefore in the first phase of a round, the leader determines if
   98  it is safe to propose any value or if there is another value that was already voted
   99  for. In the second phase, the leader then tries to get a safe value accepted. If not
  100  interrupted a round proceeds as follows:

  101  Prepare (1a) The leader sends a Prepare message to all replicas, starting a
  102  new round.
  103  Promise (1b) Replicas return a Promise not to vote in lower rounds, and
  104  include their last vote.
  105  Accept (2a) After receiving a quorum of Promise messages, the leader determines a safe value and proposes it to all replicas in an Accept message.
=== PAGE 4 ===

  106  Learn (2b) Replicas vote for the proposal, by sending the value and round
  107  number in a Learn message to all other replicas, if no higher round was
  108  started in the meantime.
  109  Decide Receiving a quorum of Learns for one value and round, a replica
  110  decides on that value.
  111  A quorum is a majority of the replicas and a quorum of messages is a set of
  112  messages of the same type, sent by a quorum in the same round. A value v is
  113  chosen if a quorum of Learn messages with value v was sent. The Decide step
  114  above ensures that only chosen values get learned.The above can be repeated in
  115  new rounds, until all replicas have learned the value. From a quorum of Promise
  116  messages, safe values can be determined following these rules:
  117  – If no replica reports a vote, all values are safe.
  118  – If some replica reports a vote in round r for value v and no replica reports
  119  a vote in a round higher than r, then v is safe.

  120  These rules ensure, that once a value is chosen, only this value is safe in higher
  121  rounds. Thus all replicas learn the same value, even if they learn it in different
  122  rounds. We call this property safety. Clearly to be able to report their votes in a
  123  later Promise message, replicas have to store their last vote (round and value)
  124  in variables vrnd and vval. For a replica to be able to promise not to vote in
  125  lower rounds, it must also store the last round it participated in. We refer to this
  126  as rnd. These variables are all that is needed to ensure safety. We call them the
  127  Paxos State of a replica. We also write Φ for the tuple (rnd, vrnd, vval).
  128  We say that an execution of Paxos is live if a value can get learned. For
  129  Paxos to be live, a leader has to finish a round, communicating with a quorum
  130  of correct replicas, while no other leader starts a higher round.

  131  2.2 The Paxos State Machine
  132  A state machine is an application that, given a state and a request, deterministically computes a new state and possibly a reply to the request. When this state
  133  machine is replicated for fault tolerance, it is important that the replicas execute
  134  the same requests to maintain a consistent state among themselves. Since several requests might interfere with each other, it is also important that replicas
  135  execute requests in the same order.
  136  The replicas in a Paxos State Machine achieve this by using Paxos to choose
  137  requests. For every new request, a new Paxos instance is started. Its messages
  138  are tagged with a request number ⟩, saying that this instance is choosing the
  139  ⟩th request. A replica only executes the ⟩th request, if it has executed request
  140  ⟩ − 1 and has learned the request chosen for the ⟩th instance via the Paxos
  141  protocol. Thus, as long as Paxos is live, new request can be processed. These
  142  will eventually be learned and executed by all correct replicas.
  143  Though execution has to be done in correct order, the Paxos instances can
  144  be performed concurrently. Thus it is possible to propose and choose a request
  145  in instance ⟩ + 1, without waiting for the ⟩th request to be learned.

  146  Note that, if concurrent Paxos instance have the same leader, round change
  147  can be common for all instances. Thus, Prepare and Promise messages for
  148  concurrent Paxos instances can be sent in the same message. [3] explains how
  149  this is done, even for all future instances.

  150  3 Liveness for a Dynamic RSM

  151  In this section, we define the problem of asynchronous reconfiguration. That
  152  is, we both define the interface used to issue reconfigurations and specify the
  153  liveness conditions for a Dynamic RSM and ARec.
  154  A reconfiguration is initialized by sending ⟨Reconf, C , i, C ⟩ to the new
  155  ⟩ l
  156  configuration C⟩. Here, ⟩ is the unique timestamp of the new configuration and
  157  Cl is some old configuration. The old configuration is needed, since the new
  158  configuration needs to contact the service to take over. We require configurations
  159  to be disjoint. Thus a replica only belongs to a single configuration. However
  160  replicas from different configurations can easily be placed on the same machine.
  161  Note that a Reconf request will typically be sent by a replica in configuration
  162  Cl that wants to move the service, e.g. in response to asynchrony or crashes. It
  163  can also be sent by an external configuration manager.
  164  We say a configuration is available, if a majority of the configuration's replicas are correct. A static Paxos state machine is guaranteed to process incoming
  165  requests, if the initial configuration is available and eventually a single leader is
  166  elected. In a dynamic system, this condition becomes more complicated. While a
  167  reconfiguration might require several old and new configurations to be available,
  168  a dynamic system should not require an old configuration to remain available
  169  after a new configuration has taken over and copied all relevant state. We say
  170  that a replica in a new configuration is stateful, if it has copied a correct system
  171  state from a previous configuration. Note that this system state might differ
  172  from the individual states of single replicas in the old configuration. We define
  173  a configuration to be stateful, when a majority of the replicas in this configuration are stateful. Thus, if a configuration is stateful and available, there exists
  174  a correct and stateful replica that can disseminate a correct system state to the
  175  other correct replicas. Clearly, a Dynamic RSM always needs at least one available stateful configuration. Also, new configurations must stay available during
  176  reconfiguration. We therefore define that a Dynamic RSM, at any time in an
  177  execution, depends on the stateful configuration with highest timestamp, Cmax,
  178  and all configurations with higher timestamps. We can now define liveness of
  179  reconfiguration as the following:

  180  Definition 1 (ARec Liveness). For any execution, if
  181  (a) at all times the configurations that the system depends on are available, and
  182  (b) ⟨Reconf, C⟩, i, Cl⟩ is sent by a correct client for a stateful configuration Cl,
  183  then the system will eventually no longer depend on Cl.

  184  Note that ARec Liveness does not guarantee that the state machine actually
  185  makes progress. That is because this always requires some synchrony assumption.
=== PAGE 6 ===

  186  Similar, ARec Liveness does not guarantee, that ⟨Reconf, C⟩, i, Cl⟩ actually results in C⟩ running Paxos. That makes sense, since in the case of concurrent
  187  reconfigurations, we don't want several configurations to start. However it guarantees that Cl will stop running Paxos, and replicas in Cl need not stay available.
  188  Clearly implementing ARec Liveness makes sense only if also the state machine
  189  is live, under reasonable assumptions. We therefore define the following:
  190  Definition 2 (Dynamic RSM Liveness). For any execution, if
  191  (a) at all times the configurations that the system depends on are available,
  192  (b) only finitely many configurations are initialized, and
  193  (c) eventually a single leader is elected in Cmax,
  194  then requests submitted to this leader will be processed.
  195  Note that synchrony between processes in Cmax is needed to guarantee (c).
  196  (b) says that eventually no more reconfigurations are issued. This guarantees
  197  that eventually, one configuration will be Cmax forever. This configuration can
  198  run Paxos without being interrupted by reconfigurations. Since it is impossible
  199  to agree on group membership in an asynchronous system [7], it can be theoretically challenging to guarantee condition (b). For example, if reconfiguration
  200  is used to replace faulty replicas with new ones, false detections might cause
  201  infinitely many reconfigurations, even with only finitely many crashes. This is
  202  because in an asynchronous system, a failure detector might falsely detect a
  203  crash, causing a reconfiguration, in which a correct replica is replaced by a new
  204  one. In practice however, the number of reconfigurations are typically bounded
  205  because of their cost. That is, reconfiguration usually requires new machines,
  206  possibly transferring large amounts of state between replicas, and may also disrupt service delivery.

  348  Just as Prepare and Promise messages in Paxos, we can send NewConf

  352  of an execution history on the new configuration. A more practical solution is
  353  to provide a snapshot of the replicated application to the new replicas when
  354  invoking Reconf. If this snapshot incorporates all requests chosen in the first k
  355  Paxos instances, it is enough to exchange NewConf and CPromise messages

  528  7 Related Work

  529  As mentioned in the introduction, the classical method to reconfigure an RSM
  530  was already explained in [1] and [2, 3]. Variations of this method where presented
  531  in [9] and it was refined and implemented in works like [10] and [4]. All these
  532  works use consensus to decide on the next configuration, resulting in a unique
  533  sequence of configurations, where each reconfiguration only involves one old and
  534  one new configuration. For this, a configuration must be available and have a
  535  single correct leader before it can be changed by reconfiguration.
  536  The work most closely related to ARec is Vertical Paxos [5]. Vertical Paxos
  537  also changes configuration between rounds rather than between instances, and
  538  uses Paxos' first phase to deduce a starting state for the new configuration, similar to ARec. Also similar to ARec, a new configuration C⟩ knows about one
  539  past configuration Cl that is stateful and must receive a quorum from all configurations with sequence numbers between l and ⟩. Different from ARec however,
  540  Vertical Paxos assumes that upon receiving a reconfiguration request, configuration C⟩ knows about all configurations Cj with l ≤ j < i. Finally, Vertical Paxos
  541  relies on an abstract, fault tolerant configuration manager to order new configurations. Instead of relying on synchrony in the old configuration, Vertical Paxos
  542  relies on synchrony in the configuration manager, which must be implemented
  543  by another RSM to be fault tolerant. Note also that the configuration manager
  544  RSM cannot use Vertical Paxos to reconfigure itself, but has to rely on classical
  545  reconfiguration. ARec does not rely on a separate configuration manager.
  546  That asynchronous reconfiguration is possible has previously only been proven
  547  for atomic R/W registers [11]. In their protocol, DynaStore, a reconfiguration
  548  does not specify a new configuration as a set of replicas, but as a set of operations, each adding or removing one replica. When several reconfigurations are
  549  issued concurrently, DynaStore takes the union of these reconfigurations as the
  550  configuration that the replicas eventually agree upon. If reconfigurations are issued by several parties, this interface has some disadvantages. For example, if
  551  several parties try to reduce the number of replicas, but disagree on the replica
  552  to be removed, they could by accident remove all replicas. Thus it is possible to
=== PAGE 15 ===

  553  violate DynaStore's Liveness property by issuing an "unlucky" reconfiguration.
  554  This is not possible with ARec.
  555  As described in [9], a Dynamic RSM has similarities to group communication
  556  systems that provide totally ordered message delivery [12]. However, while view
  557  synchronous communication requires that a message received by one process in
  558  view v is received by all processes in view v, therefore consensus is required to
  559  end a view. A Dynamic RSM ensures that requests learned by one replica in a
  560  configuration, are learned by all replicas in some future configuration. Therefore
  561  ARec only requires consensus in some future configuration.

  562  8 Conclusion

  563  We have presented ARec a reconfiguration protocol for a Paxos State Machine
  564  that enables reconfiguration in a completely asynchronous system. To our knowledge this is the first protocol for asynchronous reconfiguration of an RSM. We
  565  have precisely specified the liveness conditions for asynchronous reconfiguration,
  566  improving on previous specifications, which allow unlucky reconfigurations to
  567  break liveness. Using ARec, availability of RSM based systems can be improved,
  568  since reconfiguration can be used to restore synchrony, and thus enable the
  569  RSM to make progress. However, since our work mainly focused on proving
  570  the possibility of asynchronous reconfiguration, we expect that ARec can be
  571  significantly optimized when adjusting it to a specific system.
