   31  1 Introduction

   32  State machine replication is a well-known method of implementing a fault-

   33  tolerant service [11, 14]. The service is described as a deterministic state ma-

   34  chine that accepts client commands and produces outputs, and multiple replicas

   35  of the state machine are implemented. The different replicas operate indepen-

   36  dently and asynchronously. However, they all have the same initial state and

   37  execute the same sequence of commands, so they all produce the same sequence

   38  of outputs. Since each replica can respond to any client request, using f + 1

   39  replicas allows the system to tolerate the failure of f processes.

   40  Implementing a replicated state machine requires a fault-tolerant algorithm

   41  for choosing the sequence of state machine commands executed by the replicas.

   42  Such an algorithm must guarantee that, for each i, if a replica executes c as
   43  the ith command in the command sequence, then (i) c was issued by a client,
   44  and (ii) no replica executes a different command as the ith command in the

   45  sequence.

   46  Different replicas operate asynchronously, so they may execute the same

   47  command at different times. Moreover, if the output produced by executing

   48  command number i does not depend on what commands are executed as num-

   49  bers 1 through i − 1, then a replica may generate the output for command i

   50  before it generates the output for command i − 1. Hence, although the replicas

   51  all produce the same sequence of outputs, the outputs in that sequence could

   52  be generated in different orders.

   53  An asynchronous algorithm for choosing the sequence of state machine com-

   54  mands requires at least 2f + 1 processes to tolerate the (non-malicious) failure

   55  of f of them [4]. Hence, we need more processes to choose the commands than

   56  to execute the replicas. The processes that choose the sequence of commands

   57  are called acceptors, and the ones that execute the replicas are called learners.

   58  We can choose a sequence of commands by using a separate consensus protocol to choose each one, where the ith consensus protocol chooses the ith
   59  command. The protocol used to choose the ith command will be called the
   60  ith consensus instance. Separate consensus instances need not have disjoint

   61  implementations—for example, messages belonging to separate instances may

   62  be batched in a single physical message. However, the separate instances are

   63  logically independent, which makes reasoning about their correctness easier.

   64  Different commands in the command sequence can be chosen concurrently.
   65  Processes can begin the ith consensus instance without waiting for instances

   66  1 to i − 1 to terminate. This concurrent processing is vital to the efficiency

   67  of an asynchronous distributed system. For example, in a typical leader-based

   68  protocol, the current leader can send proposals for commands one after another,

   69  without waiting for acknowledgements of previous proposals.

   70  In a static system, all consensus instances are instances of the same algo-

   71  rithm. In particular, they all use the same sets of acceptors and learners—sets

   72  we call the configuration. However, achieving long-term resilience requires a

   73  reconfigurable system, in which the configuration can change. A reconfigurable

   74  1
=== PAGE 4 ===

   75  system requires that, for each i, there be agreement on the configuration that

   76  is to execute consensus instance i.

   77  In state machine replication, reconfiguration has traditionally been done

   78  by using the state machine itself to perform special reconfiguration com-

   79  mands [10, 14, 15]. The obvious method is to have a reconfiguration command

   80  change the configuration for all subsequent instances until the next reconfigu-

   81  ration command. However, since a consensus instance cannot be executed until

   82  the configuration executing it is known, this prevents concurrent execution of

   83  different instances. We can permit concurrent execution of up to α consensus

   84  instances by instead letting a reconfiguration command executed as command

   85  number i determine the configuration starting from instance i + α, where α is

   86  a system parameter [10]. Instances i + 1 through i + α can begin execution

   87  once commands 1 through i have been chosen. In practice, α can be made large

   88  enough so the system never has to wait to learn the current configuration, if

   89  no reconfiguration command has been issued. However, this approach has two

   90  somewhat awkward properties:

   91  • To force a reconfiguration to happen quickly, a reconfiguration command

   92  must be followed by α − 1 no-op commands that have no effect.

   93  • If α > 1, then several reconfiguration command could appear among com-

   94  mands i through i +α−1, meaning that one configuration is choosing the

   95  next several configurations. This can happen when using a leader-based

   96  consensus algorithm if a failure causes multiple processes to each think it

   97  is the leader.

   98  In this paper, we propose an alternative reconfiguration procedure based on

   99  stoppable state machines. A stoppable state machine has a special class of stop-

  100  ping commands that terminate the state machine. If a stopping command is
  101  chosen as the ith command, then the complete sequence of chosen state ma-

  102  chine commands has length i. That is, if a stopping command is chosen as

  103  command i, then no command can ever be chosen as command j for j > i.

  104  We implement the system state machine by executing a sequence of stopping

  105  state machines. Each consensus instance of a single stopping state machine is

  106  executed by the same configuration. Reconfiguration is performed by stopping

  107  the current state machine and starting a new one with a new configuration. The

  108  stopping command specifies the configuration used to execute the new stopping

  109  state machine. The system's complete sequence of state machine commands is

  110  the concatenation of the command sequences of the individual stopping state

  111  machines. If one stopping state machine is terminated by executing a stopping

  112  command as command number i, then we can number the commands of the next

  113  stopping state machine starting with i + 1. This provides consecutive numbers

  114  for the commands in the system state machine.

  115  This method of reconfiguring with stoppable state machines seems to corre-

  116  spond more closely to the way engineers have traditionally approached recon-

  117  figuration. It is similar to view changing in group communication [1, 2, 3, 5,

  118  2
=== PAGE 5 ===

  119  6, 7, 8, 12]. However, the purpose of this paper is to present Stoppable Paxos,

  120  an algorithm for implementing a stoppable state machine. We have discussed

  121  reconfiguration only to indicate why stoppable state machines may be useful.

  122  A detailed description of how stoppable state machines are used for reconfigu-

  123  ration and how they relate to group communication is beyond the scope of this

  124  paper.

  125  Stoppable Paxos is a variant of Paxos [10]. Our goal was to devise an

  126  algorithm that is as efficient as Paxos in the absence of a stopping command.
  127  This is not easy to do because Paxos allows the choosing of the ith command to

  128  be performed concurrently for different values of i. We must avoid the possibility
  129  that the ith command is chosen and a stopping command is concurrently chosen
  130  as the jth command for j < i. The obvious method is to delay the choice
  131  of the ith command until all previous commands are chosen, but this would

  132  considerably degrade the performance. Stoppable Paxos adds no messages or
  133  delays to ordinary Paxos, except that a leader cannot propose an ith command

  134  if, in the normal course of execution, it learns that a stopping command has
  135  been chosen or was proposed and may have been chosen as the j th command

  136  for some j < i. Although the basic idea of the algorithm is not complicated,

  137  getting the details right was not easy.

  138  The following section reviews ordinary Paxos. The Stoppable Paxos algo-

  139  rithm is described in Section 3, and its correctness properties are stated in

  140  Section 4. A proof of correctness appears in the appendix for reading at the

  141  program committee's discretion.

  142  2 Paxos Revisited

  143  Ordinary Paxos assumes a distributed system of processes communicating by

  144  messages. Processes can fail only by stopping, and messages can be lost or

  145  duplicated but not corrupted. Timely actions by non-failed processes and timely

  146  delivery of messages among them is required for progress; safety is maintained

  147  despite arbitrary delays and any number of failures.

  148  The core of Paxos is a consensus algorithm (originally called the Synod

  149  algorithm). In a consensus algorithm, client processes can propose values, and

  150  learner processes each learn a value. We use the term command for a value that

  151  may be proposed. A consensus algorithm must satisfy two safety properties:

  152  Consistency No two learners can learn different commands.

  153  Nontriviality Any command learned must have been proposed.

  154  For almost all consensus algorithms, including Paxos, nontriviality is easily seen

  155  to hold. We therefore ignore it and consider only consistency. A consensus

  156  algorithm must also ensure that, under some suitable hypothesis, a command is

  157  learned.

  158  A replicated state machine is implemented with a sequence of instances of a
  159  consensus algorithm, the ith instance choosing the ith state-machine command.

  161  We briefly review the Paxos consensus algorithm and how it is used to implement

  162  a state machine. We consider the static case, in which the same processes

  163  implement all consensus instances.

  164  2.1 The Paxos Consensus Protocol

  165  The Paxos consensus algorithm assumes three sets of processes: leaders that

  166  propose commands, acceptors that choose a command, and learners that learn

  167  the chosen command. These sets are not necessarily disjoint—in particular,

  168  leaders are usually learners. We ignore the clients, which provide commands

  169  for the leaders to propose. Leaders propose commands in numbered ballots.

  170  For simplicity, we take ballot numbers to be natural numbers. A configuration

  171  assigns to each ballot a unique leader that performs actions of that ballot. For

  172  example, the leader of ballot number b may be determined by the low-order bits

  173  of b. We also assume certain sets of acceptors to be quorums, subject only to

  174  the requirement that the intersection of any pair of quorums is non-empty.

  175  Acceptors accept and store proposed commands and their ballot numbers.

  176  In particular, each acceptor a maintains the value bal[a] that records the highest

  177  ballot number that a has received, "voted for", and acknowledged, and the value

  178  vote[a][b] that records the command proposed with ballot number b that a has

  179  voted for. Initially, bal[a] equals −∞ and vote[a][b] equals >, a special value

  180  that is not a command.

  181  For any acceptor a, let maxbal(a) be the largest ballot number b for which

  182  vote[a][b] 6= >, and to equal −∞ if vote[a][b] = > for all b. Define maxvote(a)

  183  to equal vote[a][maxbal(a)], or > if maxbal(a) = −∞. Instead of maintaining

  184  the entire array vote[a], acceptor a need only record the values maxbal(a) and

  185  maxvote(a). For simplicity, we ignore this optimization.

  186  At any point during the execution of the consensus algorithm, the state

  187  consists of the values of the arrays bal and vote and the sets of messages that

  188  have been sent and received by the processes. A state function is an expression

  189  whose value depends on the state.

  190  A ballot consists of two phases, each with two sub-phases. In the first phase,

  191  the leader determines whether a command may have been chosen in a lower-

  192  numbered ballot. In the second phase, it proposes a command and the acceptors

  193  vote for that command. The command is chosen if a quorum of acceptors vote

  194  for it.

  195  The heart of the algorithm is the state function val2a(b,Q), which the ballot

  196  b leader computes on the basis of messages it receives in phase 1 from acceptors

  197  in the quorum Q. If val2a(b,Q) equals a command v, then v might have been

  198  chosen in a lower-numbered ballot and the leader must propose it in phase 2.

  199  If val2a(b,Q) equals >, then no command has been or ever will be chosen in a

  200  lower-numbered ballot, and the leader can propose any value. We define val2a

  201  below. First, we describe the following actions that the algorithm can perform.

  202  Phase1a(b) The leader of ballot number b sends the message ⟨"1a",b⟩ to all

  203  acceptors. (This action is always enabled.)

  232  that c ≥ d for all ⟨d,w i ∈ R, and define val2a(b,Q) to equal v. (For any state

  233  reachable during execution of the algorithm, ⟨c,vi ∈ R and ⟨c, wi ∈ R imply

  234  v = w, so this uniquely defines val2a(b,Q).) For later reference, we also define

  235  mbal2a(b, Q) to equal c.

  236  Although the algorithm executes a sequence of ballots, those ballots need not

  237  be executed sequentially. It is possible for two or more leaders to be executing

  238  Phase1a and/or Phase2a actions concurrently, and for the resulting messages to

  239  be received by different acceptors in different orders. This can impede progress

  240  but cannot cause inconsistency.

  241  To achieve progress, Paxos uses some algorithm to select a unique active

  242  leader. The active leader starts a new ballot with a number higher than that

  243  of any other ballot it knows to have been started. An acceptor a informs the

  251  2.2 The Paxos State Machine Implementation

  252  Paxos executes a sequence of instances of the Paxos consensus algorithm. For
  253  each instance i, it maintains an array votei , where votei[a][b] is the value of

  254  vote[a][b] for instance i of the consensus algorithm. Paxos achieves its efficiency

  255  by executing Phase 1 simultaneously for all instances of the consensus algorithm

  256  as follows, using the same value of bal[a] for all of them. More precisely:

  257  1. The ballot b leader simultaneously executes Phase1a(b) for all instances,

  258  sending a single Phase1a message to each acceptor.

  259  2. Upon receipt of a Phase1a message, an acceptor simultaneously executes

  260  Phase1b actions for all instances, bundling the infinite set of Phase1b

  261  messages in a single physical message. (That physical message contains

  262  only a finite amount of information because, for any acceptor a and ballot
  263  number b, the value of votei[a][b] is > for all but a finite number of

  264  instances i.)

  265  We add an extra instance parameter to the Phase2a and Phase2b actions and

  266  to the val2a and mbal2a state functions. For example, Phase2a(i, b,v,Q) is

  267  the Phase2a(b,v,Q) action of instance i and val2a(i,b,Q) is the state function

  268  val2a(b,Q) of instance i. We subscript messages with instance numbers, so
  269  ⟨"1b", . . .⟩i is a Phase1b message sent for instance i (and bundled with Phase1b

  270  messages sent for other instances).

  271  In normal operation, there is a single active leader that receives client com-

  272  mands and performs Phase2a actions for them. When the active leader fails, a

  273  new active leader is selected that performs a Phase1a(b) action for a new ballot

  274  number b higher than any that has been used so far. When the active leader

  275  receives Phase1b messages from a quorum Q, for each i it finds either:

  276  1. val2a(i,b,Q) is a command v, meaning that v may have been chosen in

  277  instance i at some ballot less than b.

  278  2. val2a(i,b,Q) = >, meaning that no command can have been (or can ever

  279  be) chosen in instance i at any ballot less than b.

  280  In case 1, it performs a Phase2a(i,b,v, Q) action to try to get v chosen. Let

  281  k be the largest instance for which this case holds, so it is the highest instance

  282  in which any acceptor in Q has voted. For all instances i with i < k such that

  283  val2a(i,b,Q) = >, the leader performs a Phase2a(i,b,noop,Q) action to try

  284  6
=== PAGE 9 ===

  285  to choose a noop command that does nothing. Without waiting for responses

  286  to its Phase2a messages, the leader can begin performing Phase2a actions in

  287  instances higher than k for client commands.

  288  It is possible for a leader to learn a set of commands that have already been

  289  chosen and to optimize this procedure to avoid unnecessary actions for those

  290  chosen commands. This optimization is straightforward and we will not discuss

  291  it.

  292  Remember that what we have just described is how Paxos works in the

  293  normal case when there is a single active leader. Consistency is maintained

  294  even if multiple processes believe themselves to be the active leader. A single

  295  active leader is required only to ensure progress.

  296  3 The Stoppable Paxos Algorithm

  297  Stoppable Paxos uses the same variables and sends the same messages as Paxos.

  298  Before describing the actual algorithm, we sketch how the Stoppable Paxos

  299  algorithm works in the normal case when a (single) new active leader is selected.

  300  As in ordinary Paxos, the new active leader performs a Phase1a(b) action

  301  for a suitable ballot number b. The algorithm differs from Paxos if the leader

  302  finds that a stopping command stp might have been chosen in some instance i.

  303  In that case, the leader performs Phase2a actions for lower-numbered instances

  304  as before. However, to ensure that the state machine stops when it should, we

  305  must ensure that the leader does not perform a Phase2a action for any instance

  306  greater than i if the stopping command actually was chosen in instance i.

  307  The problem is to decide what the leader should do if it finds val2a(i,b, Q)

  308  equal to a stopping command stp and val2a(j,b,Q) equal to any command, for

  309  some i and j with j > i. The answer depends on the values of mbal2a(i,b, Q)

  310  and mbal2a(j,b,Q). Remember that, for any k, the value of mbal2a(k,b, Q)

  311  is the highest ballot number less than b for which some acceptor a in Q set
  312  votedk [a]. If mbal2a(j, b,Q) > mbal2a(i,b,Q), then the stopping command c

  313  could not have been chosen in (a lower ballot of) instance i, so stp is voided—

  314  meaning that the leader acts as if val2a(i,b,Q) equals >. Otherwise, the leader

  315  performs a Phase2a(i,b,stp, Q) action to try to get stp chosen and does nothing

  316  in any higher-numbered instance, including instance j.

  317  If the leader performs a Phase2a action for a stopping command in instance

  318  i, then it performs no Phase2a actions for instances greater than i. Otherwise, it

  319  begins processing new client commands as in ordinary Paxos. It continues until

  320  it performs a Phase2a action for a stopping command, whereupon it performs

  321  no further Phase2a actions for any higher-numbered instance. Except when

  322  the leader is prevented from performing Phase2a actions because of a stopping

  323  command, Stoppable Paxos allows all the concurrent execution that ordinary

  324  Paxos does.

  325  We now begin our description of the actual Stoppable Paxos algorithm. As

  326  in ordinary Paxos, the algorithm can be optimized to take advantage of knowl-

  328  edge of already-chosen commands. For simplicity, we ignore this optimization.

  329  Stoppable Paxos then differs from Paxos only in the enabling conditions of the

  330  Phase2a action. We begin with an intuitive description of these enabling con-

  331  ditions, which are labeled E1–E6.

  332  Conditions E1–E3 are the same as for ordinary Paxos except that, in E3,

  333  we replace val2a by a new state function sval2a. Recall that E 3 requires

  334  val2a(i,b,Q) to be the proposed command if it does not equal >, because

  335  in that case it might have been chosen in a lower-numbered ballot. We will

  336  define sval2a(i,b, Q) to be the same as val2a(i,b,Q) except that it equals >

  337  if val2a(i,b,Q) is a stopping command that is voided. As indicated above, a

  338  stopping command is voided if information about higher-numbered instances

  339  implies that the command could not have been chosen in this instance in a

  340  lower-numbered ballot.

  341  Enabling condition E4 applies iff v is a stopping command, in which case it

  342  requires the two conditions:

  343  E4a A Phase2a action must not have been performed for ballot b of a higher-

  344  numbered instance.

  345  E4b If the leader was not forced (by the value of sval2a) to propose the stopping

  346  command, then it must not be forced to propose any command in a higher-

  347  numbered instance.

  348  Condition E5 asserts that the leader has not performed a Phase2a action for

  349  a stopping command in ballot b of a lower-numbered instance, and condition

  350  E6 asserts that the value of sval2a does not force the leader to propose such a

  351  value.

  352  It appears that progress is impossible if the ballot b leader is forced (by E3)

  353  to propose a stopping command in an instance i and to propose some command

  354  in another instance j > i. If it executes the Phase2a action for instance i, then

  355  E5 prevents it from executing the Phase2a action for instance j . If it executes

  356  the action for instance j first, then E4a prevents it from executing the action

  357  for instance i. This situation is prevented by voiding. The definition of sval2a

  358  ensures that the Phase1b messages for instance j void the stopping command

  359  in instance i.

  360  Unlike in ordinary Paxos, in Stoppable Paxos the separate consensus in-

  361  stances are not logically separate. Enabling conditions E4–E6 and the definition

  362  of sval2a for a ballot in one instance depend on Phase2a actions performed and

  363  Phase1b messages received for that ballot in other instances. However, this im-

  364  plies no extra messages or delays. As in ordinary Paxos, the Phase1b messages

  365  for all instances are bundled together; and no enabling condition requires that

  366  a Phase2a action for another instance be done first. The enabling conditions

  367  require only that certain actions not have been done.

  402  We now state the correctness properties satisfied by Stoppable Paxos. A rigor-

  415  Consistency =∆ ∀ i, b, c,v,w : Chosen(i,b,v) ∧ Chosen(i,c,w) ⇒ (b = c)
  416  Stopping =∆ ∀ i, j < i, v ∈ StopCmd, w :

  418  Like ordinary Paxos, our Stoppable Paxos assures progress if eventually there

  419  is a unique leader for a high enough ballot number that is nonfaulty and can

  420  communicate with a nonfaulty quorum. The precise property we prove is that

  421  the following condition holds, for all b and Q.

  430  the acceptors in Q is eventually received.

  432  Condition P1(b,Q) means that the ballot b leader eventually executes the

  433  Phase1a(b) action, and that it and the acceptors in Q perform ballot b actions

  435  eventually the leader and the acceptors in Q are nonfaulty and communicate

  436  reliably with one another, using a retransmission protocol to recover from lost

  437  messages. Condition P3(b) asserts that no ballot numbered greater than b is

  438  ever started.

  439  Conditions P1–P3 are the same ones under which ordinary Paxos achieves

  506  Appendix: The Proof of Correctness

  507  We now prove that Stoppable Paxos satisfies its safety and liveness properties.

  508  For clarity and conciseness, we write simple temporal logic formulas with two

  509  temporal operators: 2 meaning always, and 3 meaning eventually [13]. We use
  510  a linear-time logic, so 3 can be defined by 3F =∆ ¬2¬F, for any formula F.

  511  For a state predicate P, the formula 2P asserts that P is an invariant, meaning

  512  that it is true for every reachable state. The temporal formula 32P asserts

  513  that at some point in the execution, P holds from that point onward.

  514  We define a predicate P to be stable iff it satisfies the following condition:

  515  if P is true in any reachable state s, then P is true in any state reachable from

  516  s by any action of the algorithm. We let stable P be the assertion that state

  517  predicate P is stable. It is clear that a stable predicate is invariant if it is true

  518  in the initial state. Because stability is an assertion only about reachable states

  519  s, we can assume that all invariants of the algorithm are true in state s when

  520  proving stability.

  521  Our proofs are informal, but careful. The two complicated, multi-page proofs

  522  are written with a hierarchical numbering scheme in which ⟨x ⟩y is the number
  523  of the yth step of the current level-x proof [9]. Although it may appear intimi-

  524  dating, this kind of proof is easy to check and helps to avoid errors.
