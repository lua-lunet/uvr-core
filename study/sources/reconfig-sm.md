Classical way of implementing the state machine:
with a consensus algorithm for choosing a single command
the implementation runs a sequence of logically separate
instances of the consensus algorithm (instance i to choose the
i th command )
Most SM implementations use a special subset of learners
called leaders, through which a client can propose a command
c that will be then assigned number i and proposed as the
command to be chosen by consensus instance i
A leader does not have to wait until command i is chosen to
propose another command i + 1 ⇒ different commands can be
chosen concurrently

Reconfiguring a State Machine

Reconfiguration made easy (cont’d)
In order to have a reconfigurable SM implementation, we
introduce cfg, a component specifying the current
configuration. (i.e. the configuration at cmd i is determined
by the value of cfg in the state immediately following
execution of command i − 1)
We add a new cmd: rcfg(C ), specifying a new configuration C
The obvious way to define the SM is to let executing rcfg(C )
in order to set cfg to C . This method is called R1 .
The problem with R1 : it prevents concurrent processing of
neq proposed cmds since the configuration used to execute
instance i + 1 of the consensus algorithm can be changed by
executing command i
⇒ the SM implementation cannot begin choosing cmd i + 1
untill cmd i has been chosen
Francesco Bongiovanni – INRIA

Reconfiguring a State Machine

Reconfiguration made easy (cont’d)

To allow concurrent processing of cmds, we define a SM with
an additional state such that executing rcfg(C ) as cmd
number i causes cfg to change after executing command
i + α − 1, for some positive integer α
A reconfiguration command can thus take effect α cmds later,
allowing concurrent processing of up to α cmds. This method
is called Rα .
