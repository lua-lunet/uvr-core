# Storage failure and diskless replication evidence

The diskless argument has two parts. Forced local writes can put storage latency and storage faults on the agreement path. Removing them moves the durability obligation to live replicas; it does not remove the possibility of data loss after a correlated loss of the quorum. Local writes at clean shutdown and boot still require their own crash-consistency argument.

## Sources published since 2023

The five source PDFs, their abstracts and single-column reading copies are in [storage-risk-2024-2026](./storage-risk-2024-2026/). The reading copies preserve extracted PDF text; inspect the PDFs for figures, tables and mathematical notation.

- Rob Norris, [*Why fsync() on OpenZFS can’t fail (and what happens when it does)*](https://papers.freebsd.org/2024/asiabsdcon/norris_openzfs-fsync-failure/), AsiaBSDCon 2024. A specific OpenZFS failure and recovery path could let `fsync()` return success when the changes had not reached disk. This is direct evidence against treating a successful flush call as an unconditional, end-to-end persistence proof. It is a particular defect, not a claim about every file system.
- Yuqi Zhang et al., [*MSFRD: Mutation Similarity based SSD Failure Rating and Diagnosis for Complex and Volatile Production Environments*](https://www.usenix.org/conference/atc24/presentation/zhang-yuqi), USENIX ATC 2024. Production SSD telemetry motivates online detection of failures that affect storage reliability and performance. Its predictive result is evidence that drive failure is an operational concern, not a measured uVRR failure rate.
- Shaohua Duan and Youmin Chen, [*Crash Consistency in Block-Level Caching Systems: An Open CAS Case Study*](https://www.usenix.org/conference/atc25/presentation/duan-shaohua), USENIX ATC 2025. Crash experiments show that a persistent cache can violate crash consistency and interfere with file-system reliability features. A durable local write therefore depends on the whole storage stack, including caches.
- Maximilian Kuschewski et al., [*BtrLog: Low-Latency Logging for Cloud Database Systems*](https://arxiv.org/abs/2606.27051), accepted to VLDB 2026. The authors report that remote block storage adds write latency and cost, while object storage has attractive durability and storage cost but unsuitable per-append latency and cost for OLTP. Their design acknowledges writes through a quorum of SSD-backed log nodes and archives larger segments to object storage outside the commit path. Its comparison with EBS is specific to the evaluated workload and deployment.
- Chaolei Hu et al., [*Come Hell or Still Water: Alleviating Tail Latency in Cloud Block Store*](https://www.usenix.org/conference/nsdi26/presentation/hu-chaolei), NSDI 2026. Alibaba Cloud production workloads exhibit cloud block-store tail-latency spikes driven by bursts from a small set of virtual disks; scheduling and throttling changes reduce measured tails. This supports treating remote block-write latency as variable, rather than assuming a uniform flush cost.

The storage case for uVRR is consequently precise: the normal agreement path avoids a dependency on local persistence and its device, file-system, cache and cloud-block-store behaviours. A clean shutdown still pays for durable writes, and safety after volatile state loss still depends on the protocol's live-quorum and reincarnation rules. No source above establishes that an arbitrary diskless design is safer than a correctly engineered disk-backed design.
